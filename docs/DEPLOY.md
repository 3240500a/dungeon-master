# DEPLOY.md — деплой на TimeWeb (Облачный сервер / VDS)

> Это БОЕВОЙ деплой. Рабочее место на второй машине (игра + редакторы + ИИ-генератор) — [SECOND_MACHINE.md](SECOND_MACHINE.md),
> нагрузочный стенд — [tools/deploy/STAND.md](../tools/deploy/STAND.md).

Игра = **один Node-процесс**, который отдаёт статику клиента (`packages/client/dist`) + REST `/api/*`
+ WebSocket `/ws` на **одном домене**. Клиент сам находит сервер на том же origin (`/api`,
`wss://<host>/ws`) — доп. настройка клиента не нужна.

## Какой сервер брать
**«Облачный сервер» (VDS/VPS, KVM)** — НЕ «Облачное приложение» (App Platform: эфемерная ФС, БД
сотрётся при редеплое) и НЕ «Виртуальный хостинг» (shared). Спека для плейтеста:
- Ubuntu **24.04 LTS**
- **2 vCPU / 2 ГБ RAM** (2 ГБ — чтобы сборка клиента не упёрлась в память; при 1 ГБ собирай
  `client/dist` локально и заливай)
- 15–30 ГБ NVMe, публичный IPv4

Нужны **Node 24** (см. `.nvmrc`) и **PostgreSQL 16+**.

## Cloud-init (необязательно, но удобно на первый раз)
Поле «Cloud-init» при создании сервера = скрипт, который выполнится ОДИН РАЗ при первом запуске
(от root). Вставь туда этот скрипт — он поставит базу (swap, Node 24, git, Caddy, фаервол), и шаг 1
ниже делать не нужно (сразу переходи к доставке кода):
```bash
#!/bin/bash
set -eux
# swap 2 ГБ — чтобы сборка клиента не упала по памяти на 2 ГБ RAM
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
apt-get update && apt-get install -y curl git ufw
# Node.js 24
curl -fsSL https://deb.nodesource.com/setup_24.x | bash - && apt-get install -y nodejs
# Caddy (авто-HTTPS reverse-proxy)
apt-get install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | tee /etc/apt/sources.list.d/caddy-stable.list
apt-get update && apt-get install -y caddy
# фаервол: SSH, HTTP, HTTPS + временный прямой порт 3001 (тест без домена)
ufw allow OpenSSH && ufw allow 80 && ufw allow 443 && ufw allow 3001 && ufw --force enable
```
Проверить после загрузки: `cloud-init status --wait` (должно быть `done`), `cat /var/log/cloud-init-output.log` при ошибках.

### 3a) Кластер: что видно снаружи (Ф4)

Клиент сначала спрашивает у гейтвея адрес игрового узла (`GET /api/route`), а дальше говорит
с узлом НАПРЯМУЮ. Гейтвей игру не проксирует специально: проксируй он кадры, вся работа,
разложенная по процессам, снова сошлась бы в одном.

**R4-13 (26.09):** раньше веб-клиенты маршрут НЕ спрашивали — сокет шёл на тот же origin, то есть к гейтвею, у
которого игрового сокета нет, и кластер из этого раздела был недоступен игрокам («Сервер недоступен» у всех). Теперь
поток входа (`client/src/net/entryFlow.ts`) спрашивает маршрут перед КАЖДЫМ подключением: вход, переподключение после
потери связи или перезапуска узла, вход к другу по коду (узел — по первой букве кода), ответ узла «wrong-node».
Очередь на вход — местом на плашке «Подключение…» и переспросом раз в 3 с. Сборка с `VITE_WS_URL` прибита к одному
адресу и маршрут не спрашивает. Адрес узла на петле (`ws://127.0.0.1:…` — умолчание одиночного режима без
`DM_NODE_URL`) клиент, открытый НЕ с машины сервера, заменяет тем же путём на своём origin — поэтому одиночный режим
за Caddy (§4) настройки не требует. В кластере адрес узла обязан быть внешним: вариант А или Б ниже.

Значит наружу должны быть видны и гейтвей, и узлы. Два способа:

**А. По путям за обратным прокси (рекомендуется — один порт, один сертификат).**
Узлы отдают адрес вида `wss://ваш-домен/ws/<i>`, прокси разносит их по портам. Узел принимает игровой сокет и на
`/ws`, и на `/ws/<номер>` (R4-13: раньше — только ровно `/ws`, и `/ws/0`, пересланный прокси как есть, получал 404):

```
Environment=DM_NODE_URL_TEMPLATE=wss://ваш-домен/ws/{i}
```

и в Caddy:

```
ваш-домен {
    reverse_proxy /ws/0 127.0.0.1:3002
    reverse_proxy /ws/1 127.0.0.1:3003
    # … по одной строке на узел
    reverse_proxy 127.0.0.1:3001        # всё остальное — гейтвею
}
```

**Б. По портам (проще, но нужен отдельный сертификат или открытые порты).**
Оставить умолчание `ws://<хост>:<порт>/ws`, задать внешний хост `Environment=DM_NODE_HOST=<IP-или-домен>` (без него
узлы объявляют 127.0.0.1, и клиент уйдёт на origin — к гейтвею) и открыть порты узлов в брандмауэре. Страница по
https с `ws://` не соединится (смешанное содержимое) — для https только вариант А. R10-17: со страницы https клиент
сам просит `wss://` у того же хоста и порта (`nodeUrl`; `ws://` браузер не открыл бы вовсе), а сокет, который не
открылся, ведёт в лобби с причиной «Не удалось подключиться к узлу игры» и кнопкой — раньше игрок оставался на плашке
«Подключение…» без кнопок.

**R10-09:** узел (`DM_ROLE=node`) по HTTP отдаёт только `/ws`, `/api/health` и служебное (`/metrics`, `/internal/drain` — с
самой машины); вход, регистрация, ростер, инструменты, конфиг и статика — 404, их отдаёт гейтвей. Раньше узел держал весь
API гейтвея, а лимиты частоты живут в памяти процесса: с открытыми портами узлов перебор пароля одного ника шёл в (N+1) раз
быстрее потолка, и каждая сверка пароля (scrypt) стояла на игровом узле.

Проверить раскладку: `curl -s localhost:3001/api/cluster` — видно все узлы, сколько на каждом
игроков и комнат. R6-20: ручка служебная — как `/metrics`, только с самой машины (или с ключом чтения `DM_METRICS_KEY`,
`Authorization: Bearer <ключ>`); через домен — 403. Ответ — из кэша на секунду. Метрики на гейтвее (`/metrics`) — СУММА по
кластеру, имена те же, что были у одиночного процесса, так что дашборд менять не надо.
⭐ E2E 30.09 (седьмой прогон): до этой даты это было правдой только для показателей ёмкости (`dm_players`, `dm_rooms`, `dm_tick_hz`,
`dm_rss_bytes`, `dm_cpu_*`, очередь) — счётчиков нод (инциденты `dm_save_conflicts_total`, `dm_write_foreign_total`,
`dm_ledger_drain_lost_total`, `dm_farewell_forgotten_total`, ошибки `dm_cmd_failed_total`/`dm_frame_errors_total`, кузница `dm_forge_*_total`,
`dm_slow_clients_dropped_total`…) на гейтвее не было вовсе, и тревоги по ним, настроенные на гейтвей, молчали бы. Теперь нода кладёт снимок
своих счётчиков в реестр с каждым ударом сердца (`cluster_nodes.counters`), а гейтвей отдаёт их сумму под теми же именами. Сумма —
монотонная (рестарт ноды и её уход её не уменьшают); прирост ноды за последние ≤ 2 с перед выходом до неё не доходит — инциденты слива
видны ещё и строкой «ИНЦИДЕНТ» в журнале ноды. Счётчики одной ноды — её `/metrics` на её порту (с самой машины).

### 3b) Обновление без потери прогресса

`systemctl restart dm` шлёт SIGTERM супервизору, тот — узлам. Узел помечается «сливаемым»
(гейтвей перестаёт слать к нему новых), дописывает прогресс всех комнат и выходит.

⚠ **Прогресс перезапуск переживает, НЕЗАВЕРШЁННЫЙ ЗАБЕГ — нет** (проверено живьём, E2E 28.09, `npm run poc:party` сценарий
`drain`). Слив пишет сейвы вместе с забегом, но поднявшийся узел на старте сбрасывает незавершённые забеги всех героев, которых
не держит ДРУГОЙ живой узел (`clearAllRuns`: «рестарт — чистый лист забегов», штрафа нет). Поэтому:
* `systemctl restart dm` поднимает все узлы разом — незавершённые забеги сбрасываются у всех; опыт, золото, сумка и сундук —
  как на момент слива;
* поочерёдный слив (`/internal/drain`, супервизор поднимает узел заново): клиент сам переподключается к живому узлу и
  спрашивает статус забега; кто успел нажать «Продолжить», пока слитый узел поднимается (секунды), продолжает забег там —
  тот же узел забега, тело, стоявшее в бою, — с тем же здоровьем, и подъём слитого узла его уже не трогает. Не успел — «Забег
  не найден» и город, всё добытое при себе. Пати после слива продолжает врозь (каждый — своей комнатой того же забега, свод
  записей общий, R9-01); собраться — входом по коду;
* игроки ДРУГИХ узлов при поочерёдном сливе не замечают ничего.
Поэтому `TimeoutStopSec` должен быть БОЛЬШЕ, чем время записи: слив узла — до конца его аренды (⭐ ENV2, ниже; при живой базе —
миллисекунды), супервизор ждёт узлы аренду + 5 с (117 с), в юните выше — 125.

**R5-08 — второй SIGTERM.** Обработчики сигналов раньше ставились `process.once`: первый сигнал снимал их, и второй (systemd
с `KillMode=control-group` шлёт SIGTERM каждому процессу группы, супервизор — свой, npm и tsx пересылают свой) убивал узел
посреди записи сейвов — без дописанных копий и снятия узла из реестра. Теперь обработчики постоянные (`process.on`, повтор —
строка в лог), супервизор ждёт ВЫХОДА узлов (код или сигнал выхода), а не отправки сигнала (`killed`), и юнит выше —
`KillMode=mixed` и `node --import tsx` без `npx`.

**R5-07 — слив — барьер.** Первым делом слив замораживает комнаты (тика нет, команды, ввод, голосования, рычаги и сундуки
отвечают «перезапускается» и ничего не меняют), потом дописывает сейвы. Раньше комнаты жили дальше: вещь, переданная соседу
по аккаунту после записи слива, но до выхода процесса, оставалась у обоих.

**R5-01 — необработанное исключение** (любая роль) больше не обрывает процесс: строка в лог и тот же слив (запись сейвов,
снятие узла), затем выход. Продолжать работу после такого исключения нельзя — поэтому слив, а не «жить дальше».

Игроки, чей узел ушёл на перезапуск, в свою комнату не вернутся: комнаты живут в памяти процесса, а слив снимает закрепления
узла. Клиент переподключается через гейтвей к живому узлу — дальше см. ⚠ выше: прогресс цел, забег — только если «Продолжить»
нажато до подъёма слитого узла.

**R7-09 — закрепление не уходит от узла, который лишь замолчал.** Героя, которого узел держал на последнем ударе сердца
(сессия, грейс, недописанная копия), другой узел не забирает, пока тот молчит меньше `NODE_DEAD_SEC` = 120 с (раньше — 10 с):
база, лёгшая на 10 с и дольше (рестарт, переключение), больше не отдаёт героя соседнему узлу вместе с правдой, которую
держит недописанная копия (дюп через соседа по аккаунту). Упавший узел, поднятый супервизором с тем же `DM_NODE_ID`, берёт
своих героев сразу; герои узла, снятого насовсем без слива, ждут до двух минут (клиент получает «герой на другом узле» и
входит снова). Уборка реестра (`sweepNodes`) не сносит узел раньше этого срока. R8-06: сброс незавершённых забегов на старте узла
(`clearAllRuns`) щадит героев по тому же правилу (`cluster/claimRule.ts`) — узел, стартовавший, пока база лежала, больше не
снимает забег и версию героям замолчавшего соседа (его сессии получали бы 4009 пачкой, а недописанная копия пропадала). Если копию всё же пришлось забыть (база лежала
дольше срока) — это инцидент: счётчик `dm_farewell_forgotten_total` и строка «ИНЦИДЕНТ» в логе узла; дюп найдёт и ночной аудит.

**R12-04 — база моргнула посреди слива.** Дописка сейвов идёт кругами (пауза 250–500 мс), пока не ляжет всё — копии ушедших,
последнее состояние присутствующих, копии снятых с неизвестным исходом фиксации, — но не дольше 7,5 с из восьми. Раньше слив
делал одну попытку и выходил за миллисекунды: закрепление героя не читалось — копия даже не пробовалась. Что так и не легло к
концу бюджета, — строка «ИНЦИДЕНТ» на героя в логе и `dm_farewell_forgotten_total`.
⭐ R13-06: круг ждётся не дольше секунды, а запись слива — своя у каждого героя: зависшая (блокировка строки, полуоткрытое
соединение до `query_timeout`) не держит круг до конца бюджета, и герой, чья запись упала сразу, дописывается следующим кругом
(раньше он становился ИНЦИДЕНТОМ); вторую запись за зависшей не ставят.
⭐ R14-07: круги ждут и свод записей забега комнат (`run_ledger`: открытые сундуки, убитые монстры, рычаги) — его запись, упавшая на
сливе (блокировка строки другим узлом, обрыв), раньше ждала повтора по таймеру уходящего процесса, и продолжение забега на другом
узле собирало эти узлы свежими. Не легло к концу бюджета — «ИНЦИДЕНТ» на комнату в логе и `dm_ledger_drain_lost_total`.
⭐ R20-01: и пачку свода, которая ещё в базе у УШЕДШЕЙ комнаты (финал или вайп отправил свод, пати вышла из города, комната снята, а база
медленная — часто это тот же деплой): раньше такая комната выпадала из учёта, слив выходил за миллисекунды, пачка падала после — без записи и
без ИНЦИДЕНТА. Теперь комната в учёте, пока её пачка в пути: слив её ждёт, упавшую пишет снова, не легшую — «ИНЦИДЕНТ».

Слив у узла ОДИН (R3-12): объявить «сливаюсь» в реестре сразу, не дожидаясь очередного удара сердца; новые входы
и «Завершить» отвечать «перезапускаемся»; дописать сейвы; снять узел и его закрепления из реестра; выйти. Всё — под
предохранителем; ⭐ ENV2: дописка идёт до конца аренды узла (ниже), поэтому `TimeoutStopSec` меньше 125 не ставить.

**⭐ ENV1 — аренда узла: замолчавший узел отгораживает себя сам.** Реестр отдаёт героев и забеги узла, молчащего дольше
`NODE_DEAD_SEC` = 120 с, другому (R7-09 — так задумано: упавший узел не запирает своих героев). Раньше сам замолчавший узел
(раздел с базой, заморозка машины, цикл событий, стоявший минуты) об этом не знал и играл дальше: герой, вошедший на соседнем
узле, жил на двух, забег шёл в двух комнатах. Теперь узел кластера (роль `node`) держит аренду (`cluster/lease.ts`): удар
сердца, дошедший до реестра, продлевает её на `NODE_DEAD_SEC − 8` = 112 с от своей отправки; за 8 с до конца — строка «аренда ноды
кончается…» в логе (⭐ R16 C-05: не слив — удар, дошедший до конца аренды, её продлевает, и узел играет дальше: простой базы короче
аренды не стоит ни сессий, ни забегов), а после конца аренды — ни тика, ни команды, ни записи строки героя, выход без записи
(«ИНЦИДЕНТ: аренда ноды кончилась»; супервизор поднимет его заново). Забег комнаты, который реестр числит за
другим узлом, комната отпускает (её героев снимают без записи, 4009), а не только пишет «ИНЦИДЕНТ». Одиночный сервер (роль
`single`) аренды не держит: отдать его героев некому.
**⭐ ENV2 — слив, пока база лежит.** Дописка слива (`flushAll` кругами) раньше сдавалась через 7,5 с — база, вернувшаяся на
девятой секунде, копий уже не получала (ИНЦИДЕНТ R12-04). Теперь круги идут до конца аренды узла (писать можно, пока его героев
никто не заберёт), при живой базе слив по-прежнему — миллисекунды. ИНЦИДЕНТ слива теперь значит «база лежала дольше аренды».
**⭐ R16 C-02 — правка конфига на всех узлах.** «Применить на сервере» редактора принимает гейтвей; узлы видят правку сверкой ревизии
оверрайдов в базе (раз в 3 с, `configSync.ts`) и пересобирают конфиг сами — перезапуск узлов после правки не нужен. Правка оверрайдов
мимо сервера (`db:repair`, SQL) доходит так же. Остаётся окно поочерёдного деплоя: пока гейтвей и узлы на разных сборках (файлы данных
другие), команды кузницы и лавки на старых узлах отвечают «Цена изменилась» — деплой узлов не затягивать.
**⭐ R17-03 — оверрайд баланса без цен форм.** Схема теперь требует в `balance.craft.formMult` строку у каждой формы, которую даёт
ёмкость: оверрайд баланса в базе, сохранённый до §21.1 (без раздела `craft`) или без строки формы, при старте и пересборке
ПРОПУСКАЕТСЯ целиком со строкой «ИНЦИДЕНТ: пропущен невалидный оверрайд конфига "balance"» в логе (с R20-08 — `console.error` и метрика
`dm_config_override_skipped_total`) — игра живёт на файле `balance.json` (раньше такой оверрайд молча ставил формы на ×1). После деплоя
проверить лог старта; увидели строку — открыть баланс в редакторе и сохранить нужные правки заново (или снять оверрайд).
**⚠ R20-05 — кривая опыта строго растёт.** Схема требует `balance.xpTable` = 0, 0, дальше строго по возрастанию, числа конечные ≥ 0.
Оверрайд баланса в базе с кривой, которая этого не держит (ступенька, повтор, минус), при старте ПРОПУСКАЕТСЯ целиком тем же
инцидентом — угадывать задуманный порог нельзя. Увидели — поправить кривую и сохранить баланс из редактора заново.
**⚠ R20-08 — оверрайд классов старше R18-07.** Старт класса в оверрайде `classes`, сохранённом до R18-07 дробью или минусом, при сборке
конфига ПРИВОДИТСЯ (вниз до целого, не ниже нуля) — прочие правки классов живут; в логе строка «оверрайд конфига "classes" сохранён под
прежней схемой — приведён при загрузке» с перечнем. Записать приведённое в базу (строка пропадёт): `npm run db:repair -- --fix`.
**⭐ R21-01/03 — конфиг собирается одним кандидатом.** Файлы данных и все оверрайды базы собираются вместе (`server/configCandidate.ts`),
и правило поверх таблиц (D4, время баффа) проверяется над итогом: от порядка строк `config_overrides` (куча Postgres) сборка больше не
зависит — годный вместе набор хозяина не выбрасывается и не «приводится». Сборка из-за этого правила не бросает никогда: новые файлы данных
деплоя, вместе с оверрайдами прод-базы нарушающие правило, при старте приводятся зажимом с ИНЦИДЕНТОМ «файл данных «…» … приведён при
сборке» (игра живёт на приведённом) — после деплоя проверить лог старта; увидели — поправить файл или связанный оверрайд в редакторе.
`npm run db:repair` проверяет оверрайды тем же кандидатом (вместе, а не каждый поверх файлов).
**⭐ R15-03 — вещи удалённых героев.** Удаление героя теперь уводит его вещи из леджера в `world` (событие `gone`, причина
`charDeleted`) той же транзакцией. Герои, удалённые ДО этой сборки, оставили вещи у «char:<удалённого>» — ночной аудит числит их
потерянными (инциденты). Один раз после деплоя: `npm run items:orphans` (показ) → `npm run items:orphans -- --fix` (увести в `world`);
повтор ничего не делает.
**⭐ R15-06 — шаг часов машины.** Аренда узла и сроки комнат идут по монотонным часам процесса: шаг настенных часов (chrony makestep,
миграция ВМ) больше не выводит все узлы разом «без записи». Если настенные часы говорят «аренда кончилась», а часы процесса — нет,
узел на миг отгораживается и сверяется с реестром ударом сердца: дошёл — играет дальше, нет — выход без записи (строка в лог).
**⭐ R16-02 — пауза машины узла.** ВМ на паузе или сон хоста дольше `NODE_DEAD_SEC` (120 с): часы процесса стоят, и по ним аренда
«ещё идёт», а реестр за это время уже отдал героев и забеги узла другому. Каждый удар сердца узла сперва спрашивает реестр, давно ли тот
его видел (по часам базы), — дольше аренды или строку узла уже сняла уборка: `ИНЦИДЕНТ: реестр не видел удара ноды … — выход без записи`,
супервизор поднимает узел заново. Делать ничего не нужно; частые такие строки — повод разобраться с паузами ВМ (снапшоты, балунинг памяти).
Часы машины базы — те, по которым реестр решает, жив ли узел: шаг их вперёд дольше аренды (112 с) уведёт узлы так же — держать chrony и на ней.
Граница (перепрогон фаззеров после R16): если и ПОСЛЕ паузы узел до реестра не достаёт (сеть к базе ещё лежит), спросить ему не у кого — до
конца аренды (не дольше 112 с по часам процесса) он держит героев и забеги, которые реестр уже отдал, и выходит без записи по её концу. Узел с
chrony (настенные часы после паузы догоняются) в этом окне отгорожен сомнением R15-06: ни тика, ни команды, ни записи; без chrony — нет. Поэтому
chrony на узлах обязателен так же, как на базе.
**⭐ R17-01 — пауза сразу после ответа сверки.** Сверка R16-02 — отдельный запрос: если машина узла встала уже после того, как база ответила
«видел 2 с назад», узел действует по устаревшему ответу. Поэтому и сам удар сердца узла с арендой ложится только при той же проверке (одним
`UPDATE` строки узла, без вставки); не лёг — `ИНЦИДЕНТ: удар сердца не лёг — реестр не видел ноду дольше аренды … выход без записи`, супервизор
поднимает узел. Первый удар нового процесса по-прежнему вставляет строку. Перед таким выходом в логе бывает строка `ИНЦИДЕНТ: забеги комнат …
кластер числит за другой нодой` — это тот же случай (реестр уже счёл узел мёртвым), а не второй сбой.
**⭐ R18-03 — окно «оттаял, до первого удара».** Если на паузе стояли ВСЕ часы машины (сомнения R15-06 нет), узел до своего удара по
расписанию (до 2 с) исполняет кадры, пришедшие в его сокеты за паузу, таймеры и шаги комнат. Поэтому каждая запись строки героя (сессия,
дописка копии, копия ждущего реконнекта, штраф и снятие забега по строке базы) ложится только с проверкой владения ТЕМ ЖЕ запросом:
закрепление героя за этим узлом, а у узла с арендой — и его удар в реестре моложе аренды. Отказ — `ИНЦИДЕНТ: героя … держит другая нода — …
не записана, копия здесь забыта` и счётчик `dm_write_foreign_total`; живая сессия снимается устаревшей (4009), игрок входит заново — к узлу,
который его держит. Делать ничего не нужно, частые — тот же повод, что у R16-02 (паузы ВМ). Тем же отказом узел, который после паузы до реестра
не достаёт, отпускает героев на первой же записи (автосейв — не реже 10 с), а не держит их до конца аренды.
**⭐ R17-06 — лог и шаг часов назад.** Строки «не чаще раза в 10 с» (сбои записи сейва и свода забега, кадры с исключением, HTTP 500, отказы
маршрутизации гейтвея, шум команд; сверка конфига — раз в минуту) меряют срок часами процесса: шаг настенных часов НАЗАД (chrony makestep,
откат снимка ВМ) их больше не глушит на свою длину — лог инцидента с часами читается целиком.
**⭐ R16-03 — откат и удалённые герои.** `items:rollback` вещи, лежавшие на отсечке у героя, которого с тех пор удалили, не трогает
(возвращать некуда; они остаются там, где лежат) и перечисляет их в показе — сверить руками.

### 3c) Прокси, адрес игрока и служебные ручки (R3-03, R3-07)

- **Прокси перед сервером обязан ставить `X-Forwarded-For`.** Caddy делает это сам; nginx —
  `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`. По этому заголовку считаются лимиты входа и
  регистрации и суточный потолок аккаунтов с адреса, а сервер ему верит, только если его прислал доверенный
  собеседник, и читает СПРАВА (левее может быть то, что написал сам игрок). Доверенные: петля (прокси на этой же
  машине) и адреса из `DM_TRUST_PROXY` (через запятую — прокси или балансировщик на другой машине).
  Без заголовка все игроки за прокси делят один лимит входа.
- **`/metrics` и `POST /internal/drain` отвечают только прямому вызову с самой машины**: с петли и без заголовков
  прокси (`curl -s localhost:3001/metrics` на сервере — да; то же через домен — 403). Слив узла — только с машины сервера.
  R5-24: `/metrics` — ещё и по ключу ЧТЕНИЯ `DM_METRICS_KEY` (`Authorization: Bearer <ключ>`, не короче 16 знаков): Prometheus
  на другой машине и стенд `dmload --metricsKey=…` с ноутбука. Без ключа стенд раньше читал отказ как «тик 0 Гц» и выключал
  проверку частоты симуляции; теперь он останавливается с объяснением. R4-27: слив по ручке — это обработчики SIGTERM процесса (запись сейвов, снятие узла), а
  не сигнал: на Windows `process.kill(self)` убивал процесс без них.
  ⭐ R12-01: свой прокси uWS (игровой порт → express на петле) не пересылает заголовки длины и соединения клиента (`Content-Length`,
  `Transfer-Encoding`, `Connection`…): длину ставит свою — ровно пересланное тело, GET/HEAD/OPTIONS с заявленным телом — 400; а
  соединение с express — одно на запрос. Раньше GET с `Content-Length` оставлял express ждать тела — им становилась голова
  следующего запроса чужого клиента на общем соединении, а его тело (`POST /internal/drain` без заголовков) express видел
  прямым вызовом с самой машины. Вторая линия: на соединении, которое открыл прокси, «с самой машины» — только с его
  доказательством (заголовок `x-dm-local` с секретом процесса; одноимённый заголовок клиента прокси снимает). Прямой вызов на
  петлю express (`DM_HTTP_PORT`) — как раньше.
  ⭐ R14-11: и не браузерная страница с этой же машины. Любая открытая в браузере страница (dev у владельца, прод, где кто-то сидит в
  браузере) ходит на `localhost` с петли и без заголовков прокси: `fetch(…/internal/drain, {method:'POST', mode:'no-cors'})` гасил
  узел, а с подменой DNS страница читала `/metrics` и `/api/cluster`. Теперь «с самой машины» — без `Origin`, с `Sec-Fetch-Site`
  только `none` (адресная строка) или без него, и `Host` — петля (`localhost`, 127/8, `[::1]`) или не прислан. curl, Prometheus,
  `dmload` и `fetch` из Node так и ходят; ⚠ `curl http://<имя-машины>:3001/metrics` (имя, которое `/etc/hosts` ведёт на 127.0.1.1) —
  теперь 403: звать по `localhost`/`127.0.0.1`.
- **Адрес игрока на игровом сокете (R4-29)** читается тем же правилом, что у HTTP: `X-Forwarded-For` от доверенного
  прокси, справа. На uWS — в `upgrade`: за Caddy раньше у всех игроков в `play_sessions.ip` стоял 127.0.0.1.
- **Тело запроса (R4-11, R6-04):** общего разбора тела нет: ручки аккаунтов разбирают своё (до 8 КБ), инструменты
  `/api/dev/*` — только после проверки прав (до 2 МБ, загрузка моделей `/api/dev/assets/` — до 64 МБ, и всё это только вне
  продакшена). Прокси uWS принимает не больше 16 КБ (вне продакшена на `/api/dev/*` — 2 МБ и 64 МБ на модели); больше —
  413 от самого прокси, тело не копится. Кривой JSON — 400 без стека в логе (R6-21). Caddy сверх этого можно ограничить
  `request_body { max_size 70MB }` (в продакшене хватит `max_size 64KB`).
- **Маршрут `GET /api/route` (R4-21)** проверяет токен, id героя, билет очереди и код комнаты до базы (кривое — 4xx, а
  не 500 со стеком) и держит потолок на аккаунт (`limits.route`). R5-13: очередь на вход (`DM_MAX_PLAYERS`) — и для входа
  по коду, код — только полный (буква узла — не пропуск); узел держит свою долю потолка сам (`DM_NODE_MAX_PLAYERS`).
  R6-08: очередь — по месту (билет живёт, пока клиент опрашивает, и только у своего аккаунта; новичок встаёт в хвост, а не
  обгоняет ждущих); герой с живым закреплением (разрыв посреди забега, вторая вкладка) идёт к своему узлу мимо очереди, вход
  по коду — в пределах запаса узла над потолком (max(4, ¼ потолка)). ⭐ E2E 27.09: к показателям узлов гейтвей прибавляет
  выданные, но ещё не отражённые направления на КАЖДОМ пути (новичок, код комнаты, возврат к своему узлу), засчитывает их
  в том же шаге, где считает сумму (одновременные маршруты — после перезапуска их тысяча — больше не проходят потолок
  разом), и снимает вторым сердцебиением узла после выдачи, а не таймером: живой прогон — 45 одновременных при потолке 30,
  впущено ровно 30, по 15 на узел. Недобор на входе на секунды возможен (вошедший, уже видный в сердцебиении, до второго
  считается дважды) — это безопасная сторона, очередь пропустит на следующем опросе.
- **Прокси uWS (R5-01)** не пересылает то, на чём `http.request` бросает (управляющий байт в заголовке, не-ASCII в пути,
  метод не-токен), — 400 от самого прокси. Раньше такой анонимный запрос ронял процесс узла со всеми комнатами.
  R7-10: ответ express прокси отдаёт ПОТОКОМ с обратным давлением (клиент не читает — прокси не читает у express), а не
  копит целиком: раньше аноним, запросивший GLB из `/assets` и не читающий ответ, держал на узле весь файл. Статику всё равно
  лучше отдавать с CDN или Caddy (`/assets` раздаёт и игровой процесс, при любом `DM_SERVE_STATIC`).
  ⭐ R10-03: на `/assets` живут ДВЕ папки — модели и текстуры сервера (`packages/server/assets`) и бандл клиента
  (`packages/client/dist/assets`: `game3d-<хэш>.js`, `poseEditor-<хэш>.js`, ленивые куски; имена меняются с каждой сборкой,
  кэш вечный). Раньше 404 раздачи моделей глотал бандл, и собранный стенд (`game3d.html`) и поз-редактор были белым экраном.
  CDN или Caddy, отдающий `/assets` сам, обязан смотреть в обе папки (сперва модели), иначе — проксировать `/assets` процессу.
  R10-16: повтор после «порт занят» (dev-рестарт) слушает тот же адрес: express в режиме uWS остаётся на петле, а не встаёт
  на все интерфейсы мимо прокси.
- **Строка запроса (R7-05):** значения — только строкой: `?charId[toString]=1` (разборщик express делает из него объект)
  на `/api/route` — 400, а не 500 со стеком в логе.
- **Вход (R7-13):** бакет сети адреса у `/api/login` платит только неверный пароль (его сверка — scrypt); ника нет — «неверно»

### 4) Домен + HTTPS (Caddy) — `/etc/caddy/Caddyfile`
Направь A-запись домена (или суб-домена) на IP сервера, затем:
```
game.твойдомен.ру {
    reverse_proxy localhost:3001
}
```
Это — одиночный режим (без `DM_ROLE`). Для кластера (§3a, вариант А) перед этой строкой — строки `reverse_proxy /ws/<i>`
на каждую ноду.
```bash
systemctl reload caddy   # Caddy сам возьмёт Let's Encrypt-серт и проксирует WebSocket
```
Открой в браузере `https://game.твойдомен.ру` — с любого компа.

**Быстро без домена (первый тест):** открой порт 3001 в фаерволе TimeWeb и играй по
`http://<IP-сервера>:3001` (WebSocket на http-странице работает; HTTPS нет).

## Обновление версии
```bash
cd /opt/dm && git pull && npm ci && npm run build && systemctl restart dm
```
Открытые вкладки игроков переживают обновление без перезагрузки (переподключаются сами), а сборка очищает `dist` и
меняет хэши ленивых кусков клиента (окно ковки, модель оружия из деталей). R10-12: вкладка, которой кусок не
загрузился, говорит игроку «Сервер обновился — перезагрузите страницу (F5)» (окно ковки — с кнопкой перезагрузки).
⭐ R18-08: и вкладка, чей КОД цен старше сервера (обновление сменило формулу, а тело конфига то же — ETag и ревизия прежние): у сборки
есть штамп — хэш исходников `packages/shared/src` (`buildStampOf`), `npm run build` вписывает его в бандл, а сервер считает его на
старте по тем же файлам, с которых работает, и шлёт в кадре `joined`. Не сошлись — «перезагрузите» на входе и на каждый отказ «Цена
изменилась», который перечитывание конфига не лечит. Поэтому сборка клиента и перезапуск сервера — из ОДНОГО состояния исходников
(команда выше): собранный клиент при неперезапущенном сервере (или наоборот) — это и есть «разные сборки», и вкладки о них скажут.
⚠ R19-06: концы строк штамп не видит (текст — к LF без BOM): `client/dist`, собранный на Windows (`core.autocrlf=true` — CRLF), против
сервера из `git pull` на Linux (LF) того же коммита — один штамп. До правки это были «разные сборки» навсегда — «перезагрузите» на каждом
входе, и перезагрузка не помогала.
⭐ D3: сверка версий — одно рукопожатие на каждом входе (`joined`: протокол, штамп, ревизия конфига), и «перезагрузите» — одна строка на вход.
И штамп теперь не только подсказка: команды кузницы, лавки и разбора несут штамп вкладки, и сервер другой сборки их НЕ исполняет (отказ «Цена
изменилась: сервер обновился»), чтобы старый код не провёл сделку не по той цене, что показал. Поэтому «разные сборки» по ошибке выкладки
(клиент собран из исходников shared, которых нет у сервера, — хоть бы и правка комментария — или сервер не перезапущен после сборки) —
это закрытые кузница и лавка у ВСЕХ вкладок, пока сборку не выровняют: собирать и перезапускать строго командой выше, из одной выгрузки.
Проверить после выкладки: вкладка, открытая заново, на входе не пишет «Сервер обновился — перезагрузите страницу».

## Важное
- **Бэкап БД:** `pg_dump dungeon | gzip > /var/backups/dm-$(date +%F).sql.gz` по cron. Бэкап диска
  TimeWeb этого НЕ заменяет: копия файлов работающей базы может оказаться нецелостной.
- **Postgres обязателен.** Сервер не поднимется без `DM_PG` в проде (осознанно: молчаливый уход на
  localhost хуже падения при старте). Схема создаётся сама при первом запуске.
- **Перенос авторского контента** со старой SQLite (позы редактора и оверрайды конфига) — разово:
  `npm run db:import -- --from=packages/server/data/dm.db`. Аккаунты и персонажи НЕ переносятся.
- **Баланс в проде фиксирован:** `NODE_ENV=production` отключает live-правку конфига из редактора
  (анти-чит). Меняй баланс локально → Экспорт JSON в `data/*.json` → коммит → обновление (см. выше).
- **Ковка открыта (`balance.craft.live` = `true`, 26.09, R4-03).** Оверрайд баланса в базе (`config_overrides`, ключ
  `balance`) перекрывает файл ЦЕЛИКОМ: сохранённый с `craft.live: false` оставит кузницу закрытой («Кузнец ещё не
  куёт»). После выкладки проверь: `SELECT json->'craft'->'live' FROM config_overrides WHERE key = 'balance';` — пусто
  или `true`. Оверрайд без ключа `live` кузницу не закроет: умолчание схемы тоже `true`.
- **Забеги после обновления (R4-01):** продолжение узла теперь помнит взятое (`save.run.node`). Забег, припаркованный
  до обновления, записи не несёт, но рестарт узла и так снимает незавершённые забеги (`clearAllRuns`) — особых шагов
  не нужно.
- **Свод записей забегов (R9-01):** таблица `run_ledger` (часть схемы `runs`, применяется сама на старте): что взято на
  узлах забега, по его личности (`RunConfig.id`). Пишут комнаты, читает вход с забегом; старт узла чистит строки, которых не
  трогали неделю (`sweepRunLedger`). Растёт на строку на узел забега — с сотен тысяч в сутки при полном онлайне; бэкапу и
  переносу не нужна (забеги рестарт не переживают).
- **Доступ к инструментальным роутам — ПО РОЛИ, а не по адресу.** Раньше `/api/dev/*` гейтились
  «запрос с локальной машины». Это не пропуск, а его видимость: браузер разработчика тоже ходит
  с 127.0.0.1, то есть под гейт подпадала любая открытая в нём страница. Теперь пускает роль
  `users.role='admin'` (выдаёт `npm run grant-admin -- <ник>`, снимает `revoke-admin`, список — `npm run admins`)
  либо `DM_ADMIN_KEY` — длинный случайный секрет для ПРОЦЕССОВ (скрипты, шим генерации анимаций).
  Отзыв: роль читается на КАЖДОМ запросе, поэтому `revoke-admin` действует сразу; ключ гасится сменой
  переменной. В проде эти роуты всё равно выключены `NODE_ENV=production` — два независимых условия остались.
- **`DM_ORIGINS` — белый список источников CORS** (через запятую; умолчание — два дев-сервера
  `http://localhost:5173,http://localhost:5174`). Раньше стоял `cors()` без параметров — API отвечал любому
  источнику. СОБСТВЕННЫЙ хост разрешён всегда, поэтому раздача клиента с того же адреса
  (`DM_SERVE_STATIC`) не требует настройки; пустая переменная трактуется как незаданная (описка не должна
  молча отрезать редакторы). Запросы без `Origin` (curl, сервер-сервер) не отсекаются: CORS защищает
  браузер от чужой страницы, а сервер защищает авторизация.
- **`GET /api/pose` и `/api/config` ОСТАЮТСЯ публичными** — это контент, который клиент тянет
  ДО входа (`render3d/game3d-boot.ts` зовёт их до экрана авторизации). Закрыть их токеном значит
  сломать запуск игры; закрыта ЗАПИСЬ (`POST/DELETE /api/dev/pose`), а она и есть опасная часть.
- **Релизы контента (Д1, 08.10).** Гейтвей (или одиночный процесс) сам режет релиз из того, что у него сейчас: конфиг одним
  файлом, анимации — по файлу на клип, прочие ключи поз — по файлу на ключ (`server/src/content/`). Повод — старт и любая правка
  конфига или поз (пауза тишины 1.5 с). Таблицы `content_releases` и `content_channels` (часть схемы `content`, применяется сама),
  файлы — в `DM_CONTENT_DIR` (умолчание `packages/server/content`, вне git): **эту папку храни между выкладками** (как базу) —
  потеряешь, сервер нарежет заново, но у клиентов с кэшем «не найден файл» до следующей правки. Раздача: `GET /api/content/pointer`
  (указатель, `no-cache`) и `GET /c/b/<2>/<sha256>` (`immutable`, gzip). Unity берёт конфиг и позы оттуда с кэшем на диске;
  старые клиенты и веб — по-старому (`/api/config`, `/api/pose` не тронуты). Уборка старых файлов и каналы `beta`/`live` — фаза Д3.
  **Арт (Д2):** публикатор Unity (DM ▸ Art ▸ Publish Content) кладёт бандлы и каталог Addressables в ту же папку по sha256 и пишет
  описание `art-abi<N>.json`; нарезчик берёт его в манифест, только если все его файлы на месте. Клиент докачивает лишь бандлы,
  которых нет в его сборке (база — в депоте Steam). Пока публикация — с машины разработки в папку этого сервера; на прод — через
  CDN, фаза Д3.
- **Масштабирование (Ф4):** комнаты живут в памяти узла и за ним закреплены на всё время жизни.
  Горизонтально масштабируется процессами на одной машине (`DM_ROLE=supervisor`); на несколько
  машин — тем же реестром в общей базе, узлам достаточно видеть один Postgres.
- **Канал важнее процессора.** При 10–12 КБ/с на игрока гигабитный канал упирается примерно
  на 7 000 игроков — раньше, чем процессор на большинстве серверов. Раздачу клиента (бандл
  и модели) держите на CDN, иначе холодные заходы съедят тот же канал.
