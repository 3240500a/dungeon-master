# Ресерч: нейросети для генерации анимаций → наш поз-редактор

Цель — понять, можно ли прикрутить open-source нейросеть, генерирующую анимации (по тексту / по ключам), к нашему `pose-editor.html`, какие есть решения и как это стыкуется с нашим форматом.

---

## 0. Что у нас уже есть (и почему это удобно)

- **Клип** = `{ name, character, weapon, loop, keys: Keyframe[] }`; **Keyframe** = `{ pose, t }`, где `pose` — `Record<боньё → [x,y,z]>` (локальные Euler-повороты кости), `t` — секунды. Хранятся JSON-ом в `localStorage['pe_clips']`.
- **Кости — Unity-Humanoid-нейминг** (`Spine/Chest/UpperChest/Neck/Head/LeftShoulder/…/LeftUpperLeg/LowerLeg/Foot`). Это ТА ЖЕ конвенция, что у Mixamo / VRM / большинства ретаргет-пайплайнов — совпадение критично.
- **Редактор уже умеет:** грузить **FBX/GLB со скелетом** (`modelAssets.ts` — FBXLoader + GLTFLoader) и **ретаргетить произвольный скелет** на наши кости (`retarget3d.ts`: `autoBoneMap` нормализует чужие имена `CC_Base_Hip→Hips`, `makeRetargetRig` ведёт все кости → `OUR_BONES`). Пока это используется для СКИНОВ (внешность), не для клипов.

**Вывод:** нам не нужно «понимать нейросеть». Нужен **мост через стандартный анимационный файл** (BVH/FBX/GLB): нейросеть отдаёт анимацию в таком файле → редактор его грузит (loader уже есть) → ретаргетит на наши кости (ретаргет уже есть) → **семплит в наши keyframes** (это единственный новый кусок). Дальше правишь руками, как обычный клип.

## 1. Какие есть open-source решения

### A. Текст → движение (text-to-motion) — «напиши „замах мечом“ → анимация»
| Проект | Год | Чем интересен | Лицензия кода |
|---|---|---|---|
| **MDM** (Motion Diffusion Model) | 2022 | Эталон, диффузия text/action→motion; **умеет in-betweening и редактирование** (inpainting между ключами); тонна форков/доков | MIT |
| **MoMask** | 2024 | Masked-генерация (residual VQ), качество выше MDM | MIT |
| **MotionGPT** | 2023 | «Движение как язык» — text↔motion, гибкий | MIT/Apache |
| **T2M-GPT** | 2023 | VQ-VAE + GPT, простой и быстрый | — |
| **OmniControl / PriorMDM** | 2023–24 | Контроль ключами/траекторией/суставами поверх MDM | MIT |
| **MotionLCM** | 2024 | Latent-consistency, генерация ~в реальном времени (важно для in-browser) | MIT |

Выход почти у всех — **SMPL-скелет / HumanML3D (22 сустава)**, конвертируется в **BVH/FBX**.

### B. In-betweening (по ключам достроить движение) — ЛУЧШЕ ВСЕГО ложится на кадровый редактор
- **MDM / PriorMDM** — режим in-betweening/edit (диффузия «дорисовывает» между заданными ключами).
- **RSMT**, transformer-in-betweening репы — real-time достройка переходов.
- Сценарий у нас: ставишь 2–3 ключа в редакторе → сеть заполняет промежуток → импорт плотного клипа → доводка.

### C. Видео → движение (mocap, альтернативный ИСТОЧНИК клипов)
- **WHAM / GVHMR / TRAM / 4D-Humans** — восстанавливают SMPL-движение из обычного видео. Не «генерация», но кормит ТОТ ЖЕ мост (SMPL→BVH/FBX). Полезно: «снял видео замаха → клип».

### D. Физика/RL (DeepMimic, AMP) — для физ-контроллеров, НЕ для авторинга клипов. Нам мимо (у нас клипы + рэгдолл ведётся к позе, а не обучается).

## 2. Мост-формат и стыковка

Все пути сходятся к одному: **нейросеть → анимационный файл (BVH или FBX/GLB) → наш ретаргет → наши keyframes.**

- **BVH** — лингва-франка мокапа (иерархия костей + Euler-повороты по кадрам). Многие тулзы экспортят BVH напрямую; SMPL→BVH — стандартный скрипт.
- **FBX/GLB** — SMPL→FBX через Blender-addon (SMPL/AMASS дают FBX); наш редактор их уже парсит.
- **Ретаргет** — `autoBoneMap` уже нормализует Mixamo/SMPL-подобные имена в наши; `makeRetargetRig` ведёт кости. Разница рест-поз (T-pose vs наша) снимается ретаргетом.

**Единственный новый кусок:** «запекатель клипа» — из загруженного АНИМИРОВАННОГО файла (Three.js `AnimationClip` → треки поворотов костей по времени) прочитать локальные повороты ретаргет-костей по кадрам и собрать наш `Clip{keys:[{pose,t}]}`. Сейчас `poseModelsTab` берёт из файла только скелет/меши (скин), анимационные треки не читает — это и надо добавить.

## 3. Как прикрутить: три пути

| Путь | Что это | Плюсы | Минусы |
|---|---|---|---|
| **A. Оффлайн → импорт** (рекоменд. MVP) | Гоняешь модель отдельно (Python/Colab) → BVH/FBX → «Импорт AI-клипа» в редакторе | Ноль ML в игре, любые SOTA-модели, быстрый прототип | Не интерактивно (сгенерил→сконвертил→импортнул) |
| **B. Локальный Python-сервис** | Мелкий FastAPI рядом; кнопка в редакторе «🧠 Сгенерировать» → промпт → сервис вернёт клип-JSON | Интерактивно (текст→клип прямо в редакторе), потом доводка ключей | Нужен запущенный Python + (желательно) GPU; это ДЕВ-инструмент, не в игре |
| **C. В браузере** (ONNX/WebGPU) | Конверт модели в ONNX → `onnxruntime-web`; текст-энкодер через `transformers.js` | Полностью клиент, без сервиса | Диффузия тяжёлая/медленная; большой вес модели; много работы. Реалистично только с лёгкими (MotionLCM/квантованный VQ) |

**Рекомендация:** начать с **A** (проверить, что ретаргет-мост даёт вменяемое движение на нашем риге), затем **B** для интерактива. Поз-редактор — ДЕВ-инструмент (не шипится в игру), так что локальный Python-хелпер приемлем. Игра при этом не тащит никакого ML — она проигрывает уже запечённые клипы.

## 4. MVP-план (минимум, чтобы увидеть результат)

1. **Выбрать модель:** старт — **MDM** (зрелая, MIT, есть in-betweening) или **MoMask** (качество). 
2. **Запекатель клипа (новый кусок, ~1 файл в редакторе):** загрузить анимированный BVH/FBX → `AnimationClip` → на каждый семпл-кадр прочитать локальные повороты ретаргет-костей (`OUR_BONES`) → собрать наш `Clip` → сохранить в `pe_clips`. Переиспользует `modelAssets`+`retarget3d`.
3. **Кнопка «Импорт AI-клипа (BVH/FBX)»** в поз-редакторе рядом с вкладкой «Модели».
4. Прогнать 2–3 клипа (ходьба/замах/уклон) через MDM оффлайн → BVH → импорт → посмотреть на нашем риге, поправить ретаргет-огрехи.
5. (Фаза 2) Локальный FastAPI: `POST /gen {prompt}` → возвращает готовый `Clip`-JSON; кнопка «🧠 Сгенерировать по тексту» → появляется клип для правки.
6. (Опц.) In-betweening: слать 2–3 наших ключа в сервис (MDM edit-mode) → получать плотный клип.

## 5. Подводные камни (важно решить заранее)

- **⚠️ Лицензии данных.** Большинство text-to-motion обучены на **HumanML3D = AMASS**, а AMASS/SMPL — **академическая (non-commercial)** лицензия. Код моделей MIT, но ВЕСА, обученные на AMASS, и сам SMPL-меш имеют ограничения на коммерческое использование. Для игры (коммерция) это риск: генерируемое движение может быть «производным» от датасета. Варианты: (1) использовать AI-клип как ЧЕРНОВИК, который дорабатывается руками (трансформация); (2) искать модели/датасеты с разрешительной лицензией; (3) юр-проверка перед шипом. **Флажок обязателен.**
- **Рест-поза и система координат.** SMPL/Mixamo — своя T-поза и оси; наш риг — свой. Ретаргет это снимает, но повороты надо приводить в НАШИ локальные фреймы (наш формат — Euler-XYZ на кость). Наш `retarget3d` уже ведёт кости, так что запекать надо ИМЕННО локальные повороты ретаргет-скелета, не сырые SMPL-параметры.
- **Кадры vs ключи.** Сеть даёт плотный поток (30/60 fps). В наш клип лучше семплить с прореживанием (или все кадры как ключи) — иначе редактировать неудобно. Можно добавить «упрощение» (выкинуть почти-линейные ключи).
- **Пальцы/лицо** сети обычно не дают (SMPL — тело). У нас их и нет — ок.
- **Физика.** У нас меш ведёт рэгдолл к позе-цели. AI-клип задаёт цель — рэгдолл сам сгладит/подчинит физике (наш существующий `DriveToPoseUsingMotors`). Т.е. AI-клип не обязан быть физически идеальным.

## 6. Итог

Технически прикрутить **реально и недорого**, потому что 90% моста уже есть (loader FBX/GLB + ретаргет на наши кости + JSON-клипы). Не хватает одного: **запекателя «анимационный файл → наш Clip»**. 

- Самый дешёвый первый шаг — путь **A** (оффлайн MDM/MoMask → BVH → импорт), чтобы проверить качество ретаргета на нашем риге.
- Дальше — путь **B** (локальный сервис, текст→клип в редакторе) для интерактивного авторинга.
- Главный НЕ-технический риск — **лицензия данных (AMASS/SMPL, non-commercial)**; решать до продакшена.

**Что могу сделать по слову:** написать «запекатель клипа» (загрузка анимированного BVH/FBX → ретаргет → наш `Clip`) + кнопку импорта в поз-редакторе — это самодостаточный кусок, который сразу позволит тянуть готовые мокап/AI-BVH (хоть с Mixamo, хоть из MDM) в наши клипы, ещё до подключения самой нейросети.

## II.0. Ответ на вопрос: «FBX — это каждый кадр, как ляжет на нашу схему?»

**Коротко: физика у нас — ПОСЛЕДОВАТЕЛЬ, а не источник, поэтому плотность кадров и физика ортогональны.**

- В игре меш ведёт **рэгдолл** (Jolt), который тянется к **позе-цели** через `DriveToPoseUsingMotors` (`humanoidRagdoll.ts`). Клип задаёт цель — физика догоняет её моторами.
- Значит импорт «всех кадров» или «разрежённых ключей» — **на физику не влияет**: рэгдолл в обоих случаях физически догоняет цель (удары, смерть → рэгдолл берёт верх, опустив вес мышц). **Физсоставляющая сохраняется автоматически.**
- Настоящий выбор не «физика vs кадры», а **«сколько ключей хранить»** — это про удобство ручной правки и размер клипа, не про физику.

**Как это делает Puppet Master (RootMotion, Unity) и активные рэгдоллы вообще** — прямая аналогия нашей архитектуре:
- FBX-анимация проигрывается на **кинематической цели** (обычный `Animator`, каждый кадр, без физики).
- Рэгдолл-«кукла» (`PuppetMaster`) состоит из **мышц** = конфигурируемых суставов с моторами/пружинами, которые **догоняют** каждую кость кинематической цели. `pinWeight`/`muscleWeight`/`mappingWeight` = сила следования.
- На удар/смерть вес мышц опускают → рэгдолл «отпускает» цель и падает по физике; потом `GetUp` возвращает следование.
- **FBX НИКОГДА не «физикализуется» напрямую** — он всегда кинематическая цель, физика поверх. Root motion цели уходит в контроллер персонажа, НЕ в рэгдолл.

Это **1:1 то, что у нас уже есть**: наш `Humanoid` (поза-цель из клипа) + Jolt-моторы (`DriveToPoseUsingMotors`) = «target + muscles». Похоже устроены Active-Ragdoll ассеты, Unity Muscle/`ConfigurableJoint`-риги, Ragdoll Dynamics (Maya). Вывод: **нам не надо ничего физикализовать при импорте** — запечённый клип просто становится поза-целью, всё остальное уже работает.

**Итог по твоему варианту:** «тянуть ключевые кадры как сейчас» + **конвертация с прореживанием** — правильный путь. Плотный поток FBX прореживаем в разрежённые ключи (между ними наш slerp + физика сглаживают — ровно как в рукотворных клипах). Опция «все кадры» остаётся для точного повтора.

## II.1. Обратный ретаргет (математика — ключевой момент)

Существующий `makeRetargetRig` (`retarget3d.ts`) гоняет **НАШ риг → импортный скелет** (для скинов): `targetWorld = W_src · R_restTarget`, потом в локаль цели. Для запекателя нужен **ОБРАТНЫЙ ход**: анимированный импортный скелет → повороты НАШИХ костей.

Инвертируем ту же формулу. Наш риг rest-world = I (T-поза, см. `retarget3d.ts:8`), R_restTarget = бинд-мировой кватернион импортной кости (уже считается в `makeRetargetRig` как `restW`). Для каждой нашей кости (порядок родитель→ребёнок):

```
W_our     = W_target · R_restTarget⁻¹          // мировое вращение нашей кости
localOur  = parentOurWorld⁻¹ · W_our           // в локаль (parent уже посчитан — идём сверху вниз)
euler     = Euler.setFromQuaternion(localOur, 'XYZ')   // наш формат Pose = [x,y,z] XYZ (bone.rotation.set)
```

- `W_target` = текущий (после применения кадра анимации) мировой кватернион импортной кости.
- `R_restTarget⁻¹` снимает бинд-разницу T-поз (та же величина, что в прямом ретаргете) → оси/рест приводятся к нашим.
- Euler-порядок строго `'XYZ'` — так наш `pose.ts` пишет позу (`bone.rotation.set(x,y,z)`), а `blendTwo`/`qEuler` интерполируют slerp'ом (эйлер только хранение). Это снимает риск gimbal (см. память `pose-keyframe-interp`).

Проще всего реализовать через НАШ `Humanoid` как аккумулятор: ставим `bone.quaternion = localOur` сверху вниз, `updateMatrixWorld`, затем читаем `bone.rotation` — hierarchy сама даёт локаль. По сути это `readBakedPose()`-подобное снятие, только источник поворотов — импортный скелет через инверсию.

**Куда положить:** новый экспорт в `retarget3d.ts`, например `makeBakeRig(loaded, boneMap, source?) → { sampleInto(humanoid): void, dispose() }`, переиспользующий `restW`/конформ длин. `sampleInto` = одна инверсная прогонка на текущем состоянии импортного скелета.

## II.2. Конвейер запекателя (пошагово)

Новый файл `packages/client/src/render3d/clipBaker.ts`:

1. **Загрузка** — `modelAssets.loadModelFile(file)` (FBX/GLB/GLTF — loader уже есть).
   ⚠️ **Правка `modelAssets`:** FBX-Group несёт `.animations` сам, а `parseModel` для GLB отдаёт `g.scene` и **теряет** `g.animations`. Надо вернуть анимации тоже — расширить `loadModelFile`/`loadModelUrl` до `{ root, animations: THREE.AnimationClip[] }` (или отдельный `loadAnimatedModel`). Для BVH — добавить `BVHLoader` (three/addons) в `parseModel` (отдаёт `{ skeleton, clip }`).
2. **Выбор анимации** — если клипов несколько, дропдаун (по `clip.name`). BVH — один.
3. **Карта костей** — `autoBoneMap(skeletonBoneNames(root))` (Mixamo/SMPL-имена уже нормализуются); ручной override — UI из `poseModelsTab` переиспользуем.
4. **Семплирование** — `mixer = new THREE.AnimationMixer(root)`, `action = mixer.clipAction(animClip); action.play()`. Идём по времени с шагом `dt` (нативный fps клипа или 30): `mixer.setTime(t); root.updateMatrixWorld(true); bakeRig.sampleInto(H); pose = readPose(H)`. Копим плотный массив `{pose, t}` (t от нуля).
5. **Прореживание (конвертация → ключи)** — жадный алгоритм на плотном массиве:
   - старт: ключи = {первый, последний};
   - находим кадр с макс. ошибкой относительно текущей slerp-реконструкции, **ошибку мерим в углах кватернионов** (max по костям, `q1.angleTo(q2)` в градусах), не в Euler-дельте;
   - если max-ошибка > ε — вставляем этот кадр ключом; повторяем, пока всё ≤ ε.
   - Ползунок **«детализация ε» (°)**: больше ε → меньше ключей → сильнее сглаживают slerp+физика. ε=0 (или тумблер «все кадры») → без прореживания.
   - Каждый ключ хранит ПОЛНУЮ позу (наш формат Keyframe = вся поза в момент t) — union времён не нужен, берём позу целиком на выбранных t.
6. **Root motion** — наши клипы это ТОЛЬКО повороты костей (таз кинематический, позицию держит игра/гейт). Перемещение корня FBX **отбрасываем** (как Puppet Master отдаёт root motion контроллеру). Опц.: посчитать среднюю горизонт. скорость таза → подсказка для гейта/скорости, но НЕ в `pose`.
7. **Сборка `Clip`** — `{ name (имя файла/анимации), character (текущий в редакторе), weapon (текущий), loop (по имени: walk/run/idle → true, иначе тумблер), keys }`. Сохранить в `pe_clips` (тот же путь, что рукотворные клипы) и открыть в таймлайне редактора для доводки.

## II.3. UI в поз-редакторе

- Кнопка **«📥 Импорт анимации (FBX/GLB/BVH)»** рядом с вкладкой «Модели» (`poseModelsTab`).
