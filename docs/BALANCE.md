# BALANCE.md — калибровка (Фаза D)

Баланс выверяется симулятором: `npm run sim -- ...` (CLI) и вкладка «🧪 Симулятор» в
редакторе. Модель: тик-бой против всей пачки, реальные формулы боя/лута/монстров,
эконом-бот (дроп→экип→магазин), макро-прокачка (нырять/фарм/смерть). Подробнее —
`packages/shared/src/sim/`.

## Опыт (переделано: без скрытых множителей)
- **Множители убраны:** `xpGainMult` и `difficulties.xpMult` удалены. Опыт с килла = `def.xp`
  напрямую (сколько в редакторе — столько и дают, × уровень монстра).
- **Опыт монстра = `base.xp × (1 + level × monsterXpGrowth)`** (`monsterXpGrowth=0.2`),
  чемпионы `× championXpMult` (=3).
- ⭐⭐ **13.10 (Г1): Уровень монстра = НОМЕР ЭТАЖА** — `round(startLevel + (этаж − 1) × floorStep)`, при `normal`
  (1 / 1) этаж N даёт монстров N уровня, потолка нет (200-й этаж → 200-й уровень). Мощь героя (`effectiveLevel`)
  в уровень монстра НЕ входит нигде: до 13.10 было `мощь + глубина`, и прокачанный герой встречал на 1-м этаже
  81-й уровень. ⚠ Следствие: опыт, золото, уровень вещей с тел и из сундуков и ступень сырья едут по кривой
  ГЛУБИНЫ — прежние числа (2…95 за 15 этажей) схлопнулись в 2…16, и вся награда забега требует перекалибровки.
- ⭐⭐ **14.10 (Г6): ШТРАФ ЗА РАЗНИЦУ УРОВНЕЙ (форма Path of Exile) И ДЕЛЕЖ НА ПАТИ** — `balance.xpShare`,
  формулы `formulas/xp.ts` (`xpLevelMult`, `xpPartyShare`, `xpForKill`), сторож `formulas/xpShare.test.ts`.
  Полоса без штрафа `floor(3 + уровень/16)` (на 20 ур. ±4, на 80 ±8), дальше плавный спад
  `((L+5)/(L+5+over^2.5))^1.5` с полом **1 %**. ЗАМЕР (процент опыта по разрыву):
  | уровень | +5 | +8 | +10 | +15 | +25 |
  | --- | --- | --- | --- | --- | --- |
  | 1 | 36.9 % | 3.0 % | 1 % | 1 % | 1 % |
  | 20 | 94.3 % | 29.0 % | 10.4 % | 1.4 % | 1 % |
  | 50 | 100 % | 86.3 % | 50.3 % | 7.9 % | 1 % |
  | 80 | 100 % | 100 % | 90.8 % | 24.9 % | 1.7 % |
  | 99 | 100 % | 100 % | 98.6 % | 39.8 % | 2.8 % |
  Опыт делится на ВСЮ пати (все игроки сессии, живые и мёртвые — как зона PoE): доля `(1 + bonus×(n−1))/n`,
  `partyBonusPerMember` = 0, то есть честное `1/n`. ⚠ ЗАЧЕМ: до Г6 штрафа не было вовсе и опыт не делился —
  самой выгодной игрой было стоять в углу, пока тебя тащат по глубине; а с Г1 уровень монстра это НОМЕР ЭТАЖА,
  значит «тащат» = «посадили на этаж не по зубам». Обратная сторона того же правила: герой 80-го уровня на 10-м
  этаже получает крохи — иначе глубина не нужна. Пол 1 %, а не 0, намеренно: «не по зубам» обязано остаться
  «честно мало», а не «бессмысленно». ⚠ Выключается ОДНИМ числом: `xpShare.floor = 1` снимает штраф,
  `partyBonusPerMember = 1` — дележ. ЗАМЕР цельного счёта: монстр 1000 xp на 60-м этаже — соло 1000, вдвоём по
  500, протащенный 10-го уровня 5 (0.5 % от соло).
- ⭐⭐ **15.10 (Г6, кооп, решение владельца): НАДБАВКА ПАТИ 50 % И МОНСТР ЖИРНЕЕ НА 50 % ЗА КАЖДОГО ЛИШНЕГО ИГРОКА.**

## ⭐⭐ Потолок героя — 99 (решение владельца 14.10, как в D2)
`balance.xpTable` — 100 строк, индекс = уровень, значит максимум `xpTable[99]`. Числом потолок не вшит нигде:
`maxLevel(xpTable) = длина − 1`, и больше его никто не знает.

Хвост 91…99 продлён **по закону самой кривой**, а не на глазок. Мера — множитель шага `шаг(L)/шаг(L−1)`: на 90-м
уровне он 1.017283 и гаснет на ~0.000235 за уровень (на 80-м был 1.019931). Отсюда пороги: 91 → 42 821 002 ·
92 → 44 046 736 · 93 → 45 292 791 · 94 → 46 559 212 · 95 → 47 846 035 · 96 → 49 153 286 · 97 → 50 480 983 ·
98 → 51 829 134 · **99 → 53 197 737**. На стыке 90→91 нет ни ступеньки, ни излома — это обычный уровень хвоста.

Сторож — `shared/src/config/levelCap.test.ts`: длина 100, строгий рост (R20-05), монотонность и РОВНОСТЬ гашения
множителя через стык, герой доходит до 99 и не выше, старый сейв 90-го уровня цел (полоса опыта показывает путь к
91-му, очки за новые уровни выдаются по разу). ⚠ Снижение потолка уровни НЕ отнимает (R9-05, `save.earned`).

## Калибровка прокачки (сим, бот-воин, «Средняя»)
Цель: 1→90 ≈ 50 ч, старт бодрый. Достигнуто (`xpTable` подогнана):
- L5 ~8 мин · L10 ~41 мин · L20 ~2.7 ч · L30 ~5.8 ч · L50 ~15.3 ч · L70 ~30 ч · **L90 ~49 ч**.
- Метод: `runSessionSim` 1→90, замер часов→уровень, порог[L] × (нужное_время/факт), 2 прохода.
- ⚠ 14.10: КАЛИБРОВКА ЦЕЛИ ОСТАЛАСЬ НА 1→90 — хвост 91…99 дописан законом кривой, а не замером времени. Девять
  уровней хвоста стоят ≈11,6 млн опыта (53 197 737 − 41 615 536), то есть ≈28 % порога 90-го: по той же скорости это
  ещё ≈14 ч. Перемерить симом — вместе с перекалибровкой награды под кривую глубины (см. выше).
- Живой игрок эффективнее бота (у бота ~180 смертей на прогон) → пройдёт быстрее; крутить
  через `xpTable` / `monsterXpGrowth` в редакторе.
- ⚠ R9-05: правка `xpTable` уровни существующих героев НЕ опускает (раньше вход пересчитывал уровень по опыту вниз, а
  добор опыта платил очки тех же уровней второй раз). Кривая стала медленнее — герой остаётся своим уровнем, а следующий
  получит, когда опыт догонит новый порог (окно персонажа покажет опыт ниже порога уровня); потолок ниже — герой выше
  потолка остаётся выше, очки за его уровни не платятся снова.
- ⚠ R20-05: `xpTable` = 0, 0, дальше СТРОГО растёт, числа конечные ≥ 0 — иначе схема отказывает (редактору 422 с номером порога).
  Опечатка (участок порогов не выше прежних — вставка мимо, пропущенная цифра, повтор) поднимала героя одним очком опыта через
  весь участок с очками за каждый уровень, а по R9-05 такие уровни не отнимаются. Вторая линия — `levelForXp` по ступеньке не лезет.
- ⭐ D2: правка прокачки (кривая, очки за уровень, старт класса, древа) касается только БУДУЩИХ выдач — выданное герой помнит сам
  (`save.earned`: очки трёх пулов за каждый уровень по числам того мига), сброс возвращает ровно вложенное, уровень не опускается.
  Оверрайд баланса в базе, сохранённый до R20-05 с кривой не по правилу, при сборке приводится (`upgradeXpTable`: выпавшие пороги — на
  прямую между оставшимися, хвост без порогов выше прежних отрезается), а не выбрасывается весь баланс. Полоса опыта терпит уровень выше
  потолка и опыт ниже порога (`xpProgress`).

## ⭐ D4 — одно правило времени баффа
**Правило (решение владельца):** откат временного баффа на КАЖДОМ ранге не короче его действия на том же ранге с отдыхом:
`откат(ранг) ≥ действие(ранг) × (1 + balance.buffMinRest)`, `buffMinRest = 0.25` (> 0: откат всегда строго длиннее действия) — под баффом
не больше 1 / 1.25 = **80 %** времени на любом ранге, со вставками, через арены и переподключения. Одно место — `formulas/buffTiming.ts`:
схема поверх таблиц (реестр и редактор не пускают нарушение, docs/CONFIG_SCHEMA.md), приведение старых оверрайдов, зажим ядра со
строкой в лог (только для конфига мимо схемы), фаззер правил (`buff-rest`, `buff-uptime` по часам героя). История: R6-15 (отката не
было — 100 %), R19-03 (ранг режет откат, а не действие: зажим был только в ядре, данные и редактор о нём не знали).

**Почему менялись данные.** Ранг баффа даёт одно — откат −3 % базы за ранг (до 35 %), действие рангом не растёт. На 20 рангах откат
падает до 43 % базы, и правило на 20-м ранге требовало бы базу ×2.33 от пола — первый ранг баффа стал бы редким (клич — 8 с раз в 23 с).
Под R19-03 ранги выше «пола» (клич — с 7-го) не давали ничего: мёртвые очки. **Выбор:** у баффов 8 рангов — наибольший общий потолок,
при котором замысел каждого баффа достижим под правилом (у «Терновой мантии» 71 % — только при потолке ≤ 8); база отката подобрана
так, чтобы **средняя по рангам доля времени под баффом была как у замысла** (действие/откат из описания до правки), без замысла —
**≤ 60 % на высшем ранге**. Ранг выше потолка (вложенный до правки) откат дальше не режет (`buffNodeCooldown`); сброс возвращает очки.

| Бафф | Действие | Было (откат × рангов) | Стало | 1-й ранг | 8-й ранг | Среднее | Замысел |

**Печати вставок** («Оберег», «Лёгкий шаг», тип «Печать»): прок-бафф освежался каждым применением носителя — на спамном ударе
(откат 0) 100 % времени. Теперь у печати свой откат (`proc.ability.cooldown`, один на все скилы с этой вставкой; бросок шанса — до
него, поток бросков мира прежний). Действие растёт с рангом донора (×2.08 на 10-м), замысла по времени нет → ≤ 60 % на высшем ранге:
«Оберег» 4 с → 8.32 с, откат **14 с** (29 % → 59 %); «Лёгкий шаг» 3 с → 6.24 с, откат **10.5 с** (29 % → 59 %). Цена вставки — как была,
на каждом применении носителя (печать в откате не вешается). Баффы зелий (`pot:`) правилу не подчиняются: они расходные — ограничены
колбами, а не временем.

**Переходы.** Откат — время героя, а не тела (`session/heroBody.ts`): конец арены берёт более поздний из города и арены (раньше
клич, взятый на арене, в городе был готов снова — два окна баффа на откат, до 2·действие / (откат + действие) времени), так же ушедшему
с арены раньше и погибшему на ней с обрывом. Между комнатами откаты идут в сейве рядом с пулами (`vitals.cd`, остаток минус время вне
игры, как реген R11-04): новая комната и запись ухода, которую обогнал сейв другой комнаты (R12-02), больше не значат «клич готов» (раньше
клич на арене → к другу и назад по коду → клич снова). Та же комната без чужой записи — запись ухода, время для ушедшего стоит (R4-06).
⭐ R22-04: и через смерть — мёртвый пишется в сейв без пулов, но с откатами (`vitalsForSave`: `{ at, cd }`), штраф смерти снимает только пулы:
погибший в коопе, закрывший вкладку, пока ждал пати, после её смены этажа (она снимает его мёртвую запись ухода) входит с откатами, а не с
готовым кличем (раньше — полный откат баффа даром за каждую смерть; фаззер правил моделирует это шагом `reconnect`).
⚠ R23-05: тело города на время арены снято на входе и стоит, а время героя идёт — бой на арене его старит (`agedBody`: откаты, баффы,
таймеры) у всех, кто его уносит: конец арены (`arenaReturn`, всё время боя), сейв с арены (`vitalsForSave` — уход до конца, автосейв,
дренаж ноды) и запись ушедшего, которой конец арены делает тело города (`arenaAwayBody`, время до ухода — `Room.arenaHome.leftAt`).
Раньше последние два несли его застывшим на входе: клич, по времени героя давно готовый, в новой комнате — снова в откате (против игрока,
до самого длинного отката). Сторож фаззера правил — «откат не длиннее часов героя» (`I3:skill-cd-long`: в теле, сейве ухода и на входе).
⭐ R21-05: и экрану — кадр входа несёт откаты, с которыми сервер посадил героя (`joined.cooldowns`: остаток и полный, мс; `GameSession.cooldownsOf` —

## Модельные правки (для достоверности сима)
- Скиллы — реальные касты (4 «хотбарных», КД/мана, `resolveAttack`), AoE бьёт всю пачку.
- Кайт: мили-удары мимо для дальнего/мага (0/35/25%); стрелки кайт игнорируют.
- Стартовый КД монстров — случайная фаза интервала (иначе в коротких боях не бьют).
- DPS считается без овер-килла.

## Тиры баз (решено — гибрид)
`item-tiers.json` — 7 тиров по `minItemLevel`, **лестница начинается со «Сломанного» = базовый
×1.0** (без штрафа): Сломанный 1.0 → Старый 1.3 → Крепкий 1.8 → Отличный 2.5 → Мастерский 3.4 →
Элитный 4.6 → Мифический 6.0. У каждой базы — диапазон **`minTier`/`maxTier`** (id тира): предмет
катает тир только в нём, зажатый уровнем дропа (по умолчанию t0–t6). Префикс имени согласуется по
роду базы (`gender`; Крепкий→Крепкое/Крепкая/Крепкие).
Генератор по ilvl дропа берёт высший доступный тир: урон/броня базы × `statMult`, требования
× `reqMult`, имя = префикс тира + архетип («Элитный Жезл огня»). Добавлены архетипы (булава,
длинный лук, арбалет, жезл молний, посох льда) — по 2–3 оружия на класс с разными
требованиями. Итог: гир растёт с глубиной, высокоуровневый обрыв закрыт (ур.50 стал реальным
боем ~78% побед / 48% HP вместо 19%), прокачка 1→90 ≈ **27 ч**. Сохраняется мягкий «зубец»
сложности на границах тиров (перед тир-апом слабее, после — сильнее) — это ожидаемо, D2-фил.
