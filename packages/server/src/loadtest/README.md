# loadtest — нагрузочный стенд и регрессионные гейты сервера

Инструменты, которыми проверяется каждая правка из плана доработки сервера. Правило плана:
**у любой правки должно быть число до и после**, иначе непонятно, дала она что-нибудь или нет.

Стенд не участвует в игре и не тянется в прод-бандл — это dev-инструменты, запускаемые вручную.

## Состав

| Файл | Что делает |
|---|---|
| `client.ts` | Один бот-клиент: регистрация → персонаж → комната → спуск → ввод с частотой тика. Ходит по настоящему протоколу (`ClientFrame`/`ServerFrame`), поэтому нагружает весь путь сервера |
| `run.ts` | CLI-раннер: поднимает N ботов, печатает вердикт с порогами, возвращает код выхода 0/1 |
| `probe.ts` | Обёртка боевого `index.ts`: тот же сервер + самоотчёт CPU, RSS и лага цикла событий раз в 3 с |
| `dupe.ts` | PoC дюпа: проверяет инвариант «один персонаж — одна живая сессия» (задача Ф0.3) |
| `flood.ts` | Проверка лимитов частоты Ф0.5: регистрация, вход, поток кадров ws |
| `tick.ts` | Бенч боевого ядра без сети: реальный `generateFloor` + `GameSession.tick` + сборка кадра |

## Как гонять

Сервер стенда поднимается отдельно от боевого и на **своей БД** — боты плодят аккаунты,
засорять ими рабочую базу нельзя.

```bash
npm run loadtest:server                       # порт 3999, data/loadtest.db, NODE_ENV=production
npm run loadtest -- --n=100 --secs=30 --hz=60 # 100 соло-игроков на реальной частоте ввода клиента
npm run loadtest -- --n=100 --group=4         # 100 игроков в пати по 4
npm run poc:dupe                              # проверка инварианта одной сессии
npm run poc:flood                             # проверка лимитов частоты (см. оговорку ниже)
npm run bench:tick                            # ядро без сети
npm run bench:tick -- --players=4 --ticks=200000
```

Ключи `run.ts`: `--n` число ботов, `--secs` длительность замера, `--group` размер пати,
`--hz` частота ввода, `--warmup` прогрев, `--descend=false` держать ботов в городе,
`--tickHz` норма частоты мира, `--rttLimit` порог RTT, `--base` адрес сервера.

**Про `--hz`:** боевой клиент шлёт ввод из рендер-цикла, то есть 60–144 Гц (`online3d.ts`,
`sendInput`). Поэтому «как в жизни» — это `--hz=60`; значение по умолчанию 30 отражает
целевое состояние после задачи Ф0.8. Сравнивать прогоны между собой только при одинаковом `--hz`.

**Про лимиты частоты.** `loadtest:server` ставит `DM_RATELIMIT=off`: сотня ботов идёт с одного
адреса и упёрлась бы в лимит регистрации раньше, чем начнётся замер. Поэтому сами лимиты
проверяются отдельно — `poc:flood` против сервера, поднятого КАК БОЕВОЙ:

```bash
PORT=3999 DM_DB=data/flood.db NODE_ENV=production npm start
npm run poc:flood
```

## Вердикт и пороги

`run.ts` возвращает **0**, если одновременно: частота мира не ниже 95 % нормы, RTT медиана
в пределах порога, не отвалился ни один бот и сервер не прислал ни одного кадра `error`.
Иначе — **1**. Это позволяет вешать стенд на CI как гейт.

## Опорные числа ДО начала работ

Стенд i7-11800H, 16 логич. ядер, Node 24.18, Windows. Снято этим же инструментом.

| Прогон | CPU процесса | RSS | Частота мира | RTT медиана | Трафик вниз |
|---|---|---|---|---|---|
| `--n=50 --hz=30` | 44–67 % | ~340 МБ | 21,9 Гц | 9,6 мс | 175 КБ/с на клиента |
| `--n=100 --hz=60` (как в жизни) | **145–163 %** | 475→531 МБ, растёт | 26,2 Гц | **12 449 мс** | 207 КБ/с на клиента |

Второй прогон — тот самый коллапс: `perMessageDeflate` жмёт каждый кадр каждому клиенту
в пуле из четырёх потоков libuv, пул захлёбывается, очередь исходящих растёт (отсюда CPU выше
одного ядра и рост RSS), задержка уходит в двенадцать секунд. Задача Ф0.1.

## После группы 1 (Ф0.1 сжатие + Ф0.2 планировщик + Ф0.8 троттлинг ввода)

Тот же прогон `--n=100 --secs=25 --hz=60`, та же машина:

| Показатель | До | После |
|---|---|---|
| RTT медиана | 12 449 мс | **13,2 мс** |
| RTT p95 | 13 307 мс | **16,0 мс** |
| Частота мира | 26,2 Гц | **28,8 Гц** ✓ |
| CPU процесса | 145–163 % | **66–74 %** |
| RSS | 475→531 МБ, рос | **333 МБ, стабильно** |
| Вердикт стенда | ✗ | **✓ все пороги** |

Трафик вниз вырос с 207 до 218 КБ/с на клиента — это ожидаемая плата за снятое сжатие;
Ф1 (дельта-кадр + область интереса) уводит его на порядок вниз.

`npm run bench:tick` (соло, 48×38, 40 монстров, 100 000 тиков):

```
  tick               37.170 мкс
  сборка кадра       22.729 мкс
  итого на комнату   59.898 мкс/тик
  кадр               7192 Б
```

`npm run poc:dupe` — **✗ дюп воспроизводится**: один `charId` входит в две комнаты одновременно.
Задача Ф0.3.

## После группы 3 (Ф0.6, Ф0.7, Ф0.9, Ф0.10, Ф0.11, Ф0.12) — Ф0 закрыта

`bench:tick`, соло, 40 монстров:

| | До Ф0.11 | После |
|---|---|---|
| tick | 37,170 мкс | **20,869 мкс** (−44 %) |
| сборка кадра | 22,729 мкс | 24,576 мкс |
| итого на комнату | 59,898 мкс | **45,445 мкс** |

Выигрыш куда больше ожидавшихся 5 %: в боевом `session.ts` `Math.hypot` стоял в существенно
большем числе горячих мест, чем в синтетическом бенче, на котором делалась прикидка.

`loadtest --n=100 --hz=60` (машина уже прогрета, сравнивать с контролем группы 1 — 24,7 Гц):

| Показатель | Группа 1 (контроль) | Группа 3 |
|---|---|---|
| Частота мира | 24,7 Гц | **29,8 Гц** ✓ |
| RTT медиана | 19,6 мс | **14,4 мс** ✓ |
| CPU процесса | 82–91 % | 72–85 % |

`GET /api/config`: 200 с телом 479 КБ → повторный запрос с `If-None-Match` даёт **304 и 0 байт**.
Dev-роуты при `NODE_ENV=production` отвечают **403**.

## После группы 2 (Ф0.3 замок + версия сейва, Ф0.4 транзакция, Ф0.5 лимиты)

- `poc:dupe` → **✓ инвариант держится**: второй вход выселяет первый, сессия A отключается.
- `poc:flood` → **✓ все три лимита**: регистрация 5 прошло / 35 отбито, вход 30 из 40 отбито,
  флуд кадрами закрывает соединение.
- Производительность не изменилась. Проверено контрольным прогоном: код группы 1 в тех же
  условиях дал 24,7 Гц при CPU 82–91 %, код группы 2 — 21,6–25,4 Гц при CPU 80–89 %. Разброс
  целиком объясняется дрейфом машины (замер группы 1 снимался часом раньше, до прогрева
  ноутбука), а не правками. **Вывод: сравнивать прогоны только подряд и в одних условиях.**

Гранулярность таймеров Windows — 15,6 мс, поэтому `setInterval(33)` там физически не даёт
30 Гц (получается ~21,5). На Windows сравнивать прогоны между собой, абсолютную норму 30 Гц
проверять на Linux.
