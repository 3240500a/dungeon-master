# loadtest — нагрузочный стенд и регрессионные гейты сервера

Инструменты, которыми проверяется каждая правка из плана доработки сервера. Правило плана:
**у любой правки должно быть число до и после**, иначе непонятно, дала она что-нибудь или нет.

Стенд не участвует в игре и не тянется в прод-бандл — это dev-инструменты, запускаемые вручную.

## Состав

| Файл | Что делает |
|---|---|
| `client.ts` | Один бот-клиент: регистрация → персонаж → комната → спуск → ввод с частотой тика. Ходит по настоящему протоколу (`ClientFrame`/`ServerFrame`), поэтому нагружает весь путь сервера |
| `run.ts` | CLI-раннер: поднимает N ботов, печатает вердикт с порогами, возвращает код выхода 0/1 |
| `probe.ts` | Обёртка боевого `index.ts`: тот же сервер + самоотчёт CPU, RSS и лага цикла событий раз в 3 с |
| `dupe.ts` | PoC дюпа: проверяет инвариант «один персонаж — одна живая сессия» (задача Ф0.3) |
| `flood.ts` | Проверка лимитов частоты Ф0.5: регистрация, вход, поток кадров ws |
| `bench.ts` + `worker.ts` | **Поиск потолка** (`npm run bench:ramp`): боты в отдельных процессах, ступени, ворота качества, защита от самообмана |
| `deltacheck.ts` | Диагностика дельт Ф1.3: один бот, при расхождении печатает ЧТО именно уехало |
| `tick.ts` | Бенч боевого ядра без сети: реальный `generateFloor` + `GameSession.tick` + сборка кадра |

## Как гонять

Сервер стенда поднимается отдельно от боевого и на **своей БД** — боты плодят аккаунты,
засорять ими рабочую базу нельзя.

```bash
npm run loadtest:server                       # порт 3999, data/loadtest.db, NODE_ENV=production
npm run loadtest -- --n=100 --secs=30 --hz=60 # 100 соло-игроков на реальной частоте ввода клиента
npm run loadtest -- --n=100 --group=4         # 100 игроков в пати по 4
npm run poc:dupe                              # проверка инварианта одной сессии
npm run poc:flood                             # проверка лимитов частоты (см. оговорку ниже)
npm run poc:delta                             # диагностика дельта-снапшотов
npm run bench:tick                            # ядро без сети
npm run bench:tick -- --players=4 --ticks=200000
```

Ключи `run.ts`: `--n` число ботов, `--secs` длительность замера, `--group` размер пати,
`--hz` частота ввода, `--warmup` прогрев, `--descend=false` держать ботов в городе,
`--tickHz` норма частоты мира, `--rttLimit` порог RTT, `--base` адрес сервера.

**Про `--hz`:** боевой клиент шлёт ввод из рендер-цикла, то есть 60–144 Гц (`online3d.ts`,
`sendInput`). Поэтому «как в жизни» — это `--hz=60`; значение по умолчанию 30 отражает
целевое состояние после задачи Ф0.8. Сравнивать прогоны между собой только при одинаковом `--hz`.

**Про лимиты частоты.** `loadtest:server` ставит `DM_RATELIMIT=off`: сотня ботов идёт с одного
адреса и упёрлась бы в лимит регистрации раньше, чем начнётся замер. Поэтому сами лимиты
проверяются отдельно — `poc:flood` против сервера, поднятого КАК БОЕВОЙ:

```bash
PORT=3999 DM_PG=postgresql://dm:dmpass@127.0.0.1:5432/dungeon_test NODE_ENV=production npx tsx packages/server/src/index.ts
npm run poc:flood
```

## Вердикт и пороги

`run.ts` возвращает **0**, если одновременно: частота мира не ниже 95 % нормы, RTT медиана
в пределах порога, не отвалился ни один бот и сервер не прислал ни одного кадра `error`.
Иначе — **1**. Это позволяет вешать стенд на CI как гейт.

## Хвосты плана закрыты: аудит по расписанию, откат аккаунта, и почему НЕ бинарный ввод

### Ф2.6 — ночной аудит инвариантов

Проверка вынесена в `db/audit.ts` и считает одно и то же для человека (`npm run items:audit`)
и для ночной задачи на гейтвее (час задаётся `DM_AUDIT_HOUR`, по умолчанию 4 утра). Гейтвей,
а не нода: он в кластере один, иначе проверка шла бы восемь раз за ночь и наперегонки.

Что проверяется:

| Находка | Уровень | Смысл |
|---|---|---|
| вещи без записи о рождении | инцидент | в леджер писал не наш код |
| одна вещь в двух местах | инцидент | дюп |
| сейв и леджер разошлись | инцидент | лишнее в сейве |
| леджер держит вещь, которой нет в сейве | инцидент | потерянное (обратная сверка) |
| незнакомая причина создания | внимание | новая ветка кода или запись мимо обычного пути |
| добыча выше медианы впятеро | внимание | выброс по аккаунтам за сутки |
| закрепления за исчезнувшими узлами | внимание | кластер разъехался |

Прогоны пишутся в `audit_runs`: без истории «ноль нарушений» не с чем сравнить, и не видно,
когда именно инвариант поехал. Находка — это повод посмотреть, а не основание для действия;
правило то же, что у детектора аномалий.

**Честно о границе: сохранности ЗОЛОТА проверить нечем** — журнала для золота нет, есть только
журнал предметов. Поэтому экономические проверки здесь о скорости появления вещей и о выбросах
между аккаунтами, а не о балансе «добыто против потрачено».

Проверено тестом: подсаженные ПРЯМО В БАЗУ дубль и старый id находятся оба — аудит ловит и то,
что записал не наш сервер.

### Ф2.7 — откат предметов аккаунта на момент времени

```bash
npm run items:rollback -- --user=<id> --to=2026-09-09T10:00:00Z            # показ
npm run items:rollback -- --user=<id> --to=… --reason="дюп" --apply       # применить
```

По журналу вычисляется, где вещи лежали на момент отсечки: потерянное возвращается,
появившееся позже забирается. Одной транзакцией — половина отката хуже, чем его отсутствие.
Леджер и журнал приводятся в то же состояние, иначе ближайший аудит объявит откат нарушением.

Откат ТОЧЕЧНЫЙ, и это принципиально: откат всей базы карает невиновных — у сотни человек
пропадает вечер игры из-за одного дупера.

Чего откат не вернёт (границы честные, а не временные):
* **золото и опыт** — журнала для них нет;
* **слоты экипировки** — журнал пишет место («у персонажа»), но не слот; всё уедет в инвентарь;
* **отозванные вещи** — решение человека сильнее восстановления по времени.

### Бинарный кадр ввода: измерено и НЕ СДЕЛАНО

`npm run bench:input` — сколько стоит разбор входящего кадра:

| Что | нс на кадр |
|---|---|
| `JSON.parse` + проверка схемой | **863** |
| двоичный разбор того же | **91** |

Кадр 128 байт против 8 двоичных. На 400 игроках при 30 Гц это 12 000 кадров/с:

* сейчас — **1,04 % ядра**;
* двоично — 0,11 %;
* экономия **0,93 % ядра**.

Меньше процента за переделку интерфейса соединения, обоих транспортов, клиента и тестов.
**Не делаем.** Заодно замер снял ещё одно подозрение: проверка схемой (zod-lite) на фоне
`JSON.parse` не стоит НИЧЕГО — разница между «с проверкой» и «только разбор» тонет в шуме.

Вывод важнее самой отмены: раз наш разбор стоит 1 %, а входящее сообщение целиком мерилось
в 13 мкс, то **остаток сидит внутри сокетного слоя, а не в нашем коде**. Именно поэтому uWS
и дал 9–12 %: дальше выигрывают не микро-оптимизации, а меньшее число сообщений или другой
транспорт.

## Ф4 (кластер): потолок 400 → 1000 игроков

Один процесс Node — одно ядро, и на потолке он съедал его целиком. Ф4 раскладывает игру
по процессам: гейтвей на своём порту, игровые ноды на своих, реестр в Postgres.

### Поиск потолка на четырёх нодах (пати по 4, ввод 30 Гц)

| Игроков | Кадры/с | Тик | RTT мед./p95 | КБ/с | CPU кластера | RSS |
|---|---|---|---|---|---|---|
| 200 | 20,0 | 30,0 | 3 / 3 мс | 12,9 | 91 % | 1221 МБ |
| 400 | 20,0 | 30,0 | 4 / 5 мс | 12,5 | 155 % | 1292 МБ |
| 600 | 20,0 | 29,9 | 4 / 6 мс | 12,2 | 233 % | 1365 МБ |
| 800 | 20,0 | 30,1 | 5 / 6 мс | 11,7 | 304 % | 1451 МБ |
| **1000** | **20,0** | **30,0** | **7 / 11 мс** | **11,5** | **386 %** | **1532 МБ** |
| 1200 | 16,5 ✗ | 30,0 | 30 / 50 мс | 9,0 | 446 % | 1640 МБ |

**Потолок: 1000 игроков** против 400 у одиночного процесса. Раскладка на предельной ступени
ровная: 303 / 298 / 301 / 298 игроков и 86 / 81 / 81 / 77 комнат — гейтвей держит баланс.

### Кривая масштабирования: ОДНА нагрузка, разное число нод

Ступенчатый поиск потолка не отвечает на вопрос «растёт ли отдача линейно» — там меняется
и нагрузка, и число процессов. Поэтому отдельный замер: 600 игроков на 1, 2, 4 и 8 нодах,
прогоны подряд.

| Нод | Кадры/с | RTT мед./p95 | CPU кластера | RSS |
|---|---|---|---|---|
| 1 | ступень не собралась — процесс не принял 600 | | | |
| 2 | 19,5 | 14 / 18 мс | 211 % | 812 МБ |
| 4 | 20,0 | 5 / 5 мс | 245 % | 1368 МБ |
| 8 | 20,0 | 3 / 4 мс | 314 % | 2505 МБ |

Читается так: **ноды покупают задержку и запас, а платят процессором и памятью.** От 2 к 8
задержка падает вчетверо (14 → 3 мс), CPU растёт на 49 %, память втрое. Каждый процесс несёт
свой конфиг и свою кучу — около 270 МБ на ноду.

### Честно про эффективность: кластер НЕ бесплатен

Одиночный процесс держал 400 игроков на ядро. В кластере на ноду приходится 250 (1000 ÷ 4),
то есть **эффективность ядра упала примерно на треть**. Причины — конкуренция четырёх занятых
процессов за память и кэш, плюс общая база под ними. Это не мешает: пятнадцать ядер всё равно
дают больше, чем одно, — но множитель от числа нод получается не ×4, а ×2,5.

### Границы: очередь и слив узла

`npm run poc:cluster -- --mode=queue` (потолок 30, желающих 50):
впущено 30, в очередь 20, освободили 5 мест — прошли ровно 5.

`npm run poc:cluster -- --mode=drain` (3 ноды, 40 игроков):
слитый узел 14 → 0, соседи 13 / 13 без изменений, игрок со слитого узла вернулся в игру
с целым прогрессом.

Слив вызывается ручкой `POST /internal/drain` (только с самой машины). На Windows сигналов
нет и проверить иначе нельзя, а в бою это штатная выкатка: слить узел, дождаться пустоты,
перезапустить — и так по одному, без простоя для остальных.

### Три грабли кластера, найденные первым же запуском

1. **Пять процессов одновременно создают схему** — «триггер уже существует». Схема теперь
   заводится под консультативной блокировкой Postgres.
2. **Порты столкнулись.** В режиме uws express уезжает на `PORT+1`, а там уже сидела
   СЛЕДУЮЩАЯ нода: боты получали HTTP 200 вместо рукопожатия WebSocket. Внутренние порты
   разведены в отдельный диапазон.
3. **Всплеск подключений уходил на ОДИН узел** (40 / 0 / 0 / 0). Показатели приходят раз
   в две секунды, и сорок ботов видели «везде по нулю». Гейтвей теперь прибавляет уже
   выданные, но ещё не отражённые направления — стало 12 / 8 / 8 / 12. Ровно та же поправка
   понадобилась очереди: без неё потолок 30 пропускал всех 50.

## Перемер uWS после общего кадра: теперь выигрывает 9–12 %

Первый замер uWS (ниже по документу) дал ноль разницы — и это был честный результат для
своей точки: транспорт тогда занимал малую долю работы. После общего кадра на комнату
арифметика изменилась. Разложение стоимости на потолке (400 игроков, 100 комнат, 108 % ядра):

| Что | Сколько ядра |
|---|---|
| симуляция — 100 комнат × 30 Гц × 19 мкс | 5,7 % |
| сборка кадра — 100 комнат × 20 Гц × 22,5 мкс | 4,5 % |
| **всё остальное: отправка, приём, разбор ввода, сборка мусора** | **≈ 98 %** |

То есть транспорт стал почти всей работой — и в этой точке замер надо было повторить.

Два прогона ПОДРЯД, пати по 4:

| Ботов | uWS | `ws` (контроль) | Разница |
|---|---|---|---|
| 100 | 35 % · RTT 3/4 мс | 36 % · RTT 4/5 мс | −3 % |
| 200 | 52 % · RTT 6/8 мс | 57 % · RTT 8/10 мс | −9 % |
| 300 | 78 % · RTT 12/14 мс | 86 % · RTT 12/16 мс | −9 % |
| 400 | 98 % · RTT 14/17 мс | ступень не собралась | — |
| **Ёмкость** | **400** | **300** | **+33 %** |

320 812 и 239 304 сверки дельт, ноль расхождений в обоих.

Чистый транспортный бенч обещал −23 %; получили 9–12 %, потому что транспорт хоть и
основная работа, но не вся. Ёмкость `ws` в этом прогоне вышла 300 против 400 в прогоне
получасом раньше — граница шумит, потому что упирается она не в игровой цикл (см. ниже).

### Что вылезло попутно: на потолке НЕ ЗАЙТИ в игру

Обе ступени за потолком проваливались одинаково — «сервер уже не успевает принимать новых
игроков». Это не артефакт стенда, а настоящее поведение: регистрация и вход идут через тот же
цикл событий, что и игра, и на занятом сервере они встают в очередь за игровыми кадрами.
Игроки внутри продолжают играть нормально; не может зайти НОВЫЙ.

Ровно на это в плане есть Ф4.4 — очередь на вход у гейтвея: держать людей в очереди дешевле,
чем принять всех и лечь. Наш замер подтвердил необходимость независимо от плана.

## Общий кадр на комнату: потолок 150 → 250 соло и 300 → 400 в пати

Разбор части 4 показал, что сборка кадра (22,5 мкс) дороже симуляции (19,0 мкс) — и вся она
умножалась на число игроков. Отсюда следовала оптимизация: считать кадр один раз на комнату.

**Что сделало её возможной — устройство игры, а не техника.** Подземелье это инстанс одной
пати, все игроки заодно, и миникарта у них общая по замыслу. Арена PvP умещается примерно
в два экрана, карта видна целиком. Город — тоже инстанс пати. Значит вид мира у всех
в комнате ОДИН, и персональный вид никому не нужен.

Поэтому область интереса (Ф1.2) выключена по умолчанию — не откачена, а именно выключена:
`DM_AOI_RADIUS=1000` возвращает персональный вид, механизм цел и покрыт тестами. Возвращать
его понадобится там, где рядом окажутся НЕ союзники: публичная зона, большая арена со стенами,
открытый мир.

Теперь снимок, контрольная сумма, дельта и бинарный кадр считаются один раз на комнату,
и всем уходит один буфер. Персональным остался только момент первого кадра: подключившийся
посреди забега получает ПОЛНЫЙ кадр того же тика, от которого посчитана общая дельта, и со
следующего тика идёт в общем потоке.

| Сценарий | Было | Стало | На потолке |
|---|---|---|---|
| Соло (каждый в своей комнате) | 150 | **250** (+67 %) | CPU 103 %, RTT 17 мс, 8,0 КБ/с |
| Пати по 4 | 300 | **400** (+33 %) | CPU 108 %, RTT 19 мс, 10,5 КБ/с |

Расхождений дельт: 196 975 и 318 543 сверки, ноль в обоих прогонах — при том, что четверо
в комнате применяют ОДИН поток дельт, а подключались они вразнобой.

### Неожиданное: выиграло не то, что чинили

Соло выиграло БОЛЬШЕ (+67 %), хотя делить там не с кем — в комнате один клиент. Значит дело
не в общей дельте, а в том, что вместе с ней ушла ПЕРСОНАЛЬНАЯ ФИЛЬТРАЦИЯ: `viewFor` создавал
на каждого клиента каждый кадр три новых массива и проходил по всем монстрам. Это стоило
дороже, чем подорожавший кадр.

Арифметика по общей дельте сходится, но объясняет мало: 300 игроков × 20 Гц × 22,5 мкс ≈ 13 %
ядра до и ~3 % после, то есть около 10 пунктов экономии; измерено 96 → 89, то есть 7. Всё
остальное держит то, что **разделить между игроками нельзя в принципе**: отправка каждому
в свой сокет и разбор входящего ввода. На 400 игроках это 8 000 отправок и 12 000 приёмов
в секунду — линейно по игрокам, и лечится только вторым процессом (Ф4).

### Цена: трафик вырос

Клиент теперь получает весь этаж, а не полтора экрана: 6,2 → 8,0 КБ/с соло и 9,4 → 10,5 КБ/с
в пати. Против исходных 228 КБ/с это по-прежнему в 22 раза меньше, а по замыслу игры общая
карта у пати — не потеря, а нужное поведение.

⚠ ПРОВЕРИТЬ ГЛАЗАМИ: клиент теперь рисует всех монстров этажа, а не ближних. На стенде это
незаметно (боты не рисуют), а на живом 3D-клиенте стоит убедиться, что оконное отсечение
справляется и кадры не проседают.

## ФИНАЛЬНЫЙ ЗАМЕР: сколько игроков держит процесс

Прежний стенд отвечал на вопрос «держит ли сервер N ботов». Он остаётся регрессионным гейтом,
но потолка не показывает. `npm run bench:ramp` добавляет ботов ступенями, пока держатся ворота
качества, — последняя удержавшаяся ступень и есть ёмкость.

Три вещи, которых у прежнего стенда не было:
1. **Боты в отдельных процессах.** Раньше все боты крутились рядом с сервером в одном процессе.
   На сотне это ещё честно, дальше — нет: прогон на 400 ботах однажды дал одинаковые 11 кадров/с
   у двух РАЗНЫХ транспортов, то есть мерил сам себя.
2. **Защита от самообмана.** Каждый рабочий сообщает свой расход CPU. Если стенд с сервером
   заняли машину, ступень помечается НЕДОСТОВЕРНОЙ и поиск останавливается с честной оговоркой.
3. **Частота симуляции в воротах.** Не только кадры и RTT, но и `dm_tick_hz` (ниже 28 — мир идёт
   в слоу-мо). Именно этот симптом однажды проглядели: при 200 игроках было 13,9 Гц вместо 30.

CPU сервера берётся не из логов, а из его же `/metrics` — по разнице счётчиков процессорного
времени между двумя сборками.

### Что упёрлось: ОДНО ЯДРО, а не алгоритмы

При 200 сольных ботах процесс съел 103 % ядра. Node однопоточен, значит это физический потолок
одного процесса — и ровно про него написана Ф4 (кластер по ядрам). На машине их шестнадцать,
и пятнадцать простаивают.

### Симуляция больше НЕ узкое место

`npm run bench:tick` на боевом ядре: тик **18,97 мкс**, сборка кадра **22,54 мкс**, итого
**41,5 мкс на комнату** → теоретически ~800 комнат на ядро. Фактически удержали 150. Разница
в пять раз — это всё, что лежит ВНЕ симуляции: персональный вид на каждого клиента (область
интереса + дельта + кодек), отправка, сборка мусора, автосейвы.

Отсюда прямой вывод для следующей оптимизации: **дальше надо удешевлять сборку персонального
кадра, а не симуляцию.** Сейчас каждый клиент получает свой вид, посчитанный с нуля; соседи
в одной комнате пересчитывают почти одно и то же.

Контрольная сумма у всех четырёх — `36973272`, то есть работа идентична.

мкс на тик. Два вывода:

* JSON-кадр стоит дороже всей симуляции: +33 мкс к тику и 9971 Б против 185 Б. Это подтверждает

после этого замера только укрепилось.

## Ф3 группа B: телеметрия, детектор аномалий, потолок аккаунтов

### Телеметрия поведения (Ф3.2)

Одна строка на игровую сессию (`play_sessions`): килы, золото, опыт, подборы, смерти, этажи,
число действий и — главное — **средний интервал между действиями и его разброс**. Разброс
считается алгоритмом Уэлфорда, одним проходом в трёх числах, без хранения истории.

Две неочевидные детали:
* пишем не только при выходе, но и **раз в пять минут** (`DM_TELEMETRY_FLUSH_MS`). Сигнатура
  «шестнадцать часов без пауз» на строке, которая пишется в конце сессии, не сработает никогда:
  бот из игры не выходит;
* интервалы длиннее минуты в разброс не идут — это пауза (отошёл, читает описание), она
  раздула бы разброс и спрятала ровно то, что мы ищем.

Проверено на стенде: 60 ботов за 45 секунд дали 64 сессии, 60 килов, 353 золота, 1156 опыта,
3267 действий.

### Детектор аномалий (Ф3.3): помечает, но не банит

`npm run watch:anomalies` — читает телеметрию и печатает очередь на разбор. Ничего не меняет
и никого не наказывает; это принципиально, а не «руки не дошли». Один ложный бан стоит дороже
десяти пропущенных ботов: бот теряет аккаунт, а честный игрок — доверие, и рассказывает об
этом всем.

| Сигнатура | Вес | Что означает |
|---|---|---|
| `marathon` | 2 | сессия ≥ 16 часов подряд |
| `metronome` | 3 | разброс интервала < 25 мс при ≥ 200 действиях |
| `ip-swarm` | 1 | ≥ 4 аккаунтов с одного адреса |
| `value-outlier` | 2 | ценность в час ≥ 5 медиан популяции |

Разные сигнатуры складываются, одна и та же повторно — нет: пять марафонских сессий это тот же
самый сигнал, а не пять поводов. Сравнение идёт от **медианы**, а не от среднего — среднее
сдвигают сами же нарушители. Пороги вынесены в `Thresholds` и меняются без правки кода.

**Замер, который стоит знать: наши собственные боты сигнатуру `metronome` НЕ вызывают** —
их разброс 39 мс против порога 25. И это не промах порога, а свойство игры: темп атак задаёт
СЕРВЕР (замах и откат), поэтому и человек, и бот, бьющие непрерывно, имеют почти одинаковый
ритм. В нашей игре ритм атак — слабый признак; сильные это длительность сессии, ценность в час
и совпадения между аккаунтами. Пороги вообще нельзя считать проверенными, пока нет живой
популяции: сейчас они выставлены с запасом в сторону «лучше пропустить, чем оболгать».

Из плана сознательно НЕ реализовано: сравнение маршрутов по этажу между аккаунтами. Оно
требует хранить траектории — это отдельный объём данных, и браться за него имеет смысл, когда
будет на ком проверять.

### Экономические предохранители (Ф3.5): что применимо, а что нет

Честно про объём: половине пунктов плана в нашей игре нечего защищать.

* «потолок передачи ценности между аккаунтами» — **передачи между аккаунтами не существует**:
  торговли нет, сундук привязан к аккаунту, а леджер Ф2 отклоняет запись целиком, если вещь
  пришла с чужого аккаунта. Это строже любого лимита;
* «задержка перед выводом свежедобытого в сундук» — сундук и так недоступен вне города (Ф3.1),
  а внутри аккаунта перекладывание не даёт ничего; задержка мешала бы только честному игроку;
* «лимит на число персонажей с одного адреса» — **сделано** в виде суточного потолка на новые
  аккаунты с одного IP (`DM_MAX_ACCOUNTS_PER_IP`, по умолчанию 5). Лимит частоты (Ф0.5) ловит
  шквал за минуту, но завести двадцать аккаунтов не спеша он не мешает — а ферму разводят
  именно так.

Проверено на боевой конфигурации: при потолке 67 и 65 уже существующих аккаунтах два запроса
проходят, третий получает 429. На стенде потолок выключается тем же `DM_RATELIMIT=off` — без
этого он резал сам стенд (в первом прогоне дошли 5 ботов из 60).

Замер после группы, 100 ботов, `--hz=60`: RTT 5,2 мс, CPU 47–56 %, 20,0 кадров мира, 0 ошибок,
60 000 сверок дельт без расхождений. 1125 тестов.

## Ф3 группа A: место команды, повтор команды, гигиена сессий

### Найденная дыра: сундук и лавка работали из подземелья

Команды города не были ограничены по месту. Изменённый клиент мог прямо с этажа продать лут,
перековать вещь и — главное — открыть общий сундук и переложить туда добычу. Последнее не
мелочь: смысл забега в том, что добытое надо ДОНЕСТИ до города, а сундук посреди подземелья
обнуляет цену смерти и даёт удобную дорожку для мула.

Граница проведена по тому, **что клиент и так запрещает**: лавка, кузница и сундук открываются
только подходом к объекту города, значит честному игроку запрет не мешает. А дерево скилов,
мастерство и журнал квестов открываются горячей клавишей где угодно — запрети мы их вне города,
сломали бы игру тому, кто поднял уровень на этаже. Сервер здесь не вводит новое правило,
а начинает соблюдать существующее (`net/guard.ts`, карта мест в одном месте).

Проверка на живом сервере — `npm run poc:cheat`: из подземелья приходит 2 отказа
«только в городе», кадров сундука — ноль.

### Чего в этой задаче делать НЕ пришлось

План предполагал проверки движения — «дистанция за тик не больше максимальной скорости».
Проверять оказалось нечего: клиент не присылает позицию вообще. Он шлёт направление, сервер
нормализует вектор (Ф0.6), берёт скорость из своих статов и сам двигает игрока. Телепорт и
спидхак через ввод невозможны по построению; добавлять сюда проверку было бы имитацией работы.

### Повтор команды (Ф2.5)

Клиент нумерует команды, сервер помнит последние 64 номера на соединение. При обрыве связи
честный клиент повторяет последнюю команду — а повтор «купить» это лишняя вещь за лишнее
золото. Повтор отбрасывается, но сейв клиенту дошлётся: он повторял как раз потому, что не
знал, дошло ли. Клиент без нумерации (старая вкладка) обслуживается как раньше.

Живая проверка считает по счётчику сервера `dm_cmd_duplicate_total`: три команды, из них две
с одинаковым номером → отброшен ровно один повтор.

### Гигиена сессий (Ф3.4)

* срок токена 30 дней → **7 дней, но скользящих**: каждое использование отодвигает срок, поэтому
  играющий не разлогинивается никогда, а брошенный токен протухает за неделю (продление не чаще
  раза в сутки, чтобы не писать в базу на каждый вход в комнату);
* `POST /api/logout-all` — отзыв всех сессий пользователя. Единственный способ обезвредить
  уведённый токен, не дожидаясь срока; сюда же должна звать смена пароля, когда она появится;
* в проде без `DM_BEHIND_TLS=1` сервер громко предупреждает, что TLS перед ним не подтверждён.
  Определить наличие https-прокси изнутри процесса нельзя, поэтому требуем явного подтверждения,
  а не тихой уверенности.

Замер после группы, 100 ботов, `--hz=60`: RTT 6,3 мс, CPU 37–45 %, 20,0 кадров мира, 0 ошибок,
60 009 сверок дельт без расхождений. 1114 тестов.

## Ф2: предметы как данные — леджер и журнал происхождения

У каждой вещи теперь есть строка в `items` (одна вещь — одно место) и неперезаписываемая
история в `item_events`. Идентификатор — UUIDv7 вместо прежнего `it_<время>_<счётчик>`:
счётчик обнулялся на рестарте, то есть id не был уникальным, а на нём должен держаться
весь журнал.

**Как это устроено — проекция, а не переписывание экономики.** Вещи по-прежнему лежат в
сейве персонажа и в сундуке. При каждой записи сейва мы сравниваем «что есть» с «что
записано» и пишем РАЗНИЦУ переходами — в той же транзакции, что и сам сейв. Поэтому леджер
и сейв не могут разъехаться: либо записано и то и другое, либо ничего.

Что это даёт на практике:
* **вещь не может быть в двух местах** — в леджере для этого просто нет места;
* **приход вещи из чужого аккаунта отклоняет запись целиком.** Торговли в игре нет, значит
  смена аккаунта — это либо дюп, либо наша ошибка. Проверено тестом: сейв не сохраняется,
  версия не растёт, вещь остаётся у законного владельца;
* **журнал нельзя переписать** — запрещает триггер в самой базе, а не наш код;
* **отзыв вещи держится и по живому серверу**: отозванная вещь помечается в леджере, и
  автосейв игрока не может вписать её обратно.

Инструменты:

```bash
npm run items:audit                                  # сверка сейвов с леджером
npm run items:history -- --id=<uuid>                 # вся жизнь одной вещи
npm run items:revoke -- --id=<uuid> --reason="дюп"   # точечный отзыв
```

Замер, 100 ботов, `--hz=60`: RTT 3,5 мс, CPU 48–52 %, кадров мира 20,0, 0 ошибок,
60 006 сверок дельт без расхождений. Проекция на цену тика не влияет: она работает раз в
10 секунд на игрока, а не в тике. Аудит после прогона: 655 вещей в леджере, 712 записей в
журнале, расхождений сейвов с леджером — ноль.

Чего журнал НЕ знает: причину перехода он видит лишь настолько, насколько её передали
(`reason`), и смотрит на мир с точностью до автосейва — между сохранениями истина в памяти.

## Ф2 (Postgres вместо SQLite): производительность не изменилась

Замер подряд, 100 ботов, `--hz=60`, одна машина, один сеанс:

| Хранилище | RTT медиана | CPU процесса | кадров мира/с |
|---|---|---|---|
| SQLite (коммит `be1cbdc`) | 6,8 мс | 46–74 % | 20,0 |
| Postgres | 6,4 мс | 53–77 % | 20,0 |

Разница в пределах разброса. Переезд делался не ради скорости, а ради того, что на SQLite
построить нельзя: предметы отдельными строками с журналом происхождения, общий замок и
несколько игровых нод на одной базе (Ф4).

Заодно это подтвердило старое правило про замеры: прежние «3,4 мс» из прогона получасом
раньше в сравнение НЕ годились — контроль на том же коде дал 6,8 мс. Машина за сеанс греется,
сравнивать можно только прогоны подряд.

### Что поменялось в коде, кроме драйвера

Доступ к данным стал **асинхронным**, и это не косметика:
* `RoomManager` получил ОЧЕРЕДЬ КАДРОВ НА СОЕДИНЕНИЕ. Иначе два кадра одного игрока шли бы
  внахлёст: второй `join` начинал бы работу, пока первый ещё читает сейв, и игрок оказался бы
  в двух комнатах — тот самый дюп, который мы закрыли в Ф0.3, вернулся бы с другой стороны.
  Мимо очереди пропущены `ping` и `input`: они не ходят в базу, зато идут десятками в секунду.
* `Room.persist` получил ОЧЕРЕДЬ НА ПЕРСОНАЖА. Версия сейва — счётчик, который читают,
  предъявляют и обновляют; две записи внахлёст предъявили бы одну версию, и вторая потеряла
  бы свои изменения.
* Остановка сервера теперь ЖДЁТ записи сейвов (с предохранителем на 5 с). Раньше запись была
  синхронной и `process.exit` сразу после неё был безопасен.

### Как поднять базу локально

На машине разработки PostgreSQL 17 стоит службой Windows (`postgresql-x64-17`, автозапуск,
порт 5432). Развернуть с нуля на другой машине — `packages/server/data/setup-postgres.ps1`
(от администратора): ставит сервер, заводит пользователя `dm` и базы `dungeon` /
`dungeon_test`, заливает дамп авторского контента.

Вручную то же самое:

```bash
psql -U postgres -c "CREATE USER dm PASSWORD 'dmpass'" -c "CREATE DATABASE dungeon OWNER dm" -c "CREATE DATABASE dungeon_test OWNER dm"
```

Адрес — `DM_PG`; в разработке по умолчанию `postgresql://dm:dmpass@127.0.0.1:5432/dungeon`,
стенд и тесты ходят в `dungeon_test`. Схема создаётся сама при старте. Разовый перенос
авторского контента со старой SQLite — `npm run db:import`.

## Ф1.6 (транспорт uWebSockets.js): выигрыша НЕТ, и вот почему

Замер, 100 ботов, `--hz=60`, два прогона подряд на одной машине:

| Транспорт | CPU процесса | RTT медиана | RSS |
|---|---|---|---|
| `ws` (по умолчанию) | 41–50 % | 3,4 мс | 389 МБ |
| `uws` (`DM_WS=uws`) | 46–50 % | 3,3 мс | 372 МБ |

Разницы нет. Это **не** противоречит транспортному бенчу, где uWS выигрывал около четверти
CPU: там кадр был 1500 Б × 30 Гц на клиента, и вся работа процесса была работой транспорта.
После Ф1.3+Ф1.2+Ф1.4 наш кадр — около 350 Б × 20 Гц, а CPU держит симуляция. Сделать дешевле
то, чего почти не осталось, нельзя. **Оценка «−23 % CPU» устарела ровно в тот момент, когда
мы закрыли Ф1.4** — и это довод считать, а не переносить числа из чужого замера.

Прогоны на 400 ботах на этой машине НЕДОСТОВЕРНЫ: при `--hz=10` оба транспорта дают
одинаковые 11 кадров/с и одинаковый лаг цикла ~55 мс, то есть меряется уже стенд (400 ботов
на тех же 16 ядрах), а не сервер. Такие числа в выводы не берём.

Что при этом сделано и остаётся в коде:
* `net/conn.ts` — интерфейс `GameConn`. Игровая логика больше НЕ знает про библиотеку `ws`:
  ей нужны только «отправить», «закрыть», «открыто ли», «вот кадр», «соединение закрылось».
* `net/wsServer.ts` — транспорт по умолчанию (`ws`), рукопожатие и heartbeat.
* `net/uwsServer.ts` — транспорт на uWebSockets.js за флагом `DM_WS=uws`. uWS не встаёт поверх
  `node:http`, поэтому игровой порт занимает он, express переезжает на порт петли
  (`DM_HTTP_PORT`, по умолчанию `PORT+1`), а всё, кроме `/ws`, uWS переправляет ему. Снаружи
  ничего не меняется: тот же порт, тот же `/ws`, тот же `/api`. Пакет опциональный — если он
  не собран под платформу, сервер пишет предупреждение и поднимается на `ws`.

Оба транспорта проверены `npm run poc:flood`: все три лимита частоты срабатывают одинаково,
то есть настоящий адрес клиента переживает прокси (иначе лимиты считались бы по `127.0.0.1`
и один флудер отрезал бы всех).

Флаг оставлен ВЫКЛЮЧЕННЫМ. Смысл в нём появится там, где вырастет доля транспорта: много
соединений на процесс при дешёвой симуляции — но решать это надо новым замером на боевом
железе, а не этой таблицей.

### Отрицательное HP: где обязан стоять зажим

Кадр пишет пулы (HP/мана/выносливость) БЕЗЗНАКОВЫМИ. При добивании монстра `hp` уходит в
минус — перебор урона, — и кодек зажимал минус в ноль у себя. Сервер считал контрольную
сумму по −2, клиент восстанавливал 0: 5–6 % расхождений под нагрузкой и РОВНО НОЛЬ на одном
боте (соло-бот почти никого не добивает) и в офлайн-тестах.

Правило, которое из этого следует и записано в шапке `wire.ts`: **квантование и зажим делает
`serializeWorld`, а не кодек.** В снапшот кладутся уже те самые значения, которые переживут
провод, — тогда «истина сервера» и «то, что видит клиент» совпадают по построению, а не по
удаче. Регрессия закрыта тестом в `wire.test.ts`.

Диагностика, если сверки снова разойдутся: `DM_WIRE_VERIFY=1` на сервере заставляет его слать
рядом с бинарным кадром эталонный JSON того же тика, а `npm run poc:delta` печатает первое
разошедшееся поле поимённо.

| Показатель | Ф1.3 | + Ф1.2 |
|---|---|---|

Античит-свойство проверяется напрямую (`npm run poc:delta`): бот считает максимальную
дистанцию до монстра, который ему пришёл. При радиусе 1000 получилось **1015 пикселей**
(перебор — это гистерезис выхода) и максимум 32 монстра в кадре вместо всего этажа.

Радиус меняется через `DM_AOI_RADIUS` (0 выключает фильтрацию). Значение взято с запасом
относительно экрана — **уменьшать только с проверкой глазами**, иначе монстры начнут
появляться на виду.

ОГРАНИЧЕНИЕ, о котором надо помнить: по области интереса режутся СУЩНОСТИ (монстры, дропы,
снаряды). Сетка этажа и декор по-прежнему приезжают целиком в `FloorInit`, то есть планировка
карты клиенту известна. Знание позиций монстров закрыто, знание геометрии — нет; стриминг
геометрии по областям это отдельная работа со своей ценой на клиенте.

### Как проверяется корректность дельт — и на чём я обжёгся

Каждый кадр `snapDelta` несёт контрольную сумму мира **на том же тике**; бот применяет дельту
и сверяет сумму своей реконструкции. Первая версия проверки сравнивала реконструкцию с
БЛИЖАЙШИМ полным кадром — и давала 594 расхождения из 602 сверок. Протокол был исправен:
полный кадр приходит ВМЕСТО дельты, то есть описывает более поздний тик, и сравнивались
попросту разные моменты времени. Правильная сверка — только на одном и том же тике.

По дороге проверка всё же нашла две настоящие ошибки в дельтах:
1. `inCombat` было опциональным, а `undefined` не переживает JSON — «флаг погас» не
   передавалось, и клиент навсегда оставался в бою. Поле стало обязательным `boolean`.
2. Сигнатура дебаффов читала несуществующее поле `until` (правильное — `expiresAt`) и вдобавок
   округляла время: изменения дебаффов в дельту не попадали.
