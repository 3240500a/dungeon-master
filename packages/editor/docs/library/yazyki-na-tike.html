Node, Rust, C#, C++ на нашем тике

Один и тот же тик написан заново на четырёх языках и прогнан до совпадения контрольных сумм. Транспорт измерен на пяти стеках, включая uWebSockets.js. Оценок не осталось почти нигде — и там, где замер опроверг мою же прикидку, это сказано отдельным блоком. Короткий ответ: разница между рантаймами на этой задаче — 4 %.

Стенд: i7-11800H, 16 логич. ядер, Windows Рантаймы: Node 24.18 · .NET 10.0.11 · Rust 1.98.1 · GCC 16.2 Тик: 150 000 повторов · Транспорт: 500 клиентов, 45 с
Симуляция

C++, Rust и C# идут вровень. Node отстаёт вдвое

В бенчмарк перенесено то, что ест CPU в Room.step: поиск ближайшего игрока, конус зрения, луч видимости по Брезенхэму, ветка ИИ, движение круга с раздельным резолвом осей, расталкивание тел O(n²) и кадр наружу. Все реализации выдали контрольную сумму 27724800 и кадр 185 Б.

Ловушка, на которую я сам наступил: Rust сначала показал 14,6 мкс

Первый прогон дал Rust медленнее C#. Причина — не язык: у Rust на windows-gnu собственная реализация atan2 стоит 34,5 нс, тогда как у .NET 9,3 нс, у Node 10,2 нс, у GCC 9,5 нс. Переключение на системную математику UCRT (те же функции, что линкует g++) вернуло Rust на 10,4 мкс. Тик на 60 % состоит из тригонометрии, поэтому его скорость определяет математическая библиотека, а не компилятор.

Транспорт

Здесь Rust проигрывает Node

500 клиентов, бинарный кадр каждому, входящий поток 30 Гц с каждого, никакой игровой логики. Считается процессорное время серверного процесса, делённое на число отправленных кадров. Все стеки получили одинаковую входящую нагрузку — 15 000 сообщений в секунду.

Прямое сравнение без поправок

uWS и Rust отправили практически одинаковое число кадров — 32 464 против 32 321 за три секунды — при одинаковом входящем потоке. CPU: 21,5 % против 30,2 %. Это не нормировка и не пересчёт, а два числа из одного и того же теста: Rust-стек оказался в 1,4 раза дороже Node-стека на той же работе.

Кадр в 15 раз меньше стоит столько же

100 байт вместо 1500 не изменили ничего (Node 26,9 → 28,0 мкс; Rust 30,6 → 32,3 на тесте с 200 клиентами). Платим не за байты, а за сам факт отправки сообщения — системный вызов и обслуживание сокета. Он одинаков в любом рантайме.

И ещё: разложив замеры uWS на 30 Гц и 10 Гц, получаем ~11,8 мкс на исходящее сообщение и ~13,3 мкс на входящее. Приём стоит столько же, сколько отправка — а клиент сейчас шлёт ввод на частоте кадров (60–144 Гц). Троттлинг ввода экономит примерно столько же, сколько снижение частоты снапшотов.

Бесплатно

Одна правка, которая работает в любом языке

В ai.ts нормализация угла сделана как atan2(sin a, cos a) — три тригонометрические функции там, где хватает вычитания. Вызывается на каждого монстра каждый тик. Замена на a − 2π·round(a/2π) даёт тот же результат до бита (контрольная сумма не изменилась).

Что решает

Раз производительность одинаковая, остаются три довода

Ни один из них не про скорость.

  • Потоки против процессов. Node — одно ядро на процесс: 48-ядерная нода это 48 процессов, каждому нужен внешний реестр комнат, свой замок на персонажа и свои ~60 МБ базовой памяти. На Rust, C# и C++ та же нода — один процесс: общая таблица комнат в памяти, замок на персонажа обычным мьютексом, комнату можно перекинуть между потоками. На 100 тыс. онлайна это 240 процессов против 3.
  • Паузы сборщика мусора. В нагрузочном тесте первого отчёта цикл Node вставал на 200–300 мс — шесть потерянных тиков подряд. Лечится дисциплиной «ноль аллокаций в тике» навсегда и во всём коде. В Rust и C++ проблемы нет.
  • Где живёт единая истина формул. packages/shared общий для клиента и сервера — главный архитектурный актив проекта. Смена языка ломает это ровно настолько, насколько клиент остаётся на TypeScript. 
Где может жить одна копия боевой математики:

  Node/TS сервер  + веб-клиент TS       →  одна копия (как сейчас)
  C# сервер       + Unity-клиент C#     →  одна копия, но веб-клиент выпадает
  Rust сервер     + wasm-ядро в браузер →  одна копия + FFI-обвязка под Unity
  любой сервер    + два клиента без wasm →  две-три копии формул

Прогнали. Не то, чего я ожидал

Прошлая оценка «~10 мкс на кадр» не подтвердилась: вышло 19,9 — столько же, сколько у обычного ws. Но сам процесс при равной работе ест на 23 % меньше CPU, чем ws, и заметно меньше, чем Rust. Плюс режим publish по топикам ложится ровно на нашу схему «кадр всем в комнате», а таймеры в нём держат частоту ближе к 30 Гц.

Вдвое быстрее там, где это не решает

Симуляция действительно вдвое быстрее, GC-пауз нет, многопоточность настоящая. Но транспорт дороже Node-стеков в 1,4 раза, а весит в общей цене больше симуляции. Итог — плюс четыре процента за переписывание всей боевой математики, экономики и генерации подземелий.

Единственный кандидат с потенциалом выше Node

Тик неотличим от Rust. Kestrel для широковещательной рассылки не годится — 105 % ядра на 500 клиентов, единственный в тесте, кто вышел за одно ядро. Но если написать транспорт на System.Net.Sockets и выйти хотя бы на уровень ws, получится ~660 игроков на ядро — лучший результат в таблице. Это оценка, не замер.

Единственный сценарий переезда — и он не про скорость. Если Unity станет основным клиентом и веб отомрёт, C# даёт одну кодовую базу формул на клиент и сервер.

Формально первый, практически неотличим

Выигрыш над Rust — 3 %, над C# — 3 %. За эти три процента вы получаете гонки данных, висячие указатели и сборку, которую надо поддерживать руками.

Ответ

Правим свой сервер, а не переписываем

Второй этап вашего плана решается измеренными числами. Полное переписывание на самом быстром из кандидатов даёт +4 % к соло-игроку. Те же силы, вложенные в протокол на текущем Node, уже дали ×12,8 — с 39 игроков на ядро до 498.

  • C++, Rust и C# на симуляции различаются на 3 %. Это один класс, а не три.
  • Node на симуляции отстаёт ровно вдвое — устойчиво, во всех прогонах.
  • На транспорте Node выигрывает у Rust в 1,4 раза при одинаковой работе. Это единственная неожиданность всей серии замеров.
  • Kestrel — ловушка: C# с ним вдвое хуже Node, хотя его тик вдвое быстрее.
  • uWS полезен, но не волшебен: цена кадра та же, экономия — в общем расходе процесса.
  • Триггер для C# остаётся один: Unity стал основным клиентом, веб отмирает.
  • Триггера для Rust нет. Он держался на оценке, которую замер опроверг дважды.
