План доработки сервера: производительность и безопасность

Пять фаз, 43 задачи. Каждая — с причиной из наших замеров, файлом, где её делать, и способом проверить, что она сработала. Порядок не произвольный: сначала то, что уже ломает игру, потом то, что даёт десятикратный рост, и только потом то, что нужно на масштабе. Решение по языку принято: остаёмся на Node — переписывание давало 4 %.

Основание: замеры частей 1 и 2 этой серии Стек: Node 24 · TypeScript · Postgres · Redis · uWS Итог: 39 → ~500 игроков на ядро
Основание

Восемь правил, которые не нарушаем

Каждое куплено чьей-то аварией — нашей или чужой. Если правка противоречит правилу, не делаем правку, а не правило.

01
Сервер — единственный источник истины о предмете.

Клиент не присылает предметы, характеристики и урон никогда, ни в каком виде. Сейчас это соблюдается — не потерять при рефакторинге протокола.

02
Один персонаж — ровно одна живая сессия во всём кластере.

Не «в комнате», не «в процессе», а глобально. Нарушение этого правила — причина подтверждённого дюпа у нас и дюпа в D2R через сундук.

03
Перемещение предмета — одна транзакция и один путь в коде.

Не две записи в две таблицы. Не пять мест, каждое со своей логикой. Один moveItem, через который проходит всё: лут, магазин, кузница, сундук, торговля.

04
У предмета есть глобальный id и журнал происхождения.

Blizzard в D2 ввела уникальные id и периодически удаляла дубли. Дуперы обошли это, превращая руны в новые предметы через Куб — id менялся, дубль исчезал. Одного id мало: нужен журнал переходов, иначе дюп нельзя ни найти, ни откатить.

05
Кадр от клиента валидируется схемой, а не приводится типом.

JSON.parse(raw) as ClientFrame — это не проверка. Zod в проекте уже есть для конфигов; та же дисциплина нужна на сетевой границе.

06
Не отправляем ничего, что можно не отправлять.

Это одновременно производительность и античит: область интереса убирает 95 % трафика и вместе с ним встроенный maphack.

07
Клиент открыт. Обфускация и клиентские проверки — самообман.

Веб-клиент читается любым желающим. Всё, что нельзя проверить на сервере, считается доступным читеру.

08
Каждая правка — с числом до и после.

Нагрузочный стенд из части 1 остаётся в репозитории и гоняется на каждой фазе. Definition of Done по вашему CLAUDE.md: обновить README модуля и строку в docs/MODULE_MAP.md.

Фаза 0

Тушим то, что горит прямо сейчас

Двенадцать задач, ни одна не меняет архитектуру. После них сервер перестаёт падать на сотне игроков, мир идёт в реальном времени, а подтверждённый дюп закрыт.

Ф0 · неделя работы эффект: 39 → ~60 игроков на ядро риск: низкий откат: тривиальный
Ф0.1

Выключить perMessageDeflate

Сжатие стоит 179 мкс на кадр на каждого клиента и выполняется в пуле из четырёх потоков libuv. На сотне клиентов пул захлёбывается, очередь исходящих растёт (RSS 270 → 730 МБ), задержка уходит в 10,8 секунды. Выключение на том же тесте: RTT 8 мс, память стабильна.

Файл: packages/server/src/net/wsServer.ts:14–19. Правка на одну строку.

Проверка 100 ботов, RTT медиана < 20 мс, RSS не растёт за 5 минут
Ф0.2

Один планировщик тиков вместо setInterval на комнату

Node переставляет интервал после колбэка, поэтому занятость цикла копится в дрейф: при 200 игроках мир шёл 13,9 Гц вместо 30, то есть игровое время текло в 46 % от реального — слоу-мо, а не лаг. Плюс все таймеры заведены почти одновременно и бьют одной пачкой.

Делаем: один таймер на процесс, аккумулятор фиксированного шага, комнаты разложены по корзинам (bucket по индексу), обработка с ограничением догоняющих шагов. Файл: packages/server/src/net/room.ts:89 → новый net/scheduler.ts.

Проверка снапшотов ровно 30/с при 100 ботах; loop p99 < 20 мс
Ф0.3

Глобальный замок на персонажа + версия сейва

Подтверждено PoC: один charId заходит в две комнаты одновременно (3SU0 и RQFC), обе держат свою копию сейва и пишут её раз в 10 секунд. Схема дюпа ровно та же, что в D2R: положил вещь в сундук из первой сессии, вторая через 10 секунд сохраняет устаревший инвентарь — вещь есть и там, и там.

Делаем два независимых барьера. Первый — реестр живых сессий charId → соединение в RoomManager: второй вход выселяет первый. Второй — колонка version у персонажа и запись через UPDATE … WHERE version = ?: устаревшая запись просто не проходит. Файлы: net/roomManager.ts:108–120, db/db.ts.

Проверка PoC-скрипт из части 1 получает error на второй вход; тест на CAS-конфликт
Ф0.4

Перемещение предмета — в одной транзакции

Сейв персонажа и сундук аккаунта — две строки в двух таблицах, пишутся раздельно и без транзакции. Падение процесса между записями даёт дубль или потерю. В accountStash.ts это даже задокументировано как «кэша нет намеренно, last-writer-wins» — на одном процессе терпимо, на нескольких смертельно.

Пока БД — SQLite, оборачиваем оба put в одну явную транзакцию. Настоящее решение — Ф2.2. Файлы: net/accountStash.ts, db/db.ts.

Проверка тест: kill процесса между двумя записями → предмет ровно в одном месте
Ф0.5

Лимиты частоты на всё, что снаружи

Сейчас лимитов нет нигде. /api/register и /api/login открыты без капчи, а каждая попытка — это scryptSync (десятки мегабайт и ~100 мс): один скрипт кладёт сервер, не открыв ни одного WebSocket. Каждый join без кода создаёт новую комнату с таймером — тысяча join'ов кладёт процесс.

Ставим: токен-бакет на IP для register/login (плюс задержка при серии неудач), лимит комнат на аккаунт и на IP, лимит кадров ws на соединение с разрывом при превышении, глобальный потолок соединений с очередью.

Проверка скрипт-флудер: 1000 запросов/с → 429 без роста CPU выше 20 %
Ф0.6

Валидация кадров схемой на сетевой границе

JSON.parse(raw) as ClientFrame пропускает в игровое ядро NaN, Infinity, отрицательные индексы и произвольные строки. Zod в проекте уже есть — переиспользуем. Разбор один раз, на входе, с отбрасыванием кадра и счётчиком нарушений на соединение.

Файл: net/roomManager.ts:56 → новый shared/session/netSchemas.ts.

Проверка фаззер шлёт мусорные кадры 60 с → сервер жив, позиции без NaN
Ф0.7

Кэшировать /api/config

structuredClone всего конфига плюс JSON.stringify на каждый запрос — 8,58 мс блокировки цикла и 436 КБ тела, без кэша и ETag. Один вход игрока съедает четверть тикового бюджета; сто входов в секунду — 86 % ядра на один роут.

Сериализуем и сжимаем один раз при старте и при правке из редактора, отдаём готовый буфер с ETag. Файлы: server/src/index.ts, shared/config/registry.ts:55.

Проверка 100 параллельных GET → loop p99 не растёт; второй запрос отдаёт 304
Ф0.8

Троттлинг ввода до частоты тика

sendInput() зовётся из рендер-цикла, то есть 60–144 раза в секунду, и каждый кадр — JSON.parse на сервере. Полезны из них 30: setInput просто перезаписывает последний. Приём стоит ~13,3 мкс на сообщение — столько же, сколько отправка, так что экономия здесь равна экономии на снапшотах.

Клиент шлёт не чаще тика (online3d.ts:1033), сервер жёстко режет лишнее и считает нарушителей.

Проверка счётчик входящих на сервере ≈ 30·N, а не 60–144·N
Ф0.9

Статику и ассеты — прочь с игрового процесса

7,4 МБ клиентского бандла и 31 МБ GLB идут через express.static того же процесса, что крутит тики. Один холодный заход — десятки мегабайт с игрового ядра.

Минимум — отдельный процесс на другом порту. Правильно — CDN с длинным кэшем и хешами в именах файлов.

Проверка игровой процесс не отдаёт ни одного байта статики (лог доступа пуст)
Ф0.10

SQLite в WAL, автосейвы пачками и вразбивку

node:sqlite блокирующий, автосейв каждые 10 с на комнату плюс запись на вход, левелап и смену этажа. Отсюда выбросы loop max в 200–300 мс — шесть потерянных тиков подряд.

Включаем WAL, объединяем записи цикла в одну транзакцию, разносим автосейвы комнат по фазе (комната i сохраняется в свою секунду), выносим сериализацию сейва из горячего пути.

Проверка loop max < 50 мс на 100 ботах в течение 10 минут
Ф0.11

Убрать дорогую математику из горячих циклов

Math.hypot в V8 стоит 12,8 нс против 1,5 нс у sqrt(dx*dx+dy*dy) — в 8,7 раза дороже, а стоит он в каждом горячем цикле. Нормализация угла сделана как atan2(sin a, cos a) — три тригонометрические функции там, где хватает вычитания; замена на a − 2π·round(a/2π) даёт бит-в-бит тот же результат и −5 % тика.

Файлы: shared/session/ai.ts, shared/world/*, shared/session/session.ts.

Проверка npm test зелёный (результат не меняется), бенч тика −5 %
Ф0.12

Закрыть редакторские роуты ролью, а не переменной среды

NODE_ENV !== 'production' — единственное, что отделяет постороннего от /api/dev/config (переписать баланс сервера), /api/dev/assets/:id (залить 64 МБ файл) и /api/dev/characters (прочитать всех персонажей всех игроков). Одна ошибка в деплое — и это открыто наружу.

Роль admin у пользователя, проверка на каждом dev-роуте, отдельный лог всех правок конфига с указанием кто и что.

Проверка тест: обычный токен и отсутствие токена → 403 на всех /api/dev/*
Фаза 1

Протокол: перестать возить весь мир каждому

Это фаза с наибольшей отдачей во всём плане: рост в десять раз по игрокам на ядро и в двадцать по трафику. Она же закрывает maphack — не как отдельную задачу, а как побочный эффект.

Ф1 · 2–4 недели эффект: ~60 → ~500 игроков на ядро трафик: 180 → 6–10 КБ/с риск: средний, нужна версия протокола
Ф1.1

Вынести статику из кадра

Сейчас в каждом снапшоте на каждого игрока едут name, classId, maxHp, weaponKey, armorModels — данные, которые не меняются между этажами. Это самая дешёвая правка фазы: отправлять один раз при входе и при изменении экипировки.

Файл: shared/session/serialize.ts:38, новый кадр peerInfo.

Проверка размер снапшота падает примерно вдвое без потери картинки
Ф1.2

Область интереса (AoI)

Клиент получает только то, что рядом — примерно полтора экрана плюс запас на скорость движения. Реализация: равномерная сетка ячеек по этажу, у каждого игрока набор видимых сущностей, события входа и выхода из области.

Это же и есть лечение maphack. Сегодня FloorInit отдаёт весь этаж целиком: сетку, весь декор, всех монстров с характеристиками — то есть карта у читера есть по построению, и никакой обфускацией это не закрыть, потому что клиент открыт. После AoI сервер физически не отправляет того, чего игрок не видит.

Проверка бот на одном конце карты не получает ни одной сущности с другого конца
Ф1.3

Дельта-снапшоты

Шлём только изменившиеся поля изменившихся сущностей. Схема: сервер держит на клиента последний подтверждённый кадр, клиент подтверждает номер, дельта считается от него; при потере подтверждений — полный кадр.

В бенчмарке дельта-кадр на 60 монстров занял 185 байт против 9 971 байт у полного JSON-снапшота той же сцены.

Проверка средний кадр < 500 Б в бою; полный кадр не чаще раза в 2 с
Ф1.4

Бинарный кадр вместо JSON

JSON-кадр стоит +40 мкс на тик (и, что показательно, в C# он ещё дороже — так что это не проблема языка). Координаты в int16 в долях тайла, состояния битами, строки — только в редких командах.

Схему кадра описываем один раз в shared и генерируем из неё кодек для клиента и сервера — чтобы не разъехались.

Проверка round-trip тест кодека на случайных мирах; тик −40 мкс
Ф1.5

Снапшоты 20 Гц, симуляция 30 Гц

Отправка стоит ~19 мкс на кадр независимо от его размера — значит цена линейна по числу кадров. Снижение с 30 до 20 Гц снимает треть транспорта; плавность добирается интерполяцией на клиенте, которая там уже есть.

Проверка глазами на 3D-клиенте: движение монстров без рывков при 20 Гц
Ф1.6

Перевести транспорт на uWebSockets.js

Замер: при одинаковой работе процесс на uWS ест 21,5 % ядра против 28,0 % у ws — на 23 % меньше. Цена кадра та же (19,9 против 19,2 мкс), так что чуда не ждём, но запас по CPU реальный, а режим publish по топикам ложится ровно на схему «кадр всем в комнате».

Версия v20.69.0, бинарь под ABI 137 (Node 24) в пакете есть.

Проверка 500 ботов: CPU процесса ниже, чем на ws, при той же частоте
Ф1.7

Метрики протокола в рантайме

Чтобы следующая правка тоже была с числом: счётчики байт на игрока, кадров в секунду, размера дельты, времени тика и лага цикла — в /metrics в формате Prometheus. Без этого фаза 1 непроверяема на живых игроках.

Проверка дашборд показывает КБ/с на игрока и тикрейт по каждой ноде

Про версию протокола

PROTOCOL_VERSION в netTypes.ts уже есть — поднять и заставить клиент проверять при joined, иначе после деплоя старые вкладки будут молча ломаться. Клиент старой версии должен получать понятное «обновите страницу», а не пустой экран.

Фаза 2

Предметы как данные: фундамент против дюпа

Ф0.3 и Ф0.4 закрывают известные дыры. Эта фаза делает так, чтобы неизвестные дыры были обнаружимы и обратимы. Именно этого не хватало Blizzard: id у предметов был, а происхождения не было.

Ф2 · 3–5 недель эффект: дюп становится находимым и откатываемым риск: миграция данных
Ф2.1

Postgres вместо SQLite

SQLite — один файл, синхронный, в игровом потоке. На 10 тысячах комнат это 1 000 записей в секунду в один файл из 48 процессов. Postgres даёт настоящие транзакции между таблицами, конкурентный доступ и, главное, возможность спросить у данных «а нет ли у нас дублей».

Драйвер асинхронный, пул на процесс, вся работа с БД — вне тика.

Проверка 1 000 записей/с без роста loop p99; миграция сейвов без потерь на копии базы
Ф2.2

Предмет — строка в таблице, а не поле в JSON-блобе

Сейчас предмет живёт внутри JSON сейва персонажа. Пока так — найти дюп нечем: ни владельца, ни истории, ни возможности спросить «сколько в мире копий этого предмета».

Делаем таблицу items: id (UUIDv7 — сортируемый по времени), owner_type (персонаж / сундук / пол / магазин / удалён), owner_id, позиция, свойства, created_at, seed генерации. Уникальность местоположения — ограничением базы, а не соглашением в коде.

Проверка запрос «предметы с более чем одним владельцем» возвращает ноль строк
Ф2.3

Журнал переходов, только на дозапись

Таблица item_events: id предмета, откуда, куда, кто инициировал, причина (лут / покупка / продажа / крафт / сундук / смерть / торговля), метка времени, id команды. Никаких обновлений и удалений — только вставка.

Это единственное, что позволяет: доказать факт дюпа, найти всех причастных, откатить точечно, а не всей базой. Урок D2 прямой: удаление по совпадению id обходится превращением предмета в другой предмет — журнал происхождения обойти нельзя.

Проверка по журналу восстанавливается полная история любого предмета за месяц
Ф2.4

Один путь для всех перемещений

Функция transferItem(itemId, from, to, reason, cmdId) — единственная, кто двигает предметы. Внутри: транзакция, проверка что предмет действительно у from, запись новой позиции, запись в журнал. Всё остальное — лут, магазин, кузница, сундук, смерть, будущая торговля — зовёт только её.

Отраслевая практика формулирует это так: одна авторитетная дорожка изменений эксплуатируется намного тяжелее, чем пять разных.

Проверка grep по коду: ни одной записи в items мимо transferItem
Ф2.5

Идемпотентность команд

Клиент присваивает команде номер, сервер хранит последний обработанный номер на сессию. Повтор при реконнекте не выполняется дважды. Это закрывает целый класс дюпов «отправил купить, разорвал связь, отправил снова».

Проверка тест: одна команда, отправленная трижды, применяется один раз
Ф2.6

Ночной аудит инвариантов

Задача по расписанию, которая проверяет: нет предметов у двух владельцев; нет предметов без владельца; сумма золота изменилась не больше, чем позволяет сумма источников; нет аккаунтов с приростом ценности выше N сигм от медианы. Расхождение — не автобан, а алерт с выгрузкой.

Проверка подсаженный вручную дубль ловится ближайшим прогоном
Ф2.7

Инструмент точечного отката

Скрипт, который по журналу откатывает конкретные предметы и конкретных игроков на конкретный момент, не трогая остальных. Отраслевой опыт: откат всей базы карает невиновных и убивает доверие, поэтому логи надо хранить и откатывать выборочно.

Проверка учение на копии базы: откатить один аккаунт на 6 часов назад 
Схема данных, к которой идём:

Фаза 3

Античит: что невозможно, что ловим, что принимаем

Начинаем с честной модели угроз. Клиент — это открытый JavaScript в браузере: любой протокол воспроизводим, любая клиентская проверка снимается. Значит защита бывает только двух видов: сервер не даёт сделать, или сервер замечает, что сделали.

Ф3 · 2–3 недели + постоянная работа подход как у GGG: серверная сторона, без кернел-драйверов

Ф3.1

Санитарные проверки движения и действий

На сервере: пройденная за тик дистанция не больше максимальной скорости с запасом; позиция всегда в проходимой клетке; интервал между атаками не меньше кулдауна; подбор предмета только в радиусе. Нарушение — не бан, а счётчик на сессию и запись в телеметрию.

Проверка модифицированный бот-клиент с телепортом ловится за 1 тик
Ф3.2

Телеметрия поведения

Пишем в отдельное хранилище: килы в час, золото в час, опыт в час, длительность сессии, распределение интервалов между действиями, доля времени в бою, маршруты по этажу, число этажей за час, соотношение подобранного к оставленному.

Исследования по детекту ботов в RPG сходятся на шести группах признаков: частота действий, социальная активность, признаки групп золотодобытчиков, последовательности действий, схожесть между аккаунтами и траектории движения. Первые четыре мы можем считать сразу, траектории — после AoI.

Проверка дашборд: распределение «золото в час» по популяции с хвостами
Ф3.3

Детектор аномалий и процесс санкций

Правило простое: ни одна автоматика не банит сама. Детектор помечает аккаунт, человек смотрит выгрузку, решение фиксируется. Один ложный бан стоит дороже, чем десять пропущенных ботов, а автоматика по единственному сигналу ложно срабатывает гарантированно.

Сигнатуры для старта: сессии длиннее 16 часов без пауз; дисперсия интервалов между действиями ниже человеческой; одинаковые маршруты по этажу у разных аккаунтов; несколько аккаунтов с одного IP, синхронно входящие и выходящие; прирост ценности выше 99-го процентиля три дня подряд.

Проверка собственный бот из нагрузочного стенда попадает в список за час
Ф3.4

Гигиена аккаунтов и сессий

Сейчас: токен живёт 30 дней, не отзывается при смене пароля, TLS в репозитории не настроен. Делаем: срок токена короче с продлением, отзыв всех сессий при смене пароля, привязка сессии к устройству с уведомлением о новом входе, обязательный TLS с проверкой на старте, что в проде не слушаем голый ws.

Проверка смена пароля рвёт все живые соединения аккаунта
Ф3.5

Экономические предохранители

Лимиты, которые ничего не стоят честному игроку и ломают экономику ботоводу: потолок передачи ценности между аккаунтами в сутки, задержка перед выводом свежедобытого в общий сундук, лимит на число персонажей с одного IP. Когда появится торговля — она сразу с журналом и лимитами, а не потом.

Проверка сценарий «слить всё на мула» упирается в лимит

Чего мы сознательно не делаем

Никаких кернел-драйверов и агрессивных клиентских античитов — для браузерной игры это невозможно, а для будущего Unity-клиента преждевременно. GGG держит Path of Exile без кернел-драйвера на серверной детекции уже больше десяти лет, и основной удар направлен на ботов и манипуляции рынком, а не на «идеальный» бан читеров. Наш случай проще: у нас нет торговли между игроками, значит нет и главного двигателя ботоводства. Пока её нет — экономика в безопасности, и это ещё один аргумент вводить торговлю только вместе с Ф2 и Ф3.

Фаза 4

Раскладка: как занять все 64 ядра

До этой фазы весь сервер живёт в одном процессе на одном ядре. Node не умеет иначе, поэтому масштаб — это архитектура, а не настройка.

Ф4 · 4–6 недель эффект: 500 игроков на ядро → десятки тысяч на ноду нужен, когда онлайн переваливает за 400–500
Ф4.1

Разделить роли: гейтвей, игровые ноды, БД

Гейтвей держит HTTP, авторизацию, ростер, конфиг и раздаёт клиенту адрес игровой ноды. Игровые процессы занимаются только комнатами. БД отдельно. Это же прямой урок D2R: у них монолит и синглтон списка игр стали потолком, чинили дроблением на сервисы.

Проверка падение гейтвея не выкидывает игроков из подземелий
Ф4.2

Реестр состояния в Redis

Две карты: roomCode → нода и charId → живая сессия. Вторая — это тот самый глобальный замок из Ф0.3, но настоящий: он работает и между процессами. Замок с TTL и продлением, чтобы падение ноды не заперло персонажа навсегда.

Проверка вход тем же персонажем на две разные ноды → второй отказ
Ф4.3

Кластер процессов, привязка к сокетам

По процессу на ядро, комнаты закреплены за процессом на всё время жизни (комната живёт минуты — переезд не нужен). На двухсокетной машине половину процессов прибить к каждому NUMA-узлу, иначе память ходит через межпроцессорную шину.

Проверка 64 процесса, суммарный CPU растёт линейно с онлайном
Ф4.4

Очередь на вход и мягкая деградация

Гейтвей знает потолок кластера и держит очередь, вместо того чтобы принять всех и лечь. Отдельно — деградация: при перегрузке сначала снижаем частоту снапшотов до 15 Гц, потом сужаем область интереса, и только потом отказываем во входе. D2R пришли к очереди после падения на старте — дешевле подержать 500 человек в очереди, чем уронить 5 000.

Проверка нагрузка ×2 от потолка: тикрейт держится, очередь растёт, никто не выпадает
Ф4.5

Деплой без потери забегов

Слив ноды: перестать принимать новые комнаты, дождаться завершения текущих (или мягко вернуть игроков в город с сохранением), потом гасить. Механизм грейс-комнат у вас уже есть — переиспользовать его для деплоя.

Проверка деплой под нагрузкой 200 ботов без единого потерянного сейва
Ф4.6

Регионализация — задел, не работа

Пока не делаем, но закладываем: комната не выезжает за регион, аккаунты глобальные, персонажи и сундуки региональные. Это прямой урок D2R — они клали сейвы в глобальную базу слишком часто и уронили её; чинили переносом в региональные.

Проверка в схеме БД есть region, код не предполагает единственный регион
Дальше

Эксплуатация: без этого всё вышеперечисленное протухнет

Что мониторим постоянно

  • Тикрейт по нодам — падение ниже 28 Гц значит мир идёт в слоу-мо; это симптом, который мы уже один раз проглядели.
  • Лаг цикла p99 и max — выбросы выше 50 мс означают блокирующую операцию в горячем пути.
  • RTT p95 по игрокам и размер очереди исходящих — рост очереди предвещает коллапс за минуты до него.
  • КБ/с на игрока — если после Ф1 поползёт вверх, значит в кадр вернулось что-то лишнее.
  • Экономика: медиана и 99-й процентиль золота в час, число предметов в мире, скорость роста сундуков.
  • Инварианты Ф2.6 — ноль расхождений каждую ночь; любое ненулевое значение это инцидент.

Что делаем, когда дюп всё-таки нашли

  1. Не банить и не откатывать сразу. Сначала зафиксировать: выгрузить журнал по подозрительным предметам.
  2. Понять механику по журналу — какая последовательность переходов невозможна легально.
  3. Закрыть дыру в коде и выкатить. Пока не закрыта, откат бессмысленен.
  4. Найти все затронутые предметы запросом к журналу, а не глазами.
  5. Точечный откат по Ф2.7: только эти предметы, только эти аккаунты.
  6. Решение по санкциям — человеком, с сохранением выгрузки как доказательства.
  7. Разбор: почему инварианты не поймали раньше, и какой инвариант добавить.

Две развилки, где можно остановиться

После Ф1 — если онлайн не превышает пары сотен, Ф4 не нужна: одна нода на одном процессе уже держит впятеро больше. Ф2 и Ф3 при этом делать всё равно, они не про нагрузку.

Перед торговлей между игроками — вот здесь останавливаться нельзя. Пока обмена предметами нет, дюп вредит только самому дуперу, и ботоводство лишено смысла. В день, когда появится торговля, Ф2 и Ф3 должны быть уже сделаны, иначе экономику разберут за неделю.
