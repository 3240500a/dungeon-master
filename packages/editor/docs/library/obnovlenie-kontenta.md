# Обновление контента без пересборки клиента

Oct 7, 2026 · план стадии с решениями владельца по комментариям (11 пунктов, таблица «Решения за тобой»)

Steam раздаёт клиент вместе с базовым контентом — снимком на момент выпуска клиента, для нас бесплатно. Всё, что добавлено или изменено после, — модели, материалы, текстуры, звуки, конфиг и анимации — приходит с нашего CDN. При запуске клиент сверяет один короткий номер версии: совпал — ничего не качает; изменился — докачивает только новые файлы, один раз, и хранит их у себя.

## Как это работает

**Версия совпала — ноль скачиваний; нет — только новые файлы.** Что делает клиент на каждом запуске:

1. **Запуск игры.**
2. **Указатель версии** — запрос к нашему серверу, сотни байт.
3. **Клиент старше `minClient`?** Да — экран «Обновите игру в Steam» (Steam докачает клиент сам). Нет — дальше.
4. **Версия совпала?** Да — сразу **вход в игру**. Нет — дальше.
5. **Манифест релиза** — проверка подписи и хэша.
6. **Разница с диском** — показать размер: «Обновление 38 МБ».
7. **Докачка стартового набора** — 4–8 потоков; `.part` → хэш → файл.
8. **Переключение версии** — `state.json` одной операцией.
9. **Вход в игру** — всё читается с диска.

В фоне с главного меню: герои, город, биомы, музыка — к подземелью всё готово.

В обычный день срабатывает правая ветка: версия совпала, и игра стартует с диска после одного запроса.

## Цели и правила

Добавил или поменял контент — игроки получили его при следующем запуске, без нового клиента в Steam. Новый клиент нужен только при смене кода.

- **Одна сверка на запуск.** Клиент спрашивает у сервера один номер версии. Совпал — ноль скачиваний, игра стартует сразу.
- **Только разница.** Изменился — клиент качает лишь новые файлы. Неизменённое не качается повторно никогда.
- **Один раз.** Скачанное лежит на диске игрока и проверяется хэшем. Обрыв связи не портит кэш.
- **Базовый контент в Steam.** Установщик несёт код и снимок контента на момент выпуска клиента, его раздаёт Steam. С нашего CDN приходят только изменения после этого снимка.
- **Один источник правды.** Сервер, клиент, редактор конфигов и поз-редактор видят одну и ту же версию контента.
- **Откат одной кнопкой.** Плохой выпуск откатывается переключением указателя, без перезаливки.

Чего не делаем:

- **Отдельный лаунчер-exe.** Steam просит его не делать, Steam Deck за него снижает оценку. Обновление идёт внутри игры.
- **Код через сервер.** Новый код — только новый клиент через Steam. Так устроен движок, и так безопаснее.
- **Подмена контента посреди боя.** Новое применяется на старте или на экране загрузки.

## Что сейчас

Каждый запуск клиент заново качает около 32 МБ: кэша на диске нет, номера версий живут только в памяти. Замер на локальном сервере:

| Что качается | Размер | В gzip | Как сейчас |
| --- | --- | --- | --- |
| Конфиг `/api/config` | 0.75 МБ | 0.09 МБ | целиком на каждом запуске, ETag только в памяти |
| Анимации `/api/pose` | 6.65 МБ | 0.70 МБ | целиком, без проверки версии; правка одного клипа = вся библиотека |
| Модели (GLB) | 13.6 МБ | — | по имени `/assets/<id>.glb`, перезаливка перезаписывает файл |
| Текстуры (PNG) | 11.4 МБ | — | сжимаются в игре на главном потоке при каждом запуске |
| Кованое оружие | по запросу | — | свой ETag, кэш только в памяти |

Почему так нельзя выпускать:

- **На проде нельзя ничего опубликовать.** Ручки редакторов (`/api/dev/*`) в продакшене отвечают 403. Контент прода меняется только деплоем из git.
- **Файлы перезаписываются под тем же именем.** С CDN или кэшем игрок до часа видит старое; Unity перезалитую текстуру вообще не замечает.
- **Модели рыцаря не в git и не в бэкапе.** Деплой их не привезёт.
- **Версии разрознены.** Есть ETag конфига, ревизии поз (`/api/pose/rev`), версия протокола и `cfgRev` в рукопожатии, но одного номера на всё нет. Позы и арт рукопожатие не проверяет.
- **Визуальная правка закрывает кузницу.** `cfgRev` считается по всем таблицам: поменял текстуру — команды кузницы получают отказ «Цена изменилась».
- **Сервер не сжимает ответы.** Анимации в gzip весят в 9.5 раза меньше.
- **Вес установщика — шейдеры, а не арт.** Тестовая сборка 417 МБ, из них шейдеры 281 МБ; шейдеры glTFast — около 67 МБ.
- **Прод на сборке от 08.08,** Unity к нему ни разу не подключали. Новая система будет и первым большим деплоем.

Что уже годится как основа: ETag и 304, ревизии поз по ключам, синхронизация версии конфига между процессами через базу и защита от затирания (409 по `baseRev`).

## Как делают другие

Почти все серьёзные игры обновляются двумя слоями: Steam несёт код и редкие крупные релизы, свой CDN — контент между ними. На старте клиент сверяет маленький указатель версии, а файлы лежат по хэшам и никогда не перезаписываются.

| Игра | Как доставляется контент | Что берём |
| --- | --- | --- |
| [League of Legends](https://technology.riotgames.com/node/99) | Свой патчер: подписанный манифест, чанки по содержимому, докачка после обрыва. Обновление в среднем меньше 40 с вместо 8+ минут, отказы 2.2% → 0.3% | подписанный манифест, докачка, параллельные запросы |
| [Marvel Snap](https://unity.com/resources/marvel-snap) (Unity) | Addressables + Unity CCD; месячные релизы клиента, контент еженедельно | та же связка Addressables для арта |
| [Path of Exile](https://poedb.tw/Bundle_schema) | В Steam — через депоты; монолитный архив 26 ГБ разрезали на десятки тысяч бандлов, чтобы патчи стали маленькими | не делать огромных архивов |
| Warframe | Даже в Steam патчится мимо Steam через свой CDN, проверка файлов — в игре | кнопка «Проверить файлы» |
| Last Epoch (Unity) | Всё через Steam; игроки жалуются на тяжёлые хотфиксы | антипример: контент отдельно от кода |
| WoW (Blizzard CASC) | Хранилище по хэшам; стадия «Можно играть» — играешь, пока остальное докачивается | минимум на старт, остальное в фоне |

Позиция Valve: в разделе лучших практик они просят обновляться через Steam и не требовать докачки внутри игры ([Steamworks: Updates](https://partner.steamgames.com/doc/store/updates)). Это рекомендация, а не пункт ревью: запрета нет, и Warframe с Tarkov так и живут. Поэтому стартовый набор разумно держать в Steam, а разницу — своим CDN (подробнее в разделе про Steam).

## Архитектура: два слоя

Steam доставляет код и базовый контент, наш CDN — всё, что новее. Всё, что сервер раздаёт как контент, собирается в пронумерованный **релиз контента**: один номер версии покрывает и арт, и конфиг, и анимации.

| Что | Где живёт | Формат | Как обновляется |
| --- | --- | --- | --- |
| Код игры, движок, экран загрузки и входа, шрифты | депот Steam | плеер Unity | новый клиент через Steam |
| Модели, префабы, материалы, текстуры, VFX, звуки, шейдеры | Steam (снимок на момент выпуска клиента) + наш CDN (всё новее) | бандлы Addressables | релиз контента |
| Конфиг (баланс, предметы, монстры, этажи) | тот же CDN + игровой сервер держит его у себя | JSON, сжатый, имя = хэш | релиз контента |
| Анимации (клипы, походка, хваты) | тот же CDN | JSON по клипам, имя = хэш | релиз контента |
| Кованое оружие (форма из деталей) | строится сервером по запросу | двоичный меш | по подписи вида + свой дисковый кэш |
| Сейвы, инвентарь, мир | игровой сервер | протокол | как сейчас, к релизам не относится |

Три кирпича, из которых состоит система:

1. **Указатель** — крошечный ответ сервера «текущий релиз — такой-то». Именно его клиент сверяет на каждом запуске.
2. **Манифест** — список всех файлов релиза с их хэшами и размерами. Качается, только когда указатель изменился.
3. **Хранилище по хэшам** — файлы на CDN, имя файла = его хэш. Файл никогда не перезаписывается, поэтому CDN может хранить его вечно, а клиент — не перепроверять.

Игровой сервер бандлы не читает никогда: всё, что влияет на игру, лежит в конфиге. Арт адресуется ключом = id из конфига (решение прошлого плана «Unity — дом контента»).

## Версия, манифест и хранилище

Номер версии — это пара «порядковый номер релиза + хэш его манифеста». Клиент сравнивает его с сохранённым и больше ничего не делает, если он совпал.

**Указатель** — `GET /api/content/pointer?channel=live&abi=1&build=<номер сборки>`. Отвечает наш сервер (не CDN), с ETag, порядка сотни байт:

```json
{ "seq": 42,
  "manifest": "sha256:9f1c…",
  "manifestSize": 48211,
  "cdn": ["https://cdn.наш-домен/c/", "https://api.наш-домен/c/"],
  "minClient": 118, "latestClient": 121 }
```

Почему указатель отдаёт сервер, а не файл на CDN: сервер может дать разные релизы разным каналам и сборкам, раскатывать по процентам и откатывать одной строкой в базе. У файла на CDN есть время жизни в кэше, и он «залипает».

**Манифест** — файл на CDN, имя = его хэш, сжат, подписан:

```json
{ "seq": 42, "abi": 1, "created": "2026-10-07T12:00:00Z",
  "catalog": "sha256:…",
  "data": { "config": "sha256:…", "pose/clips/run_fwd": "sha256:…", "…": "…" },
  "files": { "sha256:…": { "size": 5242880, "pack": "core" }, "…": {} },
  "packs": { "core": […], "town": […], "biome:crypt": […], "class:warrior": […] },
  "keys": ["knight_06_modular_rig", "crypt_wall_base_01", …],
  "sig": "ed25519:…" }
```

- `files` — все файлы релиза с размерами: по ним клиент считает «надо скачать N МБ» до начала загрузки.
- `packs` — группы для загрузки по частям: стартовый набор, город, биомы, классы.
- `keys` — все ключи арта релиза: сервер и редактор конфигов проверяют по ним, что конфиг не ссылается на несуществующее.
- Конфиг и анимации входят в тот же манифест, поэтому один номер версии покрывает всё.

**Хранилище на CDN:**

| Путь | Что | Кэширование |
| --- | --- | --- |
| `c/b/<первые 2 символа>/<sha256>` | бандлы, конфиг, клипы, каталог Addressables | вечно (`immutable`, 1 год) |
| `c/m/<sha256>` | манифесты | вечно |
| `/api/content/pointer` | указатель (наш сервер) | `no-cache` + ETag |

**На сервере** — две таблицы в Postgres: `content_releases` (номер, ABI, хэш манифеста, хэши конфига и анимаций, когда создан) и `content_channels` (канал, ABI, текущий релиз, процент раскатки). Все процессы сервера читают их одинаково — как сейчас синхронизируется конфиг.

Хэш — только sha256. Нынешний 32-битный FNV годится для «изменилось ли», но не для адресации тысяч файлов: высок риск совпадений.

## Совместимость клиента и контента

Контент меняется свободно, пока не меняется код, на который он опирается. Эту границу ведёт номер **ABI** — целое число, вшитое в клиент. Каждый релиз контента собирается под конкретный ABI, и сервер выдаёт клиенту релиз именно его ABI.

| Можно без нового клиента | Нужен новый клиент через Steam (ABI +1) |
| --- | --- |
| новые и изменённые модели, текстуры, материалы на уже имеющихся шейдерах | любой новый или изменённый код C# |
| новые префабы из уже существующих компонентов, VFX, звуки | новый компонент или новое сохраняемое поле на префабе |
| конфиг и анимации в текущей схеме | смена схемы конфига, которую старый клиент не прочтёт |
| новые группы, адреса и метки бандлов | обновление Unity или Addressables, настройки URP с влиянием на шейдеры |
| шейдеры из бандла шейдеров (если группа обновляемая) | смена версии протокола с сервером |

Как сервер решает, что ответить клиенту:

1. **Сборка клиента ниже `minClient`** — экран «Обновите игру в Steam». Для этого у Steam есть штатный вызов `MarkContentCorrupt`: Steam проверяет и докачивает клиент сам ([ISteamApps](https://partner.steamgames.com/doc/api/ISteamApps)).
2. **Сборка старая, но ещё поддерживается** — последний релиз контента её ABI и плашка «Доступно обновление игры».
3. **Сборка свежая** — текущий релиз своего канала.

Важно: Steam доставляет новый клиент не мгновенно. У Path of Exile 2 игроки попадали в бесконечное «обновитесь», пока депоты не отдали новую сборку. Поэтому `minClient` поднимаем с задержкой после выкладки в Steam, а сервер какое-то время принимает предыдущую версию протокола.

## Запуск клиента по шагам

Обычный запуск без обновлений — один запрос в несколько сотен байт и всё с диска. С обновлением игрок видит размер и прогресс, а качается только разница.

1. **Читаем локальное состояние** `state.json`: текущий и предыдущий релиз на диске.
2. **Запрашиваем указатель** (таймаут 3–5 с). Сборка ниже `minClient` — экран «Обновите игру в Steam».
3. **Версия совпала и стартовый набор на месте** — ноль скачиваний, сразу вход в игру.
4. **Версия новая** — качаем манифест, проверяем хэш и подпись, считаем, каких файлов нет на диске.
5. **Показываем размер** («Обновление: 38 МБ») и проверяем свободное место на диске.
6. **Качаем стартовый набор** (шейдеры, интерфейс, главное меню, конфиг, анимации — только то, без чего не открыть меню): 4–8 параллельных загрузок, прогресс по байтам.
7. **Каждый файл**: пишем во временный `.part`, считаем хэш на лету, проверяем и только потом переименовываем. Обрыв — докачка с того же места (`Range`), повторы с паузой.
8. **Переключаем версию атомарно**: замена `state.json` одной операцией. До этого момента игра видит старую версию целиком, смеси версий не бывает.
9. **Вход в игру.** Всё остальное — герои, город, биомы, музыка — качается в фоне сразу после проверки версии: пока игрок в главном меню, создаёт персонажа и осваивается в городе. Пока он в городе, биом ближайшего забега ещё и подгружается в память, а шейдеры прогреваются, поэтому вход в подземелье проходит без ожидания.
10. **Уборка кэша** в фоне после успешного старта: удаляем файлы, которых нет ни в текущем, ни в предыдущем релизе.

**Ждать игрок может только в двух местах.** Экран запуска — если обновился стартовый набор. Вход в мир после выбора персонажа — если герой и город ещё не докачались. Остальные переходы (в подземелье, между этажами и биомами) незаметны: нужное уже на диске и в памяти. Если фон не успел (очень медленный интернет), переход показывает обычный экран загрузки с прогрессом.

**Кэш на диске** — `%USERPROFILE%\AppData\LocalLow\<компания>\<игра>\content\`. Не в папке установки (Steam проверяет её файлы) и не в Steam Cloud (гигабайты синхронизации). Базовый контент клиент читает прямо из папки установки (её обновляет Steam), в кэш ложится только пришедшее с CDN. Имена компании и игры входят в этот путь, поэтому фиксируем их до первой внешней сборки: потом смена имени = все перекачивают контент и теряют настройки.

**Когда что-то пошло не так:**

| Ситуация | Что делаем |
| --- | --- |
| Сервер недоступен | игра онлайновая: «Нет связи с сервером» и повторы, как сейчас |
| CDN недоступен, сервер работает | запасной адрес из указателя; если в кэше есть версия, которую сервер ещё принимает, — играем на ней |
| Файл не совпал по хэшу | удаляем и качаем заново, одна повторная попытка |
| Не хватает места | понятная ошибка до начала загрузки |
| Антивирус держит файл | повтор переименования с паузой |
| Кэш испорчен | кнопка «Проверить файлы» в настройках: полная сверка хэшей и докачка плохих |

Экран загрузки управляется и мышью, и геймпадом — требование Steam Deck.

## Addressables: настройки и группы

Addressables — штатный пакет Unity, который упаковывает арт в бандлы и грузит его по ключу. Берём его как формат и загрузчик, а скачиванием, проверкой и переключением версий управляет наш тонкий слой. Так у арта, конфига и анимаций один кэш и одни правила.

**Два варианта связки — выбираем прототипом в первой фазе:**

|  | А. Свой кэш (рекомендую) | Б. Кэш Unity |
| --- | --- | --- |
| Кто качает бандлы | наш слой по манифесту | Addressables сам |
| Откуда Unity их грузит | с диска: адрес переписывается на локальный файл (`InternalIdTransformFunc`) | из своего кэша бандлов |
| Проверка целостности | sha256 каждого файла | CRC (Unity пережимает файлы в кэше, хэш не подходит) |
| Докачка после обрыва | есть (`Range`) | нет: бандл качается заново |
| Атомарное переключение и откат | есть: меняется один `state.json` | частично |
| Объём работы | больше кода, нужно проверить прототипом | меньше кода |

**Настройки (фиксируем до первого внешнего релиза — их смена заставит всех перекачать всё):**

- Версия пакета **2.11.2** — официально выпущенная для нашей Unity 6000.6. Линия 4.x свежая, её смотрим до публичного запуска.
- Все группы **удалённые**, включая группу по умолчанию: в клиенте бандлов нет.
- Имя бандла с хэшем (Append Hash) — у каждой версии свой неизменный адрес.
- Каталог бинарный, проверка обновлений каталога — только вручную (её делает наш указатель), имя каталога = `abi<N>`.
- Prevent Updates выключен везде. Каждый релиз — полная сборка контента; неизменённые бандлы получают то же имя и не качаются. Детерминированность сборки проверяем тестом: две сборки подряд дают одинаковые хэши.
- В редакторе Unity — режим «Use Asset Database»: бандлы не собираются, правка видна сразу.

**Группы бандлов** (ориентир — 5–64 МБ на бандл, вместе лежит то, что вместе грузится):

| Группа | Что внутри | Когда грузится |
| --- | --- | --- |
| `shaders` | все шейдеры и их варианты — единственная копия | старт, первым |
| `shared` | общие текстуры и материалы, интерфейс | старт |
| `hero` | тела героев, броня, оружие | в фоне с главного меню, свой класс — первым; ждём при входе в мир |
| `town` | город | в фоне с главного меню; ждём при входе в мир |
| `env_<биом>` | тайлы, декор, свет биома | в фоне с главного меню; в городе — ещё и в память |
| `mon_<семья>` | монстры семьи | вместе с биомом |
| `vfx`, `sfx` | эффекты и звуки | общие на старте, биомные — с биомом |
| `music` | музыка | в фоне |

Шейдеры живут только в бандле: если оставить их ещё и в клиенте, получим две копии и непредсказуемый `Shader.Find`. Заодно это и облегчает установщик: сейчас шейдеры — 281 из 417 МБ. Ключ арта = id из конфига, адреса назначает импортёр по папке.

## Конфиг и анимации в том же релизе

Конфиг и анимации не кладём в бандлы Unity: их читает и игровой сервер, а правят веб-редакторы, и каждая правка не должна требовать сборки в Unity. Они идут отдельными файлами в том же манифесте, с теми же правилами: имя = хэш, кэш на диске, проверка.

| Данные | Сейчас | Станет |
| --- | --- | --- |
| Конфиг | 0.75 МБ каждый запуск | один сжатый файл \~90 КБ, качается только при изменении |
| Анимации | 6.65 МБ каждый запуск, вся библиотека одним ключом | по файлу на клип (и на каждый раздел настроек: походка, хваты…); поправил один клип — качается несколько КБ |

**Одна правда для сервера и клиента.** Релиз запоминает хэш своего конфига. Игровой сервер включает конфиг текущего релиза на всех процессах через уже существующую синхронизацию, а клиент берёт тот же файл. В рукопожатии при входе в комнату рядом с версией протокола едет номер релиза.

**Делим ревизию конфига на две.** Игровая часть (баланс, цены, предметы, коллайдеры декора) и визуальная (ссылки на арт, фейд стен). Команды кузницы и лавки сверяют только игровую — и правка текстуры больше не даёт отказ «Цена изменилась».

**Редакторы публикуют данные без Unity.** Редактор конфигов и поз-редактор по кнопке «Опубликовать» создают новый релиз, в котором арт тот же, а данные новые. Перед этим сервер проверяет, что каждый ключ арта из конфига есть в релизе. Так сохраняется нынешний принцип «правка в редакторе сразу видна в игре».

**Кованое оружие** в релиз не входит: его форма строится по запросу из деталей и уже адресована подписью вида. Ей добавляем свой дисковый кэш с ограничением размера.

Сервер начинает сжимать ответы (gzip/brotli), а клиент — их распаковывать: сейчас ни того, ни другого нет.

## Публикация и каналы

Новый арт ты выпускаешь одной кнопкой в Unity, новые данные — кнопкой «Опубликовать» в редакторах, как сейчас. Выпущенное сначала попадает в канал `dev`, игрокам — только по твоему решению.

**Кнопка «Опубликовать контент» в Unity** делает по порядку:

1. Проверки: каждый ключ конфига есть в арте и наоборот; нет дублей между бандлами; материалы только на разрешённых наборах шейдеров; стартовый набор в пределах бюджета.
2. Сборка бандлов (в фоновом режиме Unity, как уже собирается клиент).
3. Хэши файлов, сборка и подпись манифеста.
4. Заливка только недостающих файлов (сервер говорит, чего у него нет), потом манифеста.
5. Регистрация релиза на сервере — сервер перепроверяет хэши.
6. Переключение канала `dev` на новый релиз — автоматически.

**Порядок важен:** сначала файлы, потом манифест, потом регистрация, потом указатель. Иначе конфиг сошлётся на ключ, которого ещё нет, и у всех пропадёт модель.

**Каналы** совпадают с ветками Steam, клиент узнаёт свою ветку у Steam:

| Канал | Кто на нём | Как меняется |
| --- | --- | --- |
| `dev` | ты, локальный и тестовый сервер | сам, на каждой публикации |
| `beta` | тестеры (закрытая ветка Steam) | кнопкой «В бету» |
| `live` | все игроки | кнопкой «Выпустить»; можно по процентам, например 10% → 100% |

**Откат** = указатель канала снова смотрит на прошлый релиз. Игроки ничего не качают: файлы прошлого релиза ещё лежат у них в кэше. Номер релиза при откате всё равно растёт — на него опирается защита от подставного старого релиза.

**Публикация на прод.** Сейчас в продакшене закрыто всё — это осознанный запрет живой правки баланса. Запрет остаётся, а рядом появляется отдельная дверь: регистрация и продвижение готового релиза под ролью админа. На прод попадает только то, что прошло `dev`, и никогда не правка в обход релиза.

**Уборка хранилища.** Файл, на который не ссылается ни один из последних N релизов всех каналов, удаляется по сроку, а не сразу: иначе сломаем старые клиенты и откат.

## Steam и установщик

В установщике — код, стартовая сцена с экранами загрузки и входа, шрифты и базовый контент: снимок бандлов, конфига и анимаций на момент выпуска клиента. Он лежит в папке установки отдельными файлами с именами по хэшу, клиент читает его оттуда напрямую. Сам код станет легче нынешних 417 МБ: glTFast удаляется, вырезаем ненужные библиотеки (DirectML 14 МБ, Roslyn 6 МБ).

**Что говорит Valve и как мы с этим живём:**

- **«Не заставляйте качать контент внутри игры»** — рекомендация, не пункт ревью. С базовым контентом в депоте мы её соблюдаем: новый игрок ставит игру из Steam и с нашего CDN качает только изменения после выпуска клиента. Файлы адресованы хэшами, поэтому пришедшее со Steam повторно не качается.
- **Никакого внешнего лаунчера.** За него Steam Deck снижает статус с «Verified» до «Playable» ([Steam Deck](https://partner.steamgames.com/doc/steamdeck/compat)). Обновление — экран внутри игры, с геймпадом.
- **Новый клиент доставляет Steam.** Он патчит дельтой кусками по \~1 МБ, трафик для нас бесплатный ([Uploading](https://partner.steamgames.com/doc/sdk/uploading)). Не сжимаем сборку целиком: у одной Unity-игры правка одной строки кода давала патч 600 МБ из 1 ГБ. Базовый контент лежит отдельными бандлами по 5–64 МБ, и Steam перекачивает только изменившиеся.
- **Ветки Steam = наши каналы.** Закрытая ветка `beta` берёт контент из канала `beta`; клиент узнаёт свою ветку через Steam API.

**До первой внешней сборки фиксируем:**

- имена компании и игры в проекте Unity — сейчас `DefaultCompany`; они входят в путь кэша и настроек;
- версию клиента (`build`) — сейчас Unity её не шлёт;
- бэкенд сборки (Mono или IL2CPP): от него зависит, какой код вырежется и что сможет потом прийти в контенте.

## Хостинг и стоимость

До релиза всё раздаёт наш сервер — одно место, без внешних сервисов. CDN выберем ближе к релизу: схема адресов та же, и переключение не требует нового клиента. Таблица ниже — на будущее; кандидат пока Cloudflare R2: исходящий трафик бесплатный.

Пример: 1000 игроков × 3 ГБ ≈ 3 ТБ в месяц — столько пришлось бы раздать, если бы первая установка шла с CDN. С базовым контентом в Steam первую установку раздаёт Steam, а на CDN остаются только обновления между выпусками клиента.

| Вариант | Тарифы | За пример, $/мес | Заметки |
| --- | --- | --- | --- |
| [Cloudflare R2](https://developers.cloudflare.com/r2/pricing/) + свой домен | хранение $0.015/ГБ, трафик $0 | ≈ 0 | нужен свой домен и правило кэширования для бандлов; адрес `r2.dev` — только для тестов |
| [Bunny CDN](https://docs.bunny.net/cdn/pricing) | $0.005–0.01/ГБ | ≈ 30 | простой, европейский |
| [AWS CloudFront](https://cloudburn.io/blog/amazon-cloudfront-pricing) | 1 ТБ бесплатно, дальше $0.085/ГБ | ≈ 170 | дорого при росте |
| [Unity CCD](https://support.unity.com/hc/en-us/articles/35114118738324) | 50 ГБ бесплатно, дальше $0.08/ГБ | ≈ 236 | удобно с Addressables (релизы, «бейджи»), но самое дорогое |
| Наш сервер (TimeWeb) | входит в тариф VDS | — | годится для разработки и как запасной адрес; для всех игроков упрётся в канал и диск |

Указатель всегда отдаёт наш сервер. В нём список адресов хранилища (CDN, затем наш сервер), поэтому CDN можно сменить без нового клиента.

## Безопасность и обновления посреди сессии

Подменить контент на CDN нельзя: клиент принимает только манифест, подписанный нашим ключом, и файлы, чей хэш совпал с манифестом.

- **Всё по HTTPS.** В проде http запрещён, как и сейчас в сборке клиента.
- **Подпись манифеста (Ed25519).** Закрытый ключ — только на сборочной машине, открытый вшит в клиент. Утёкший ключ от CDN не позволит подсунуть игрокам чужое.
- **Номер релиза только растёт** — старый релиз нельзя выдать за новый.
- **Размеры файлов в манифесте** — клиент не качает больше обещанного.
- **Регистрация и продвижение релиза** — только роль админа. Ключи хранилища — только на сборочной машине.
- Подпись защищает цепочку поставки, но не от модов на компьютере игрока. Это нормально: игра серверная, и клиенту и так не доверяем.

**Если релиз вышел, пока игрок в игре:**

| Что изменилось | Что происходит |
| --- | --- |
| Только арт | клиент докачивает в фоне и применяет при следующем запуске или на экране загрузки; в бою ничего не подменяется |
| Игровые правила (баланс, предметы, монстры) | у всех игроков плашка «Обновление игры через 10:00» с таймером (срок задаёшь при выпуске): время доделать и выйти в город. В ноль — отключение с причиной «игра обновилась»; клиент сам переподключается, берёт новый релиз на экране загрузки и возвращает игрока. Сейв живёт на сервере и не теряется |
| Анимации | как арт: новые клипы — со следующего входа в комнату |
| Нужен новый клиент | плашка «Доступно обновление игры»; старый клиент доигрывает сессию |
| Сервер сослался на арт, которого у клиента нет | видимая заглушка и докачка по требованию, никогда не «пустота» |

Нужен ли таймер, решает сам релиз: если в нём изменилась игровая часть конфига, публикация предлагает срок предупреждения. Правки только арта и анимаций проходят тихо, без таймера. Новые входы в игру после выпуска сразу попадают на новый релиз.

Каталог Addressables посреди игры не меняем: смена блокирует все загрузки и конфликтует с уже загруженными бандлами.

**Сначала данные, потом арт: каждая фаза закрывается проверкой.**

| Фаза | Что делаем | Готово, когда |
| --- | --- | --- |
| **Д0. Основа и прототип** | Addressables 2.11.2, группы бандлов, ключ арта = id из конфига; прототип: свой кэш (вариант А) против кэша Unity (вариант Б); имена компании и игры, номер сборки клиента в рукопожатии | бандл грузится из кэша; две сборки — одни хэши |

| **Д2. Арт в бандлах** | после первых фаз плана «Unity — дом контента» (FBX, каталог); кнопка «Опубликовать контент», заливка только недостающего; экран обновления, фон, «Проверить файлы»; шейдеры уходят в бандл | правка → качается 1 бандл; обрыв → докачка; порча → восстановление |

| **Д4. Полировка к релизу в Steam** | предзагрузка следующего релиза до его выхода; лимиты кэша, статистика скачиваний, бюджет первого запуска | с CDN — только изменения; первый запуск в бюджете |

Д1 не зависит от арта и сразу убирает 7 МБ с каждого запуска; Д2 ждёт импорта FBX из плана «Unity — дом контента».

### Д3 (локально) — сделано 08.10

Серверная часть каналов, раскатки, отката и подписи (`packages/server/src/content/`, `net/releaseRoutes.ts`) и клиент Unity (ниже). Кнопки редактора — вкладка «📦 Выпуски» (справка «Выпуски контента», 08.10). CDN и ветки Steam — ещё нет.

- **Каналы.** `dev` переключается сам на каждой нарезке; `beta` и `live` — только ручками администратора. Первый выпуск канала — на 100%, дальше можно по процентам поверх прежнего релиза: 10% → 50% → 100% (процент только растёт). Пока раскатка не доведена до 100%, другой релиз в канал не выпускается.
- **Откат** — канал на прежнем содержимом под новым номером: новая запись `content_releases` с тем же манифестом (`origin_seq` — чей), файлы не копируются. Номер у клиента только растёт. Повторный «Откатить» не возвращает плохой релиз — нужен явный `toSeq`.
- **Корзина устройства:** `sha256("<id>|<channel>|<seq>")`, первые 4 байта big-endian по модулю 100; меньше процента — новый релиз, иначе прежний. Без `id` новый релиз выдаётся только при 100%.
- **Канал без указателя.** `dev` → 503 «повтори». `beta`/`live` вне продакшена (или при `DM_CONTENT_DEV_FALLBACK=1`) получают указатель `dev` с `channel: "dev"`, на проде — 404 «канал не выпущен»: клиент играет тем, что у него на диске.
- **Версия клиента:** `minClient`/`latestClient` задаются на канал и ABI. `build < minClient` → ответ 200 с `clientRequired: true` (экран «Обновите игру»); `build < latestClient` → `clientOutdated: true`. Без `build` считается 0.
- **Уборка хранилища** — ручка администратора, по умолчанию сухой прогон. Файл удаляется, только если его не держит ни один из последних N релизов, ни один указатель канала и ни одно арт-описание, и он старше срока (не меньше суток).

**Контракт подписи (по нему пишутся Unity и редактор).** Подписывается строка UTF-8 `dmcontent:v1|<abi>|<seq>|<manifest>|<channel>`: `abi` и `seq` — десятичные, `manifest` — 64 знака hex sha256 манифеста, `channel` — поле `channel` ответа. Алгоритм — Ed25519 (RFC 8032). Подпись — 64 байта в base64 со знаками `=` (поле `sig`, `sigAlg: "ed25519"`). `keyId` — первые 16 знаков hex sha256 сырого открытого ключа (32 байта). Клиент проверяет подпись своими зашитыми ключами, затем sha256 скачанного манифеста против `manifest`. Он отвергает `seq` меньше сохранённого и `channel`, отличный от запрошенного (`dev` принимает только сборка разработчика). `GET /api/content/pubkey` отдаёт открытый ключ стенду и для деплоя, клиент ему вслепую не верит. Ключ сервера задаётся в `DM_CONTENT_SIGN_KEY_FILE`; без переменной сервер сам заводит ДЕВ-ключ (см. `docs/DEPLOY.md`).

**Клиент Unity — сделано 08.10** (`Assets/DM/Net/ContentSync.cs`, `Ed25519.cs`; подробно — `tools/unity-check/README.md` «Релиз контента» и `DEPLOY.md` Unity). Указатель запрашивается с `build` (номер сборки `ContentSync.ClientBuild`, сейчас 1) и `id` (sha256 от «dm-device|» и идентификатора машины). Сборка ниже `minClient` — экран «Вышло обновление игры — обновите её в Steam», вход закрыт; ниже `latestClient` — плашка «Доступно обновление игры». Подпись проверяет своя реализация Ed25519 (порт TweetNaCl + отказ при S ≥ L) ключами из `contentKeys` в `server.json` сборки (`build_player.py --content-key`, выпускной с ключом нужен `--channel beta|live`). Отказ — как сбой указателя: игра идёт старым путём, кэш не тронут. Без ключа (редактор, стенд) подпись не проверяется, в лог — одно предупреждение.

## Риски и ловушки

Большинство ловушек ловится проверками при публикации; самые дорогие — настройки, которые нельзя менять после первого внешнего релиза.

| Риск | Чем грозит | Что делаем |
| --- | --- | --- |
| Файл перезаписан под тем же именем | игроки сроками видят старое из кэша CDN | имя файла = его хэш, перезапись невозможна |
| Недетерминированная сборка бандлов | игроки перекачивают неизменённое | тест «две сборки подряд = одинаковые хэши»; запасной путь — штатное обновление Addressables по прошлой сборке |
| Конфиг ссылается на ещё не залитый арт | у всех пропадают модели | порядок публикации + сверка ключей сервером |
| Шейдер и в клиенте, и в бандле | две копии, непредсказуемый `Shader.Find` | шейдеры только в группе `shaders` |
| Варианты шейдеров вырезаны при сборке | материалы теряют нормали или розовеют | бандлы собираются с теми же настройками URP, что и клиент; тестовые сборки со строгим совпадением |
| Один ассет и в клиенте, и в бандле | две копии (у нас это микшер звука и профиль вида) | правило «либо там, либо тут» + автопроверка дублей |
| Код вырезан как неиспользуемый (IL2CPP) | новый контент не грузится | список сохраняемых типов + «хранитель модулей» в клиенте |
| Смена имени компании/игры после выпуска | все перекачивают контент и теряют настройки | фиксируем до первой внешней сборки |
| `minClient` поднят раньше, чем Steam раздал клиент | бесконечное «обновитесь», как у Path of Exile 2 | задержка после выкладки и поддержка предыдущей версии |
| Старые файлы удалены слишком рано | ломается откат и старые клиенты | удаление по сроку и по ссылкам всех живых каналов |
| Длинные пути Windows (>260 символов) | падает сборка или кэш у игрока | короткие имена групп + проверка длины |
| Каталог заменён посреди игры | блокируются загрузки, конфликты бандлов | применение только на старте и на экране загрузки |
| Известные баги Addressables (зависание загрузки, испорченный каталог) | игра висит на загрузке | свой сторож прогресса, сброс и один повтор, кнопка «Проверить файлы» |
| Прод на старой сборке (08.08) | первый выпуск системы = большой деплой | сначала тестовый сервер с полным сценарием, потом прод |

## Решения за тобой

Десять вопросов, от которых зависит работа. По каждому есть моя рекомендация; выбери статус в последней колонке или оставь комментарий к строке.

| # | Вопрос | Рекомендую | Другие варианты | Решение |
| --- | --- | --- | --- | --- |
| 1 | Чей кэш для бандлов | свой (вариант А): один кэш на всё, sha256, докачка, атомарное переключение. Окончательно — после прототипа | кэш Unity (вариант Б): меньше кода, без докачки | Согласен |
| 2 | Что в установщике Steam | код + базовый контент на момент выпуска клиента (раздаёт Steam, бесплатно); с CDN — только изменения после него | только код в установщике, весь контент с CDN | Согласен |
| 3 | Первая загрузка | всё в фоне с главного меню; ждать игрок может только на экране запуска и при входе в мир | всё сразу перед входом | Согласен |
| 4 | Хостинг контента на проде | пока всё на нашем сервере; CDN выбираем ближе к релизу (кандидат — Cloudflare R2, трафик $0) | Unity CCD, Bunny, только наш сервер | Согласен |
| 5 | Каналы и выпуск | `dev` сам, `beta` и `live` кнопкой, в `live` можно по процентам | один канал, сразу всем | Согласен |
| 6 | Новое посреди сессии | арт и анимации — на старте или экране загрузки; смена игровых правил — предупреждение с таймером, потом переподключение | только плашка «перезапустите» | Согласен |
| 7 | Версия Addressables | решено: 2.11.2 (выпущена для нашей Unity 6000.6); 4.x пересматриваем до публичного запуска | сразу 4.1 | Согласен |
| 8 | Имена компании и игры в Unity | игра — The Fourth Bequest; компания — пока Palimpsest Games (рабочее название). Окончательно решаем перед первой внешней сборкой — напомню | сейчас `DefaultCompany` / `Ashes of the past` | Ждёт решения |
| 9 | Mono или IL2CPP в релизе | решено: IL2CPP во всех сборках игры уже сейчас (мягкая чистка кода, список сохраняемых типов, модули движка не вырезаем) — чтобы поломки всплывали по одной, пока контента мало; редактор Unity остаётся на Mono | IL2CPP сразу | Согласен |
| 10 | Порядок с планом «Unity — дом контента» | решено: одна очередь — Д0+Ф0 → Д1 и Ф1–Ф2 рядом → Д2 → Ф3–Ф5 сразу в бандлах → Ф6 (glTFast прочь) → Д3–Д4; ничего не делаем дважды | сначала целиком один план, потом другой | Согласен |
| 11 | Коммит, пуш и выкатка на сервер без тебя | решено: git — я сам (разрешить пуш в настройках Claude Code); выкатку делает CI: пуш в ветку релиза → GitHub Actions обновляет сервер по ключу деплоя и откатывается, если сервер не поднялся; ключ заводишь ты один раз | прямой SSH-доступ к серверу с этой машины | Согласен |
