# Модуль: render3d (3D-клиент, ОНЛАЙН)

**ОТДЕЛЬНЫЙ 3D-клиент** на Three.js. Старый 2D-клиент (`index.html` → `main.ts`, Phaser) **не тронут** —
два клиента живут параллельно на одном сервере. Запуск: `npm run dev` → `http://localhost:5173/game3d.html`.

Стиль — **2.5D (Diablo/PoE)**: геймплей на плоскости, камера под углом. Клиент **ПОЛНОСТЬЮ ОНЛАЙН**, как 2D:
реальный `App`+`NetClient` к авторитетному серверу, авторизация/выбор персонажа, мир из кадров `joined`/
`areaChanged` (`FloorInit`) и снапшотов (`WorldSnapshot`); бой/движение/награды/лут считает сервер. Никаких
локальных сессий. Отличие от 2D — только рендер (Three.js вместо Phaser); DOM-панели/HUD/модалки — те же.
См. [[render-3d-migration]] (память).

## Файлы (онлайн-клиент)
- **`online3d.ts`** — оркестратор (аналог 2D `OnlineScene`+`NetDriver`+`UIScene`): рендерер/сцена/камера;
  подключение `connect→runStatus→lobby/resume→join`; постройка области из `FloorInit` (env3d-адаптер + физика);
  рендер мира из `WorldSnapshot` (свой игрок/пиры — куклы `makeGamePlayerDoll`, монстры — `makeHumanoidDoll`,
  снаряды/дропы — меши; сглаживание своего игрока, low-pass скорости кукол против 30/60Гц-джиттера); ввод
  (WASD/мышь-взгляд/ЛКМ-атака/ПКМ+1-3 скиллы) → сервер; NPC/портал/лестница/рычаги/двери (интерактив `[E]`);
  модалки (лобби/голосование/смерть/код комнаты/пинг); события сервера → VFX+лог+звук. Регистрирует все DOM-панели
  (инвентарь/персонаж/скилы/мастерство/магазин/кузница/квесты/сложность/сундук) + `GameLog`+`SfxController`.
- **`screens3d.ts`** — DOM-экраны авторизации (вход/регистрация → выбор/создание персонажа), reuse `authApi`+
  `listClasses`; `runAuthFlow(app)` резолвится, когда `app.auth`+`pendingCharId` готовы.
- **`hud3d.ts`** — DOM-HUD (HP/мана/выносл./XP + ур./золото/этаж) из `app.state` (пулы авторитетны с сервера).
- **`pose.ts`** — **ghost-риг**: чистый генератор ЦЕЛЕВОЙ позы (углы суставов вокруг локальной X) —
  ходьба (синус), атака (дуга замах→удар→возврат), поза смерти. Единый источник для ОБОИХ ригов ниже.
  `PoseDriver {setMove,attack,setDead,update(dt)→PoseTargets}`.
- **`ragdoll.ts`** — **АКТИВНЫЙ РЭГДОЛЛ на Jolt Physics** (`jolt-physics`, wasm-порт движка из Horizon
  Forbidden West / Death Stranding 2). Кости — динамические тела на **анатомических суставах**: спина/шея/
  плечи/бёдра — `SwingTwist` (эллиптический конус + скрутка), колени/локти/щиколотки — `Hinge` с
  АСИММЕТРИЧНЫМИ лимитами (колено не выворачивается — by design, а не подбором знака). «Мышцы» — моторы
  суставов с `mMaxTorqueLimit` (предел силы по группам: ноги сильные, руки/спина слабые — рецепт Exanima).
  К позе ghost-рига ведёт ШТАТНЫЙ `Ragdoll.DriveToPoseUsingMotors` — рукописный PD не нужен.
  Тело кости начинается В СУСТАВЕ (форма сдвинута `RotatedTranslatedShape`) — иначе кость крутится вокруг
  своего центра. Авторитет сима цел: **таз — kinematic** (`MoveKinematic`), стоит там, где сказала игра.
  Смерть → таз Dynamic + моторы `Off` → свободный коллапс. `PhysWorld` держит статику этажа.
  **Почему не Rapier:** там в JS-биндингах моторы есть только у revolute (dimforge/rapier.js#287) → риг был
  одноосевым, боковой баланс невозможен, ведение к позе — руками. Замер: проскальзывание опорной стопы при
  ходьбе **80 u/с (Rapier) → 16 u/с (Jolt)**.
- **`joltTest.ts` + `jolt-test.html`** — изолированный стенд Jolt (вне игры): собирает риг по шагам с логом,
  ловит немые `abort()`. Именно им пойманы грабли ниже — держать под рукой.
- **ЕДИНЫЙ РИГ (игрок И монстры).** Кукла `makeHumanoidDoll` (`gamePlayerDoll.ts`): физ-рэгдолл
  `humanoidRagdoll` ВСЕГДА ведёт, рисуется `renderRagdollGhost` (humanoid-меш по `readBakedPose` + заземление
  низшей стопы). Отличие только во входе: класс → `applyGaitConfig` (→ глобальный `GAIT/POSE`) + контент класса;
  монстр → `loadGaitLocal` (свои plant/gx, глобальный GAIT делит с игроком) + контент `'monster'` с фолбэком на
  Волкодава. Спавн — `ragdoll.snapToPose()` (без флейла T-поза→стойка). Старые `makeRagdoll`/`actor.ts` СНЕСЕНЫ.
- **Дебаг-панель тюнинга** (клавиша **G** в `game3d.html`): живые ползунки походки (`GAIT`), позы рук
  процедурной ходьбы (`POSE`), боевого гарда меч+щит (`GUARD`) + авто-бег. Всё применяется мгновенно (читается
  каждый кадр). «в консоль» — дамп, «сброс» — к дефолтам. Так походку/стойки настраивают ГЛАЗАМИ (синтетические
  замеры шумят из-за случайного этажа). Per-класс/монстр тюн бега/стоек/ударов — в РЕДАКТОРЕ поз
  (`pose-editor.html`; тумблер «персонажи | монстры»), сохраняется в localStorage (`pe_gait`/`pe_clips`/`pe_sway`/`pe_twist`).
- **Torso-lead (голова ведёт, таз догоняет) + скрутка корпуса.** Прицел (`aimYaw`, курсор/сервер) ведёт голову/плечи,
  таз (`rootYaw`) догоняет с задержкой (`stepTorsoLead`), остаток размазан по позвоночнику (`applyTorsoTwist`). Профиль
  `TwistProfile` {порог таза/скорость доворота/макс.скрутка/выравнивание/веса} задаётся **ОТДЕЛЬНО для стой/ходьба/бег**
  (`pe_twist[char] = {stand,walk,run}`; легаси-плоский конфиг применяется на все 3). В игре эффективный профиль блендится
  ПЛАВНО по скорости (`blendTwist`, 3 якоря @0/@speedWalk/@speedRun — как `sb` у ног/рук). Тюн — вкладка «Повороты»
  (кнопки стой/ходьба/бег переключают редактируемый режим; приставной шаг при повороте — отдельная группа `pe_gait`).
  Так же **раздельно ходьба/бег** настраиваются руки в походке (`armDown/armDownRun`, `armSh/armShRun`, …).
- **Вьюпорт поз-редактора (Blender/Unity-стиль).** По умолчанию: **скелет-манекен** (арматура — октаэдр-кости +
  шары-суставы, крупная клик-цель; `buildHumanoid({style:'skeleton'})`) + **полупрозрачное физ-тело-силуэт**
  (`ghostHuman`, физика вкл на boot). **Оружие крепится к ФИЗ-телу** (`attachWeapons(ghostHuman…)`), как в игре к
  `solid` — видно реальное игровое отображение (до инициализации физики fallback на манекен, `ensurePhysics`
  переносит). Кнопка «манекен» циклит скелет→тело→скрыт; дебаг-тумблер «боксы физтела» (`ragdoll.group`).
  **Гизмо пределов сустава** (`poseLimitGizmo.ts`): выбрал кость (FK) → на суставе рисуется допустимая зона той
  же параметризацией, что клэмп и кольца (`jointDof`: углы осей, асимм. бокс + дуга твиста; hinge = клин min/max)
  + **жёлтый индикатор** текущего положения кости (сколько до предела). Ориентация = кватернион родительской кости.
- **СТЕПЕНИ СВОБОДЫ СУСТАВА — ЭТО СКАЛЯРЫ** (`jointDof.ts`; так устроены Unity Muscle `HumanPose.muscles`,
  ozz `twist_angle`/`mid_axis`, Godot `LookAtModifier3D`, эйлер-каналы Blender). **Поза = три угла в осях сустава
  `[plane, normal, twist]`, кватернион ГЕНЕРИРУЕТСЯ (`quatFromDof`); разложение (`dofFromQuat`) — только на импорте
  и на ВЫБОРЕ кости, никогда в цикле драга.** Отсюда бесплатно: одно кольцо двигает ровно одну ось (двум другим
  нечего менять), упор — скалярный `clampDof` без ветвей и перескоков, цикл «туда-обратно» возвращает бит-в-бит,
  сингулярность ±180° недостижима. Базис фиксирован и ПРАВОСТОРОННИЙ (X=plane, Y=normal, Z=twist); варьируется
  СТРОКА порядка Эйлера (перестановка самих осей делает базис левосторонним и ломает `setFromRotationMatrix`).
  **Порядок задаётся ДВУМЯ правилами, оба выведены замером:** (1) **твист ВСЕГДА последний** ('XYZ'/'YXZ') —
  порядок в three ИНТРИНСИЧЕН, последняя буква крутит УЖЕ ПОВЁРНУТУЮ (телесную) ось, и только там твист остаётся
  ОСЕВЫМ вращением кости. С твистом в середине ('XZY') у поднятой руки его кольцо не крутило плечо, а роняло его
  вперёд/назад (ось руки уезжала с [0,1,0] на [0,0.5,±0.87]) — это ровно жалоба «руку вверх с предплечьем НАРУЖУ
  поставить нельзя, выкручивает к голове»; стало: ось руки стоит ровно, предплечье уходит вбок на ±0.99.
  (2) в середину — более узкая из plane/normal (гимбал-лок наступает на ±90° СРЕДНЕЙ оси).
  **Разложение выбирает СОВМЕСТИМУЮ ветвь** (Blender `mat3_to_compatible_eulO`): у эйлеровой тройки всегда есть
  вторая, равноценная `(внешняя+π, π−средняя, внутренняя+π)`, а `setFromQuaternion` отдаёт только каноническую —
  ту, где средний угол зажат в ±90°. У плеча сгиб ±97.4° > 90°, поэтому «рука вниз + сгиб 97°» возвращалось как
  `(82.6, 90, 180)`, и следующий драг считал приращение от ЧУЖОЙ тройки: **шесть коротких драгов по 20° ломали
  сценарий там, где один длинный работал.** Теперь берём обе ветви, разматываем к `prev`, выбираем ближайшую
  (без `prev` — «спокойнее» по сумме модулей). У ШАРНИРА ветвь одна: две оси заперты, и переброс после их зануления
  дал бы ДРУГОЙ поворот (замер: локоть переворачивался на 180°).
  ПОЧЕМУ НЕ swing-лог-карта: `rP`/`rN` — компоненты ОДНОГО вектора поворота,
  правка одной разворачивает саму ось swing (проверено, откачено); чистые swing’и вообще не образуют подгруппу
  SO(3) (`swing·swing ≠ swing`), поэтому композиция `q · R(ось,угол)` ОБЯЗАНА рождать твист — это геометрия, не баг.
  Лог-карта заманчива тем, что у неё вырождений нет вообще, и её МЕРИЛИ как альтернативу: твист там честно осевой,
  round-trip 3e-6° по всей области, НО сценарий «рука вниз, ведём кольцо сгиба» уводит руку с [0,−1,0] на
  [−0.68,−0.50,−0.54] — она всплывает и косит вбок, т.е. кольцо едет не по нарисованному кругу. Эйлер с
  совместимой ветвью держит и то, и другое: рука идёт строго в сагиттальной плоскости (x ровно 0).
- **FK-ГИЗМО ПРАВИТ СКАЛЯР, А НЕ КВАТЕРНИОН.** Кольца висят на прокси, ЗАПАРКОВАННОМ в `parentWorld · dofBasis`
  (`parkProxy`, каждый кадр — `TransformControls` снимает точку отсчёта в `pointerDown`, ДО события
  `dragging-changed`, так что «выставить на захвате» поздно). Раньше базой был `boneWorld` — кольца ехали с костью
  и расходились с зоной предела, отсюда «вижу одно кольцо, а кручу другую ось». На захвате снимаются углы
  (`beginProxyDrag`), в обработчике дельта прокси `qStart⁻¹·qNow` — чистый поворот вокруг X/Y/Z, её угол копится
  (`ringDelta`, период 4π) и кладётся в ОДИН скаляр. У шарнира две оси заперты → рисуется ОДНО кольцо.
- **FK-КЛЭМП: кости манекена ОБЯЗАНЫ слушаться пределов** (`jointClamp.ts` — ТОНКИЙ АДАПТЕР над `jointDof`).
  Кость упирается в границу конуса/шарнира (руку/локоть НАЗАД не согнуть). Тумблер «клэмп FK». Чистый модуль
  (type-only импорт `LimitView`) → node-тест (`jointClamp.test.ts`).
  **ОДНА МОДЕЛЬ НА ВСЁ — не косметика:** пока клэмп жил в swing-лог-карте, а кольца в эйлеровых скалярах, области
  различались, и это ловилось живьём — ИК парковал плечо в `plane = −143°` (конус пускал), первое же касание кольца
  зажимало до −97.4°, **поза прыгала на 46°**. Теперь солвер не может оставить кость там, где редактор её не удержит.
  Накопитель по кости (`lastValid`/`ACC_MARGIN`) УБРАН: он лечил разложение в цикле драга, которого больше нет, а в
  итеративном солвере был вреден (клэмп зовётся по несколько раз за солв). Лимит снова ЧИСТАЯ функция, как в Blender;
  `clampAngle` (ближайшая граница ПО ДУГЕ = их `clamp_angle`) остался для не-интерактивных писателей.
  **Измерено (а не предположено):** мировая предкомпозиция (`aimRootAtTarget`, `swivelRootToPole`,
  `fullBodyIk.positionsToRotations`) твист НЕ инжектит — правое умножение сохраняет локальный твистовый множитель
  (90 мировых свингов на опущенной руке: твист ровно 0.0°). Поэтому `removeTwist` в солвер НЕ добавлен: он бы
  стёр свивель (полюс локтя), ровно ту регрессию, что чинилась в Ф23.
- **Пределы суставов — ПЕР-СУСТАВ, АСИММЕТРИЧНО по осям, симметрия L/R** (`humanoidRagdoll.ts`:
  `CANON`/`JOINT_DEF`/`jointOv`/`effJoint`/`jointLimitView`). swing = `{planeMin/Max, normalMin/Max, twistMin/Max}`
  (вперёд/назад независимо, как FinalIK — назад ограничено); hinge = `{flex,hyperext}` (знак из `B[]`). Канон-id
  объединяет L/R (правишь один — обе; симм. дефолты зеркалятся авто зеркальными осями, асимметрия калибруется).
  Групповой `×` (`LIMITS`) — множитель поверх. Jolt-конус симметричен → физика берёт `max(|min|,|max|)`
  (приближение; точный асимм. предел — на манекене через клэмп/гизмо). Оверрайды — `pe_ragdoll.joints` (миграция
  старых pCone/nCone). **Голеностоп** — теперь SWING (малый ход лево-право = твист + питч + крен, не жёсткий
  hinge). **Носок** (`ToeL/ToeR`) — добавлен в риг (hinge, гнётся + предел; риг 15→17 тел). Тумблер «заземл. стоп»
  (foot-IK off → авторская ротация стопы видна на физ-теле).
- **`chars3d.ts`** — реестр персонажей 3D (класс/фракция → пол/телосложение/оружие). **Ростер БЕЗ хардкода:**
  список классов/монстров-фракций и имена берутся из СЕРВЕРНОГО конфига (`/api/config` → `classes`/`monsters`,
  кэш `localStorage['pe_config']`, тянет boot-обёртка). Внешность 3D — производная от конфига (оружие из
  `startWeaponId`, телосложение из `startAttributes`), поверх сид-дефолты + авторские правки `pe_appearance`
  (серверный pose-ключ; авторятся в поз-редакторе, вкладка «Персонаж»). Создал класс/монстра в серверном
  редакторе конфигов → он появляется и в игре, и в поз-редакторе. Единая истина — сервер.
- **DOM-панели 2D над 3D-канвасом** — те же файлы, что в 2D (`ui/domUi`+`ui/kit`+`modules/*`), регистрируются в
  `online3d` над реальным `App` (сеть): инвентарь/персонаж/скилы/мастерство/магазин/кузница/квесты/сложность/
  сундук. Панели читают `app.state.save`+`app.config`+серверные слепки, действия шлют `app.sendCmd`→сервер (та же
  валидация). Открытие: клавиши **I/K/C/J** (`DomUi.bindKeys`), город — по `[E]` у NPC (`ui:open`). 1:1 как в 2D.
- **`env3d.ts`** — окружение из `DungeonLayout`: пол/стены (инстансинг) + двери + пропсы (колонны/сундук/
  лестница) + факелы (партикл-пламя + точечный свет). Спокойные серые процедурные текстуры (плитняк/кладка).
  «Карманный свет» игрока + низкая глобалка + туман = настроение как в 2D. Масштаб: TILE=32u=1 м, стена 3 м.
  Perf: факелы = пул 10 `PointLight` (ближайшие) + **туман-кулинг** — `updateTorches` прячет группу факела за
  ~1800u (в сплошном тумане не рисуем прозрачный additive-овердро); общие геометрии столбика/сундука (реюз).
- **`vfx.ts`** — партикл-эффекты: `burst` (вспышки ударов/выстрелов), `ring`/`cast` (магия/новы), `slash`
  (дуга-взмах), `damage` (всплывающие числа урона, крит крупнее).
- **`demo.ts` + `three-demo.html`** — ранний спайк окружения (Ф0/Ф1), справочно.

## Статус (ОНЛАЙН — проверено end-to-end в браузере)
Полностью онлайновый 3D-клиент работает как 2D: регистрация/логин → создание персонажа → лобби (соло/комната) →
`joined` → **город в 3D** (NPC-столбики с подписями + портал) → спуск (портал→сложность→`descend`, соло авто-голос) →
**подземелье в 3D** (19 монстров с HP-барами, факелы) → движение (ввод→сервер→снапшот) → бой/лут/прогресс (сервер).
DOM-панели (инвентарь/персонаж/скилы/мастерство) рендерят серверный сейв, команды идут на сервер. HUD синкается.
Мультистраничная сборка: `dist/{index,game3d,pose-editor}.html`. `typecheck`×4 + `vitest`(201) + `build` — зелёные, консоль чиста.
NB: в скрытой вкладке браузер паузит `requestAnimationFrame` — гнать кадры вручную `__o.frame(1/60)` (мостик кадров).

## Грабли (дорого дались — не наступать снова)
- **⚠️ Временные объекты emscripten.** Методы, возвращающие ЗНАЧЕНИЕ (`Quat.sIdentity()`, `ShapeSettings.Create()`,
  `Ragdoll.GetBodyID()`, `Mat44.GetTranslation()` …), отдают ПЕРЕИСПОЛЬЗУЕМУЮ обёртку, а не свежий объект.
  `J.destroy()` на такой рушит аллокатор — падает НЕ СРАЗУ, а позже и в другом месте (немой `abort()`,
  «table index is out of bounds» внутри `Step`). Складывать её в массив тоже нельзя: все элементы укажут на
  последнее значение (так `ids` из 13 костей ссылался на одну стопу). Уничтожать — ТОЛЬКО созданное через `new`,
  значения — копировать сразу (`new J.BodyID(id.GetIndexAndSequenceNumber())`).
- **Настройки форм НЕ уничтожать** после `CreateRagdoll` — они держат форму живой. Формы кэшируются один раз
  (`humanoidRagdoll.ts`) и переиспользуются всеми куклами; `dispose` их не трогает (иначе следующая кукла — в
  освобождённую память).
- **`Ragdoll.SetPose` РАБОТАЕТ** в текущей сборке биндингов — `humanoidRagdoll.snapToPose()` жёстко ставит тела
  на позу-цель + обнуляет скорости на СПАВНЕ (иначе перехлёст T-поза→стойка болтает верх тела ~1с, голова летит
  до ~94). (Раньше в старом риге SetPose падал `null function` — обходили спавном на месте; теперь не нужно.)
- **Диагностика немого `abort()`**: только `jolt-test.html` — в игре стек бесполезен (машинные адреса).
  Отладочная сборка (`jolt-physics/debug-wasm-compat`) абортит РАНЬШЕ, ближе к причине.
- **Мышцы соразмерны гравитации** (g=−9.81·32): слабые моторы → корпус провисает и сутулится.
- **NaN убивает физмир безвозвратно** → `setPose` фильтрует нефинитные значения. Источник в проде —
  `facing` без значения (`PlayerInput` — это `{move, facing, attack, cast, interact}`, не `aim`).

## Экономия рендера (сделано)
Оконный кулинг ФИЗИКИ монстров (`setSimEnabled` → тела вон из `pw.step`, спящие идут `doUpdate=false` — тяжёлый
поза/ghost-апдейт пропущен), поза-LOD (без FOOT-IK вдали), физ-LOD (кинематик дальним), пул 10 факельных `PointLight`,
тени OFF по умолчанию, запекание трупов в 1 меш — были ранее. Добавлено: **адаптивное разрешение** (авто-`pixelRatio`
по FPS, лестница до **0.5×**, гистерезис 48↓/57↑, шаг раз в 0.6с). В ⚙ блок «Разрешение»: чекбокс **«авто (по FPS)»**
(def-on) + **ручной ползунок 0.5–2×** (активен, когда авто выкл; >1 = суперсэмплинг). **`camera.far` 6000→2600** (под туман: точнее z-буфер + уже фрустум теней), **туман-кулинг факелов**,
**реюз геометрий пропсов** (см. `env3d`).
- **Temporal (rate) LOD анимации монстров** (`ANIM_FULL_R2`/`ANIM_MID_R2`): при плотной толпе `ms_world` (главный поток:
  поза-пайплайн + физ-бленд + скиннинг × N монстров) — узкое место, НЕ `ms_phys`/`ms_rend`. Дальние активные монстры
  пересчитывают тяжёлую анимацию не каждый кадр — stride по дистанции (ближе `480u` — каждый кадр; до `900u` — через;
  дальше — через два). `dt` копится в `Actor.animAcc`, на strideFrame отдаётся накопленный (`driveActor(…, updateDt)`) →
  фаза/сглаживание верны (не slow-mo); дешёвые сеттеры (цель/скорость) — каждый кадр. Фаза `(animFrame+id%stride)%stride`
  разносит пачку по кадрам (нет синхронного спайка). Ближний бой (stride 1) и HP-неймплейты — как раньше, каждый кадр.

## Импорт 3D-моделей и свап по слотам (система ассетов, C1–C7)
Пайплайн «свой скинед-меш на игроке», glTF-выровненный (материал→текстуры, меш→материалы по сабмешам).

- **Данные (config-реестр shared):** секции `models` / `materials` / `textures` (см. `schemas.ts`); у предмета
  (`items.base`) — `modelId`. Бинари GLB/PNG на диске сервера (`packages/server/assets/`), отдаются `/assets/<id>.<ext>`.
- **Поз-редактор — вкладка «Модели»** (`poseModelsTab.ts`): импорт FBX/GLB → `autoBoneMap` → `makeRetargetRig`
  (наш риг ведёт импортный скелет каждый кадр) → правка карты костей/материалов → **Экспорт GLB** (+запись `models`)
  и **Экспорт по слотам** (модульный меш → послотные базы GLB через `SkeletonUtils.clone`). Редактор=конвертер:
  тяжёлый FBXLoader только тут, игра грузит компактный GLB.
- **Рантайм (`modelSkin.ts`):** слой скинов над куклой игрока (`gamePlayerDoll`, физ-ведомый `solid`):
  `resolveSlotModels(config, equipment)` — предмет.`modelId` → GLB предмета, иначе `base`-модель слота, иначе
  процедурка; ретаргет ведётся `solid`, покрытые процедурные меши прячутся (регион по кости), материалы из `assetCache`.
  Свап при смене экипа — `RagdollHandle.setAppearance(equip)`; пиры — из снапшота (`PlayerView.armorModels`, C7).
- **КОНТРАКТ ЗАГРУЗКИ послотных GLB (важно):** ось «вверх» и масштаб берём по **скелету**, не по меш-bbox
  (послотный GLB = один сабмеш, bbox врёт): upZ = доминанта вектора `Hips→Head`; scale = высота скелета source(solid) /
  высота скелета импорта. `retarget3d`: `'root'` НЕ синоним `Hips` (арм-рут AccuRIG стоит у стоп → пинил бы не таз);
  позиция корня `hips − hipRestY` (без повторного `×scale`).
- **АВТО-ENFORCE T-POSE ПРИ ИМПОРТЕ** (`retarget3d.enforceTPose`, как кнопка «Enforce T-Pose» в аватаре Unity): клипы авторены
  в T-позе (руки горизонт = «поворот 0»). Если модель забинжена в A-позе (AccuRIG/CC часто, руки ~45° вниз), клип «рука вниз 90°»
  лёг бы как 45+90 → **руки крестом, скин корёжит**. Поэтому `poseModelsTab.importAtlas` ПОСЛЕ `skeleton.pose()` и ДО замеров/
  экспорта зовёт `enforceTPose(g, map)` — доворачивает кости РУК (AIM_CHILD, обе стороны) в канон-направление (baseHumanoid),
  правя только локальные повороты. Экспортный GLB несёт T-позу в нодах, `measureBoneOffsets` читает T, рантайм грузит канон-T (как
  рыцарь). Ре-бинд в DCC НЕ нужен — достаточно переимпортировать модель. Ноги/спину не трогаем (и так канон); `legAdduct` добирает
  мелкий развал ног. Рантайм-компенсации рук (`armAdduct`) НЕТ — снята (при 46° вносила твист).
- **РЕЗОЛВ КОСТЕЙ — `boneIndex(loaded)` (НЕ traverse-byName)**: CC/AccuRIG glTF ДУБЛИРУЕТ скелет — реальная ДРАЙВ-иерархия
  (`RL_BoneRoot→…→Upperarm→Forearm`, вращаешь — двигается меш) плюс отдельные ЛИСТЬЯ-референсы `skin.joints`, висящие ПОД ней
  (зомби: 204 нода / 100 skin.joints; skin-форарм = лист, его родитель — дубль-форарм, не skin-плечо). traverse last-wins мог
  взять лист (нет детей → вращение впустую). `boneIndex` берёт кость С КОСТЯМИ-ДЕТЬМИ (узел реальной иерархии). Используется в
  measureBoneScales/measureBoneOffsets/makeRetargetRig/enforceTPose. Рыцарь работал случайно (traverse-порядок + T-поза).
- Кэш материалов/текстур: `assetCache.ts` (`getMaterial`/`getTexture`, общий `Map`, сброс на `config:reloaded`).
- Осталось: материалы контента (сейчас нейтральный silhouette), волосы под шлемом-короной (hideHair=false — 2 слоя),
  живая 2-клиентская проверка C7 (нужен редеплой сервера).

## Модульные пропорции тела + оживление ретаргета (D0–D3)
- **D0 — карта костей из ЗАГРУЖЕННОГО скелета** (`modelSkin.resolveBoneMap`): экспортные послотные GLB
  суффиксят имена костей (`CC_Base_Hip_4`), сохранённый `boneMap` не матчился → модель Т-позой парила. Теперь
  `autoBoneMap` нормализует имена загруженного скелета (сохранённый map — override). Ретаргет ведёт все кости.
- **D1 — параметрический профиль тела** (`bodyProfile.ts`, как MMO-слайдеры/MakeHuman): `BodyProfile{height,
  arm,leg,torso,girth}` — множители ДЛИНЫ (в офсеты костей, не root.scale — чтобы физ-рагдолл был в тех же
  размерах) и ОБХВАТА. `buildHumanoid(profile)` строит высокого/худого/длиннорукого; `pelvisHeight` держит стопы у пола.
- **D1 — конформ ретаргета** (`makeRetargetRig(...,source)`): длины звеньев ИМПОРТА масштабируются под скелет
  `source` (наш риг с профилем) по цепи `OUR_PARENT` → повороты 1:1, меш морфится под пропорции, стопы/кисти совпадают.
- **D2 — конструктор в редакторе**: вкладка «Модели» → «Сборка персонажа»: 5 выпадашек по слотам (всё видно
  разом через `modelSkin`) + слайдеры пропорций (живой морф). Превью 1-в-1 с игрой.
- **D3 — игра**: `makeHumanoidDoll({profile})` → solid/target с профилем, импорт-скин конформится. Присвоение
  профиля per-персонаж (из редактора/конфига) — контент-шаг.
- Осталось: физ-рагдолл пока в БАЗОВОМ размере (сильный профиль → возможен фут-слайд; ребилд рагдолла под профиль — потом);
  girth для скиннед-меша (поперечный scale кости) — грубый, форму живота/лица лучше морф-таргетами.

## Персонаж-атлас: один FBX, авто-раскладка по слотам (E)
Модульный персонаж по образцу Synty modular / MMO-гардеробов: ОДИН FBX/GLB = скелет + все части
(голова/тело/руки/ноги/волосы) отдельными объектами. Всё «садится само» — части засканы на общий скелет.
- Схема: `models` `kind:'character'` + `slots: submesh→slot`. Классификатор `modelSkin.classifySubmesh`
  (hair→helm, head→head, armor/plate/chest→chest, hand/glove→gloves, leg/boot→boots).
- Рантайм `modelSkin.setAtlas`: ОДИН GLB, ОДИН ретаргет-риг (конформ к профилю тела), submesh-тумблер по
  слоту (`visible[slot]`: имя = только этот вариант / '' = скрыть / нет ключа = все). `resolveCharacterModel`
  — приоритет над легаси послотными GLB (`resolveSlotModels`).
- Редактор (вкладка «Модели» = конструктор): импорт FBX → авто-классификация частей → ОДИН GLB-character
  в конфиг → превью через тот же `modelSkin`. UI: части по слотам (видимость), классификация (переназначить
  слот + материал per-меш), слайдеры пропорций. Экспорт-по-слотам (C6a) больше не нужен.

### Свап части по экипу + профиль тела (F)
- **Свап (F1):** `RagdollHandle.setAppearance(equipment)` строит `visible`-карту слот→сабмеш (item.modelId = имя
  сабмеша-варианта) и зовёт `setAtlas`. Надет шлем → волосы прочь (`hideHair`). `setAtlas` variant-safe: незнакомый
  modelId НЕ прячет слот (нет варианта → показать все сабмеши слота). Пиры — из `PlayerView.armorModels` (C7).
- **Профиль тела per-персонаж (F2):** `models.character.body` = {height,arm,leg,torso,girth} (partial). Игра
  (`online3d`) читает профиль из `app.config` и передаёт в `makeGamePlayerDoll` → `solid`/`target` строятся с ним,
  атлас конформится (превью редактора = игра). Слайдеры конструктора персистят в `character.body`. Рагдолл базового
  размера (сильный профиль → возможный фут-слайд — на потом).

### Атлас-на-персонаж + базовый вид + монстры (3D-items)
- **Ключ атласа `models.classId`** — generic: id класса игрока ИЛИ семья монстра (`subfaction||faction`, «один FBX на
  всех зомби»). `resolveCharacterModel(cfg, key, allowFallback)`: есть атлас с этим classId → он; иначе игрок → глобальный
  фолбэк (allowFallback=true), МОНСТР → `undefined` (allowFallback=false: нет атласа семьи → процедурка, не knight).
- **Базовый вид пустых слотов (M0):** `classes.baseAppearance{hair→helm, head, hands→gloves, body→chest, feet→boots}` =
  submesh-вариант по умолчанию. `atlasVisible` слот = `equip.modelId ?? baseAppearance[slot]`; нет ни того, ни другого →
  ключ не задаём (setAtlas покажет все submesh слота). Редактор: `fieldCustomRenderers.baseAppearance` = 5 выпадашек по слотам.
- **Гир монстра как 3D (M1-M3):** `monster-gear.modelId` (weapon→GLB kind:'weapon', armor→submesh-вариант атласа семьи,
  shield→GLB). `generateMonster` застолбляет на `ScaledMonster` (летит клиенту в `FloorInit.monsters[].def` целиком):
  `atlasKey`, `weaponKey` (форма процедур.меша, `weapon3dKeyFromEquipment`), `weaponModelId/shieldModelId`, `armorModels{chest,helm}`.
  Клиент (`online3d`): монстру — `atlasKey` + `weaponModels` + `setAppearance(armorModels)` (зеркало peer-пути). Скин
  монстра разблокирован (был гейт по `classId` → теперь `classId ?? atlasKey`).
- **Выпадашка `item.modelId` в редакторе** фильтруется по виду/слоту (`modelIdOptions`): armor→submesh-варианты атласов
  слота; weapon→models kind:'weapon' по `weaponType===weaponClass`; shield→weaponType='shield'. Обслуживает и предметы, и monster-gear.
- **Оружие GLB (Ф3):** `attachWeapons(human, weapon, models?)` тег `weaponModelId`; `applyWeaponModels` свапит процедурных
  детей на GLB (хват/хост-синк целы). Оружие ОБЩЕЕ на всех, per-char только хват (`pe_grip`). Пиры/монстры на ПРОД — редеплой.
- **Устойчивость:** `loadAssetConfig` не кэширует провал `/api/config` (ретаит), иначе кукла зависла бы с пустым
  конфигом и атлас не появился бы.

### Напольный декор + суб-тайловая коллизия (сервер-авторитетно)
Внутрикомнатные колонны/очаги/статуи/пропы: коллизия по **форме меша**, а не по целому тайлу 1×1. Сервер расставляет
и считает, клиент только рисует. (Стеновые колонны `role:'pillar'` — как раньше, клиент/cellHash, без коллизии.)
- **Ядро (shared):** `Obstacle`(круг/бокс) в `WorldState`; единственный резолвер `moveWithCollision(...,obstacles?)`
  выталкивает актёра-круг наружу; `blocksSight` → препятствие перекрывает и LoS (`lineOfSight`).
- **Расстановка (shared `dungeon/decor.ts`):** `placeFloorDecor` детерминированно кладёт `role:'decor'/'prop'`-объекты
  по комнатам (footprint-резерв, грид не меняем → проходимость цела) → обогащённый `DecorObject{kind:'obj',objectId,rot,footprint}`,
  едет клиенту в `FloorInit.decor`. `obstaclesFromDecor` деривит препятствия из коллайдера. Встроено в `generateFloor(spec,prefabs,decorSpecs)`; `room.ts` собирает `decorSpecs`→`obstacles`→`enterFloor`.
- **Рендер (`env3d.ts`):** `EnvKit.props: Map<objectId,PropVariant>`; `buildEnvironment` инстансит `kind:'obj'`-декор.
  Мульти-тайл (footprint N×M) масштабируется общим `unitScale`. `online3d.propSpecs(biome)` грузит role decor/prop.
- **Коллайдер из меша (`server/glbMeshBbox.ts`):** невидимый меш `collider*` в GLB → XZ-bbox → доли тайла (100ед=1тайл, Z-up).
  Извлекается на аплоаде (`/api/dev/assets`), редактор пишет в `models[].collider`. Форму (круг/бокс) выбирает объект.
- **Свет из меша:** невидимый меш `light*` → `PointLight` в его позиции (кормит общий пул факелов). Параметры — `objects[].light`.
- **КОНВЕНЦИИ авторинга GLB декора:** меши `collider*` (коллизия) и `light*` (свет) невидимы в игре; масштаб 100 ед = 1 тайл
  (Z-up Max); галки `blocks`/`blocksSight` + `footprint` на объекте. **Влияет на СЕРВЕР → онлайну нужен редеплой прод.**


## Поз-редактор как ИСТОЧНИК АНИМАЦИЙ для любого движка (Ф1–Ф2)

Процедурная походка (`StepPlanner`/`PoseDriver`) больше не обязана жить в клиенте. Редактор **запекает** её
в обычные покадровые клипы и отдаёт glTF/GLB — дальше клип играет любой движок своими средствами.

### Пайплайн

```
PosePlayer (та же математика, что в игре)
  └─ clipBake.bakeGaitToClip     — цикл ловится по ноге, фейсинг вычитается, ключи прореживаются
       └─ Clip (clipModel.ts)    — ОДНА модель клипа на редактор и игру
            ├─ clipPoseAt        — воспроизведение (наше, единственное: и в редакторе, и в игре)
            └─ clipToAnimation   — THREE.AnimationClip (ТОЛЬКО формат вывоза)
                 └─ clipExport   — GLB с анимациями + JSON-манифест
```

### Контракт с принимающей стороной (любой движок)

| Что даёт редактор | Что делает клиент |
|---|---|
| Клип = **только повороты костей** + дорожка `Hips.position` | играет клип; корневое движение — своё |
| Клипы **in-place**: `Root` не анимируется, фейсинг вычтен из `Hips.y` | сам поворачивает персонажа |
| Манифест: имя, длительность, `loop`, `kind` (`locomotion`/`idle`/`hit`/`skill_hit`/`combat_idle`) | строит блендер/стейт-машину |
| `unitsPerMeter: 32` (наш TILE) | масштабирует под свои единицы |
| Профиль имён костей на выбор: канон (Unity Humanoid) / как в модели / UE5 Mannequin / Mixamo | ретаргет не нужен, если профиль совпал |
| — | **свой** foot-IK и **свой** рагдолл: наши физ-каналы (`__match`/`__pinKp`) в экспорт не едут |

### Грабли, стоившие отладки

- **`GLTFExporter` тихо выбрасывает дорожку, у которой имя не резолвится в узел.** Переименовывать надо
  ОБЕ стороны — и дорожки, и узлы скелета (`exportClipsToGLB` делает это временно и откатывает).
  `checkTracksResolve` ловит несовпадение ДО экспорта, редактор показывает «⚠ потеряно дорожек: N».
- **Префикс `mixamorig:` в экспорт НЕ ставим.** three разбирает имя дорожки как путь, где `:` — разделитель:
  `parseTrackName('mixamorig:Hips.quaternion') → nodeName 'Hips'`. Узел `mixamorig:Hips` не находится, и
  из 24 каналов выживает 1. Голые имена узнаются ретаргетерами не хуже (мы сами этот префикс стрипаем).
- **`walk_back` обязан задавать `yaw: 0`.** Без него фейсинг берётся ПО ДВИЖЕНИЮ, и «ход назад» становится
  «развернулся и пошёл вперёд» — та же походка под другим именем. Признак: период совпадает с `walk_fwd`.
- **Разогрев перед съёмом обязателен** (~2 с): у планировщика инерция (планты, подшаг, torso-lead).

### Измерено

Паритет запечённого клипа с живой походкой (порог прореживания 1.5°): **макс. 0.85° на шаге, 1.36° на беге**.
Компрессия: 86 кадров цикла → 45 ключей (шаг), 50 → 34 (бег), стойка 31 → 2.
Порог 0.5° даёт 0.26–0.48°, но почти не сжимает (73 ключа); 3° — 34 ключа при 1.8°.

**Поворотов в наборе нет осознанно:** разворот — это вращение КОРНЯ, а клипы in-place. Появятся вместе
с треками `Root` (см. план).

### Два режима интерфейса

Тумблер в тулбаре (`pe_ui`). Не два интерфейса, а один с прогрессивным раскрытием:
Про ДОБАВЛЯЕТ панели (лимиты суставов, моторы, PHYS, тюнинг походки, дорожки тайм-лайна,
пальцы поштучно, замеры телосложения по регионам), ничего не переставляя. В Простом эти настройки
продолжают действовать со своими значениями — просто не показываются.

### Разделение каналов (инвариант — не смешивать)

| Канал | Где живёт | Едет ли в клип |
|---|---|---|
| Анимация | `pe_clips` | да, это и есть клип |
| Телосложение | `pe_morph` / `pe_appearance` | нет — свойство персонажа |
| Хват кисти | `pe_gripposes` | нет, накладывается поверх |
| Пределы/физ-профиль | `pe_ragdoll` (в т.ч. `physrig` — набор тел) | нет, инструмент авторинга |

Смешаешь — анимация перестанет быть переносимой (клип «толстого» не ляжет на худого).
Проверяется тестом `clipPortable.test.ts`.

**Офсет таза — тоже канал, и он ДЕЛЬТА.** `__hipsD` = смещение таза относительно rest-высоты ЭТОГО тела
(`humanoid.hipsRest`), а не абсолютная позиция. Читать только через `hipsOffset(pose, restY)` — он же
понимает легаси-ключ `__hipsP` (абсолют) и приводит его к той же дельте. Иначе «присед на два юнита»
у среднего персонажа на высоком читался бы как «стоит на цыпочках».

### Набор физ-тел

Не константа, а данные (`physRig.ts` + `pe_ragdoll.physrig`): пресеты `Минимум (13)` / `Базовый (17)` /
`+ пальцы (47)` и галки по телам в Про. Физика в редакторе — **инструмент авторинга**: на экране один
персонаж, результат всё равно запекается в клип, поэтому объём физики выбирает автор, а редактор честно
показывает цену (тел, суставов, замер шага).

Одна вещь, которую нельзя забыть при выключении тела: в потомка переезжает не только РОДИТЕЛЬ (ближайший
включённый предок), но и ЦЕПЬ РЕТАРГЕТА — углы исчезнувшего тела обязаны войти в его цель, иначе тело
целится мимо позы. Это и есть содержимое `resolvePhysSet`.

### Вид скелета: почему шары-суставы «дышат»

Шар-сустав держится **постоянного экранного размера** (`scaleJointsToScreen`, ~7px), как контроллеры в
Blender/Cascadeur. Это не украшение: у шара был жёсткий минимум радиуса 1.6 юнита, а фаланга — 0.8–1.9
юнита ДЛИНОЙ, то есть шар был крупнее кости, кисть превращалась в ком, и попасть по пальцу мышью было
нельзя. При постоянном экранном размере подлёт к кисти сам делает шары мелкими относительно пальцев.
Ширина кости-октаэдра по той же причине имеет **относительный** пол (`boneWidth`): при `len >= 4` он равен
прежним 0.8 (тело не изменилось ни на пиксель), ниже — сжимается вместе с костью.

### Режим «Хват»

Кнопка `✋ хват` в тулбаре (вне зависимости от Простой/Про): камера подлетает к кисти, кликабельны
**только фаланги**. Вне режима по пальцам кликнуть нельзя вообще — иначе, целясь в кисть, постоянно
хватаешь фалангу. Видимость от режима не зависит: пальцы строятся, если они есть в модели
(`modelsTab.hasFingers()`), включены кнопкой `✋` в дереве костей, или включён режим хвата — три
независимые причины, объединённые OR (`wantFingers`), чтобы выход из режима не сносил чужие пальцы.

### Геометрия скелета при загруженной модели

**Правило (как у Unity Avatar / UE5 IK Retargeter / HumanIK):** семантика (какая кость `LeftUpperArm`,
цепи, пределы) — каноническая; **геометрия — всегда из импортированного скелета**; нормализуется только
поза. Ни один боевой инструмент не рисует канон-риг, отмасштабированный поверх чужого меша.

**Морф двигает И кости, И меш** (как параметры тела в MetaHuman). Механизм: риг-источник `asmSrc`
строится ТЕМ ЖЕ профилем, что манекен (`atlasProfile()` = телосложение атласа × морф персонажа), а конформ
длин в `makeRetargetRig` тянет кости модели под него. Если построить `asmSrc` без морфа — морф поедет на
скелет и не поедет на меш: замерено, все кости были ×1.08 от модели.

Три вещи, которые тихо портили замер (каждая врала и при морфе = 1):
- **Обнуление Z у осевой цепи** резало ДЛИНУ (у CC-бинда шея 5.21 → 4.63, −11%) и конформ переносил
  укорочение на модель. Замеренный офсет берётся как есть.
- **Несмапленная кость убивала офсеты своих ДЕТЕЙ.** У CC два спайна, `UpperChest` не мапится — и
  `Neck` с обеими ключицами падали на хардкод (4 кости из 22 посреди торса). Теперь недостающее звено
  ставится по ДОЛЕ ДЛИНЫ между ближайшим смапленным предком и потомком, как FK-цепи в UE.
- **Нормировка к литералу 57** (это Y головы, а размах базы = 56) давала +1.8% на любом импорте.

**Длины ноги и заземление.** `footIk` читает длины бедра/голени с самого рига, а не из констант: иначе
солвер ставит колено на 15 юнитов вдоль бедра, которое не 15 длиной, и остаток каждый кадр уходит
в сдвиг КОРНЯ — «заземление съезжает». Осталось расхождение-долг: `pose.ts` (гейт) и рэгдолл держат
свои копии длин ноги.

### Пальцы: откуда берётся геометрия и вокруг чего они гнутся

Три вещи, которые легко сломать по отдельности и которые дают один и тот же симптом «пальцы не работают»:

1. **Геометрия — из модели.** `measureBoneOffsets` идёт по `OUR_BONES` + `OUR_FINGERS` (родители фаланг —
   `FINGER_PARENT`). Если этого не сделать, `posOf` тихо падает на хардкод `FINGER_GEO`, и от правильного
   запястья висит чужая процедурная кисть. Выпрямление T-позы и конформ длин фаланг НЕ касаются — там они
   вредны, «канонического направления пальца» не существует. Уже импортированные модели лечатся сами при
   загрузке (замер по бинд-позе, дописываются только отсутствующие ключи).
2. **Ведение модели.** Риг-источник `asmSrc` обязан строиться с `fingers: true`, иначе повороты фаланг
   некуда копировать и `RetargetRig.drive` молча их пропускает (`driver.bones.get(...) === undefined`).
3. **Ось сгиба — выводится, а не зашита** (`fingerAxes.ts`): `plane = along × palmInward`, где `palmInward`
   определяется по стороне, с которой сидит большой палец. Зашитая ось врала даже на нашем манекене
   (пальцы разложены по Z, ладонь тонкая по Y → сгиб вокруг Z, а в коде стоял Y — палец уезжал ВБОК).

**Правило знаков** (закреплено тестом «зеркало»): `mirror(R(a,θ)) = R(Ma, −θ)`. Ось сгиба сама зеркальна
(`plane_R = −plane_L`), поэтому у СГИБА пер-стороннего множителя быть не должно; ось «вдоль пальца»
полярна, поэтому у противопоставления большого пальца — должен. Легко перепутать в обе стороны.

**Хват не должен складываться с биндом.** Хват задаёт сгиб «от ПРЯМОГО пальца», а rest-поза — это бинд
модели, и он у разных моделей разный: где-то пальцы прямые, где-то заметно поджаты. Поэтому из хвата
вычитается `bindCurlOver` — насколько ЭТА кисть согнута СИЛЬНЕЕ канонической. Отсчёт у каждого сустава
свой: проксимальная — от пястной кости (запястье→корень пальца, это и есть MCP и самый большой ход),
средняя — от проксимальной, дистальная — ОЦЕНКА по средней (кости-кончика у CC нет, `L_Index3` без детей).

Именно ИЗБЫТОК, а не абсолютный угол: у большого пальца пясть идёт под углом к фаланге, и на нашей
собственной прямой кисти это даёт 23°. Вычти их — и хват недобирал бы 23° на любой модели, включая
процедурную. Замерено на `knight_05`: указательный MCP 13.2°, PIP 26.4°, DIP 26.4°, большой MCP 39.9°.

### Слайдер «ладонь ↔ хват» и принудительное выпрямление (Ф16)

Бинд-кисть модели — ЭТО НЕ «раскрытая ладонь», и ЛЕВАЯ С ПРАВОЙ ПОДЖАТЫ ПО-РАЗНОМУ
(`knight_05`: MCP указательного 13.2° слева и 21.7° справа; средний избыток по кисти ≈ 22°, максимум 40°/53°).
Пока ноль слайдера означал «бинд как есть», один и тот же пресет давал две разные кисти, и никакой
пресет этого не лечил. Теперь локальный доворот — `max·close − bindCurlOver`:

* `close = 0` — палец доворачивается **НАЗАД** на свой бинд-сгиб → выпрямленная ладонь на ЛЮБОЙ модели;
* `close = 1` — ровно угол пресета, одинаковый у обеих кистей;
* между — линейно. Множитель `close` стоит ТОЛЬКО у пресета, вычитание — безусловное.

Клэмпа `Math.max(0, …)` быть НЕ ДОЛЖНО: у кисти, поджатой сильнее пресета, правильный ответ —
ОТРИЦАТЕЛЬНый доворот (разогнуть до целевого угла), а клэмп снова расходил бы Л и П.

Следствия, которые легко пропустить:

* **Свой хват** (готовые углы) тоже слушается слайдера — через slerp от `straightHandPose`
  (раньше слайдер на своём хвате молча не делал ничего).
* **Зеркало кисти** — `mirrorHandPose`: кроме канон-знаков `[x, −y, −z]` добавляет разницу бинд-избытков
  вокруг оси сгиба целевой фаланги. Голое зеркало углов даёт разный АБСОЛЮТНЫЙ сгиб (8° в MCP на knight_05).
* **Запечённые фаланги в клипах глушат хват.** Кадр с явными фалангами хват не перебивает — это дизайн,
  но старые клипы держат углы ПРОШЛОЙ формулы (замерено: все 15 фаланг правой кисти `idle_axe` забиты
  почти-нулями → рука намертво в бинде, MCP 78°, слайдер на неё не действует и выглядит сломанным).
  Панель хвата показывает число таких кадров и кнопку `✕ отдать пальцы хвату`.
* Строка «бинд модели поджат: Л …°, П …°» (`bindCurlReport`) — диагностика: без неё выпрямление
  происходит молча и «кисть в редакторе не как в модели» читается как баг.

Остаток, который выпрямление НЕ трогает — боковой развод (веер ладони): это ФОРМА кисти,
меш сидит на нём. Замерено на `knight_05` при `close = 0`: PIP ≤ 4° у всех пальцев кроме левого
указательного (16°) и больших (18°) — это их собственная геометрия, а не согнутость.

### Один канал, плоскость большого, плывущие пределы (Ф17)

Три вещи, которые выглядели как один баг, а оказались тремя разными.

**1. Хват — ЕДИНСТВЕННЫЙ источник позы пальцев.** Раньше кадр с явно записанными фалангами
хват не перебивал, а `readPoseFull` писал в кадр всё, что ОТЛИЧАЕТСЯ от текущего хвата. Любая правка
формулы хвата превращала старые совпадения в мёртвые ключи, глушащие канал навсегда. Именно это
читалось как «на левой хват работает, на правой нет, причём только на топоре»: в `idle_axe` все 15 фаланг
правой кисти были забиты почти-нулями (MCP 78°). Теперь фаланги в клип НЕ ПИШУТСЯ вообще (только
на экспорте, `bakeGripIntoClip`), старые вычищаются миграцией на старте, а ручная правка кисти
сохраняется кнопкой «★ запомнить правую/левую» в тот же канал.

**2. Тип хвата — ВСЕГДА из ключа оружия, списка пресетов в UI нет.** Список был не просто лишним:
`weaponGripBind()` записывал `defaultWeaponGrip(weapon)` в конфиг при ПЕРВОМ же показе панели, и дальше
смена оружия хват уже не меняла. Действующий хват считает `effectiveWeaponGrip` — база пересчитывается
от оружия, в конфиге живут только слайдер и явно сохранённые кисти (`c_*`).

**3. У большого пальца СВОЯ плоскость сгиба.** Его пясть развёрнута на ~90° (противопоставление), поэтому
он сгибается ПОПЕРЁК ладони (кончик к мизинцу), а не «вниз»: `plane = нормаль ладони`, ортогонализованная
к фаланге. Берётся `palmN`, а НЕ `palmInward`: первый — псевдовектор (знак зеркалится сам), второй полярен
и потребовал бы пер-стороннего множителя. Замерено на knight_05: угол между осью большого и осью
указательного стал 86°/89° (Л/П) вместо почти-нуля; указательный со средним — 6°/15°, как и должно.

### Концы слайдера снимаются руками, у большого нейтраль — его бинд (Ф18)

Процедурная математика угадывает хват на любой модели «в общем верно», но наверняка — нет. Вместо того
чтобы нагромождать проверки на каждую особенность чужого рига, ОБА КОНЦА СЛАЙДЕРА МОЖНО СНЯТЬ
С ЖИВОЙ КИСТИ: крутишь фаланги FK в режиме `✋ хват` и жмёшь `✋ снять ладонь` / `✊ снять кулак`.

Снятый конец воспроизводится БИТ-В-БИТ: никакого вычитания бинда и клэмпов поверх — иначе
«выставил глазами и снял» перестаёт быть предсказуемым. Неснятый конец остаётся процедурным
(выпрямленная кисть / пресет по оружию), и когда ОБА процедурные — работает старый аналитический
путь (`gripToPose`), а не бленд двух поз: точно и без регрессий.

**У большого пальца бинд-избыток НЕ СЧИТАЕТСЯ вообще** — и это не костыль, а граница применимости
самого приёма. Для четырёх пальцев анатомический ноль — ПРЯМОЙ палец, и канон-риг его точно
воспроизводит, поэтому разность = согнутость модели. А наш процедурный «большой» — просто ещё один
палец, сдвинутый в угол ладони (пясть не развёрнута, оппозиции нет), так что разность с ним меряла
разницу ДВУХ РИГОВ. Замерено на knight_05: −29° — и окно предела большого съезжало в сгиб
(−31°…+124° вместо −60°…+95°), и отвести палец в сторону было НЕКУДА — FK-клэмп упирал в границу.
У большого нейтраль — ЕГО СОБСТВЕННЫЙ БИНД (художник лепит кисть в покое).

И сам диапазон большого асимметричен В ДРУГУЮ СТОРОНУ, чем у прочих: у них отрицательная сторона —
крохотный переразгиб (−25°), а у большого это лучевое отведение на все 60° — тот самый увод «в сторону»,
которым ставится раскрытая ладонь (плюс ладонное отведение ±50° вместо ±35°). Проверено живьём:
окно стало −60°…+95°, увод на 45° и 55° проходит клэмп нетронутым.

**Пределы фаланг сдвигаются на бинд-избыток.** Числа в `fingerJoints` — анатомия от ПРЯМОГО пальца
(переразгиб −25°, сгиб +95°), а локальный угол кости отсчитывается от rest, то есть от БИНДА. У CC бинд
поджат на 20–50° → выпрямление вылетало за `planeMin`, а кулак не добирал до `planeMax`. `extraLimitView`
вычитает `bindCurlOver` из обеих границ — «прямой палец» всегда внутри зоны, «полный кулак» ровно на
её краю, на любой модели. Боковой развод и твист НЕ сдвигаются — их не выпрямляют.
Живой замер на knight_05: при close = 0 / 0.5 / 1 худшая из 30 фаланг имеет 25–35° ЗАПАСА до границы.

**Ловушка имён:** у CC/AccuRIG на СТОПЕ есть `L_IndexToe1`/`L_MidToe1`/`L_RingToe1`/`L_PinkyToe1` — без
отсечки `toe` они занимают слоты фаланг кисти (замерено: 8 костей из 30). Тот же класс, что `fore` → `Forearm`.

### Пястные кости, анатомия большого, хват на призраке (Ф19)

**Кость рисуется к КАЖДОМУ ребёнку, а не только к первому.** Скелет-вид брал `kids[0]`, и у кисти
появлялась РОВНО ОДНА пястная кость — к большому пальцу (он первый в `FINGER_GEO`), а четыре
остальные пальцы висели в воздухе. Отдельных костей-пястей в риге нет и быть не может (ни у Unity
Humanoid, ни у CC/AccuRIG — драйвить их нечем), но СЕГМЕНТ запястье→костяшка задан офсетом
фаланги и рисуется бесплатно. Клик по пясти выбирает КИСТЬ — именно она этот сегмент и крутит.
Попутно появились два бедра на тазе и две ключицы на верхней груди — как в Blender/Maya.

**У большого ТРИ РАЗНЫХ СУСТАВА, а не «base / не base».** В именах Unity у него те же
Proximal/Intermediate/Distal, но анатомически это пястная (CMC), проксимальная (MCP) и дистальная (IP):
фаланг у большого всего две. Общие «широкие» числа Ф18 давали клин шире анатомии на всех
трёх сразу. Стало: CMC — сгиб −45…+50°, развод ±45°, твист ±35° (седловидный: отведение и оппозиция);
MCP — −10…+55°, ±10°, ±5° (почти шарнир); IP — −20…+80°, ±3°, ±5° (шарнир с переразгибом).

**ХВАТ НАДО КЛАСТЬ И НА ПРИЗРАКА** — именно он ведёт МЕШ, когда физика включена
(`modelsTab.drive(physOn ? ghostHuman : human)`). Фаланги не имеют физ-тел в базовом наборе, поэтому
`renderRagdollGhost` их не трогает и они остаются в БИНДЕ. Замерено на knight_05: фаланга призрака
расходилась с манекеном на 5.8°, кончик — на 1.1u, причём НЕЗАВИСИМО от `PHYS.match` (при match = 1
то же число) — то есть это был НЕ бленд физики, а просто недоставленный канал. Со стороны:
«включаю физику — меш съезжает, кости стоят». Хват теперь кладётся на оба рига и повторно — после
каждого шага призрака (он пересобирает позу покадрово). Проверено: 5.8° → 0.00°.

### Видимые кости = кости модели (Ф20)

Редактор рисовал ПРОЦЕДУРНЫЙ скелет, а меш деформируют другие кости — настоящие, внутри GLB.
Так не делает никто: Unity в настройке аватара рисует кости модели сквозь меш; UE5 IK Retargeter
держит во вьюпорте оба скелета и в Edit Mode правит реальные кости; MotionBuilder кладёт эффекторы
контрол-рига поверх скелета персонажа; в Blender контрол- и деформ-кости живут в ОДНОЙ арматуре.

**Главный замер, который всё перевернул.** Ретаргет ведёт кости модели И ПОЗИЦИОННО (`posDrive`,
[retarget3d.ts](retarget3d.ts)), то есть суставы модели НАСИЛЬНО садятся на суставы ВЕДУЩЕГО рига.
С выключенной физикой расхождение тела с манекеном — ровно **0.000u** (даже при сильном пер-костном
морфе), пальцы 0.01u. Значит всё, что выглядело как ошибка ретаргета или бленд физики, на самом деле
было одним: **ведущий риг не тот, который мы показываем** — при включённой физике меш ведёт
ЗАЗЕМЛЁННЫЙ призрак, а виджеты читали НЕзаземлённый `human`.

Стало три вещи:

1. **`asmSrc` строится ТЕМ ЖЕ, чем манекен.** Раньше — `curAtlas()?.boneScale` без пер-костного морфа
   персонажа (`profile` доезжал через `charProfile`, `boneScale` — нет). Добавлен `charBoneScale`.
2. **Виджеты берут ПОЗИЦИЮ из `viewRig()`** — того же рига, что в `modelsTab.drive(…)`: гизмо предела,
   кольца FK, полюса IK, фокус камеры, маркеры стоп. На `human` СТРОГО остаётся всё, что ПРАВИТ позу
   (`syncEff`/`solveRig`, дельта-математика прокси, `decomposeToLimit` и кватернион родителя) — эта математика
   верна только в его фрейме. Плюс `placeLimitGizmo()` переехал ПОСЛЕ `drive` (до него локальные
   трансформы костей модели держат вывод прошлого кадра).
3. **`boneView.ts` — скелет рисуется по НАСТОЯЩИМ костям.** Плоская группа в мировых координатах
   (иерархию строить не надо и вредно: у модели между нашими костями сидят промежуточные узлы).
   Топология — НАША (`parentOfOur`), сегмент идёт до ближайшего СМАПЛЕННОГО предка, иначе шея повисла бы
   в воздухе (у CC/AccuRIG нет `UpperChest`). Кости, которых у модели нет, НЕ рисуются — они и меш не
   двигают. Ключи `userData` (`bone`/`joint`/`jr`) — ТЕ ЖЕ, что у манекена, поэтому выбор, подсветка,
   список костей и `scaleJointsToScreen` работают без правок.

Проверено живьём на knight_05: 51 кость (всё, кроме несмапленного `UpperChest`), расхождение
нарисованный сустав ↔ кость модели = **0.0000u** и с физикой, и без; переключение физики двигает
КОСТИ ВМЕСТЕ с мешем (таз 41.11 → 40.28); реальный клик мышью по кости модели выбирает её; свап
атласа пересобирает вид без падений.

**Попутно:** у тумблера физики появилась ЕДИНАЯ точка правды `setPhys(on, byUser)`. Состояние
выставлялось из шести мест, метку кнопки обновляло одно, а стартовое `ensurePhysics().then(…)`
резолвится через секунды (WASM) и молча включало физику поверх ручного выключения. Кнопка
показывала «выкл», пока меш вёл призрак — ловушка для любого замера.

**ЗАЗЕМЛЕНИЕ ПОПАДАЕТ В ЗАПИСАННУЮ ПОЗУ** (Ф20.5, решение юзера: «заземление в поз-редакторе
как раз и надо, чтобы делать позы, которые уже полу-соответствуют, а в игре подгонится, если пол кривой»).
Сделано ОДНИМ ШВОМ внутри `readPoseFull`: заземлить → прочитать → вернуть как было. ПОКАДРОВО НЕЛЬЗЯ:
`gs.off` — интегратор без затухания, заземление крутилось бы на собственном выходе, после первого кадра
стёрло бы авторские углы ног и отменяло правки IK. Свой `GhostGround` (делить с призраком нельзя —
два рига на одном интеграторе удваивают шаг) и `baseY` от `hipsWorldY()`, независимый от заземления.
Проверено: читается колено `[0.328, 0.059, 0.033]` при авторском `[0.335, 0, 0]`, а манекен после
чтения восстановлен бит-в-бит. `__hipsD` считается от `hipsRest`, а заземление двигает КОРЕНЬ — не течёт.

**Что РАСХОЖДЕНИЕМ ОСТАЛОСЬ** (замерено, не трогалось): ЗАЗЕМЛЕНИЕ СТОП применяется
ТОЛЬКО к призраку (`renderRagdollGhost(…, footGround)`), манекен не заземляется никогда → корень
призрака выше на 0.26u, колено разошлось на 18.4°, бедро 9.4°, стопа 9.0°. Это тоже НЕ бленд
(match не влияет). Лечится заземлением манекена тем же `groundFeet`, НО: манекен — источник
авторской позы для `readPoseFull`, и IK-поправка ног запеклась бы в записываемые кадры. Требует
отдельного шва (снимок авторской позы до заземления), поэтому сделано НЕ было.

### Один инструмент, IK — тумблер, корпус скручивается (Ф21)

Жалоба: «в ИК можно двигать, в ФК крутить — а надо и то и другое сразу, как в каскадёре» и «в ИК
двинешь — всё тело раскорячивает». Оказалось — ПЯТЬ разных причин, и каждая ловилась замером.

**1. Солвер решал ВЕСЬ скелет** от перетаскиваемой точки. Замерено на knight_05: тянешь
ПРАВУЮ кисть на 3u — ЛЕВАЯ уезжает на **13.32u**, голени на 6.5u, носки на 6.2u. Лечится
МАСКОЙ АКТИВНЫХ КОСТЕЙ (`solve(…, active)`) — прямой аналог **Chain Length** в IK-констрейнте
Blender, где сказано прямым текстом: Chain Length = 0 гонит солвер до корня и тянет спину с
торсом — «обычно это не то, что нужно». Кость вне маски НЕ сеется, НЕ участвует в FABRIK и
НЕ получает новый кватернион. Корни цепей: кисть → ключица, стопа → таз. Фаланги — НИКОГДА
(ими владеет канал хвата, Ф16–Ф19). После: левая кисть 0, спина 0, голова 0, стопы 0, пальцы 0.

Запиненные цепи входят в маску ТОЛЬКО когда в ней есть ТАЗ. Это оказалось главным: стопы
запинены по умолчанию, и вместе с ногами в маску попадал `Hips` — таз становился СВОБОДНЫМ,
и тяга кисти уносила всю фигуру. При неподвижном тазе запиненная стопа и так не уедет.

**2. Тяга кисти ДВИГАЛА ТАЗ.** В `objectChange` стоял `moveHips(дельта × bodyFollow)` — КАЖДЫЙ кадр
драга весь персонаж ехал на 0.45 смещения руки, а запиненные стопы держали. Убрано: таз теперь
двигается только СВОЕЙ ручкой — как в Cascadeur, где таз отдельный контроллер.

**3. КЛЮЧИЦА РАБОТАЛА ВТОРЫМ ПЛЕЧОМ** — вот почему корпус не скручивался. `RETARGET` сливает
ключицу с плечом в ОДНО физ-тело (`ArmR: [RightShoulder, RightUpperArm]`), а `limitViewForBone` спрашивал
сначала физ-риг — и ключица получала ПЛЕЧЕВЫЕ диапазоны ±97°/±69°. Замер тяги кисти
поперёк тела: **ключица 89.5°, спина 0°**. Две правки: явная таблица теперь ВЫИГРЫВАЕТ у
физ-рига, и в неё добавлена анатомичная ключица (выведение ±20°, подъём ±15°, осевое ±10°).
После: ключица 14–20°, остаток уходит выше по цепи — в корпус.

**4. PULL по ФАКТИЧЕСКОМУ НЕДОЛЁТУ, а не по расчётной длине цепи.** Модель — Maya HumanIK
(«эффект Pull виден, только если вытянутой руки не хватает»). Первая версия сравнивала дистанцию с
суммой длин звеньев — то есть видела только «далеко» и НЕ видела «не в ту сторону», а главный
случай юзера (рука поперёк тела) по дистанции ДОСТИЖИМ. Теперь: решили конечность →
посмотрели, где кисть ФАКТИЧЕСКИ оказалась; не дошла — подключаем корпус.

**5. Корпус СКРУЧИВАЕТСЯ, а не гнётся FABRIKом.** Скрутка идёт через `twistTorso` — тот же шов,
что и в походке (веса по Spine→Head, сумма 1), но АДДИТИВНО и БЕЗ таза: в редакторе таз авторский.
Пробовали отдать корпус FABRIKу (добавить в маску) — ЗАМЕР СКАЗАЛ НЕТ: недолёт стал ХУЖЕ
(6.96 → 9.38), спина получила Chest `[10, 20, 24]` — боковой наклон с роллом вместо скрутки, а левая
кисть улетала на 43u. Причина известна и описана у авторов FABRIK: на развилке (две руки + шея
от UpperChest) суб-база усредняется. Поэтому спина FABRIKом НЕ решается вовсе — это замеренное
решение, а не недоделка. Не дотянулся скруткой — честно не дотянулся (Pull &lt; 1 в HumanIK так же);
наклониться — ручка таза.

Замерено (правая кисть к точке перед левым плечом, стопы запинены):

| Pull | недолёт | Spine y | Chest y | UpperChest y | Head | стопы | таз |
|---|---|---|---|---|---|---|---|
| 0 | 8.81 | 0° | 0° | 0° | 0 | 0 | 0 |
| 0.45 | 5.02 | 4° | 7° | 7° | 0 | 0 | 0 |
| 1 | **0** | 8° | 16° | 16° | 0 | 0 | 0 |

А при цели В ПРЕДЕЛАХ руки корпус стоит ровно на нуле при любом Pull — точно как в HumanIK.

#### Один инструмент вместо двух режимов

`mode: 'fk' | 'ik'` ушёл. Остался `ikOn` — ПРОСТО ТУМБЛЕР инверсной кинематики. Клик рейкастит
И ручки, И кости сразу (ручки первыми — они мельче и рисуются поверх). Почему это важно было:

* шесть мест в UI вынужденно дёргали `setMode('fk')` (режим хвата, оружие, маркер, список костей);
* гизмо предела в IK не показывалось НИКОГДА — оно рисуется по `selected`, а `selected` в IK всегда `null`;
* `setMode` был разрушительным (сбрасывал выбор, подсветку, прокси) — тумблер не сбрасывает ничего.

**Кольца по удержанию Shift**, а не вторым постоянным набором ручек: держишь — гизмо становится
кольцами КОСТИ (выбранной или конца активной ручки), отпустил — вернулись стрелки. Со снапом
(тот же Shift) конфликта нет: снап важен ВО ВРЕМЯ драга, кольца — ДО, гейт по `gizmo.dragging`.

Тумблер ВЫКЛ: ручки конечностей и полюсов скрыты, солвер не зовётся, чистый FK. **Ручка таза
остаётся всегда** — таз это не IK, а корень персонажа.

Ручки теперь ГОНЯТСЯ ЗА КОСТЯМИ, пока ничего не тянешь (`captureRig` каждый кадр вне драга).
Раньше этого не требовалось — в FK ручки были спрятаны целиком; теперь они видны всегда, и без
этого синяя ручка висела бы в воздухе после поворота плеча кольцами.

#### Молчавшие ручки заговорили

Две вещи в FBIK-пути не читались ВООБЩЕ — и выглядело это как поломка:

* **`e.pole`** — оранжевые ручки локтя/колена таскались, а сторона сгиба бралась из ЗНАКА ПРЕДЕЛА.
  Теперь полюс имеет приоритет в `placeHingeMids`; так как `syncEff` снимает полюс С ЖИВОЙ ПОЗЫ при
  каждом захвате, драг больше НЕ сбрасывает авторскую докрутку сустава. Знак предела остался фолбэком
  (это он починил «колено назад» в Ф4).
* **`setEndOrient`** — кисть с оружием крутилась за предплечьем. Теперь зовётся и после FBIK —
  у перетаскиваемого и у запиненных, С КЛЭМПОМ по пределу: держать мировую ориентацию при
  повороте плеча на 90° значило бы вывернуть запястье на те же 90°; живое держит НАСКОЛЬКО МОЖЕТ.

Третья — **`e.ik`** — теперь входит в маску: тумблер «рука Л: FK» наконец что-то делает.

### Фиксаторы, предел таза и возврат корпуса (Ф22)

Три жалобы после Ф21, каждая с отдельной причиной.

#### 1. Фиксаторы не держали при FK-вращении

Солвер звался ТОЛЬКО на драге РУЧКИ (`gizmo.dragging && onHandle`). Крутишь кость кольцами — пины
не участвуют вообще. Замер при всех четырёх запиненных точках: `Hips` на 40° — ОБЕ кисти уезжали
на **26.06u**, `Spine` на 40° — тоже 26.06u. В Cascadeur фиксатор (клавиша R) держит точку при ЛЮБОЙ
манипуляции — там «both these modes are supported simultaneously».

Сложность не в том, чтобы позвать солвер. Цепь от таза до кисти идёт ЧЕРЕЗ КОРПУС:
выкинешь корпус из маски — маска распадётся на несвязные куски и forward-проход от якоря не дойдёт
ни до одной руки; оставишь как есть — корпус будет КОМПЕНСИРОВАТЬ твоё же вращение, и крутить
кость станет бессмысленно. Отсюда третье состояние кости — **ЖЁСТКАЯ** (`solve(…, rigid)`):
в цепи участвует, свой угол не меняет, тягу выше себя не пускает.

Правило сборки при FK-драге: **жёсткие = всё, кроме собственных цепей запиненных конечностей,
плюс сама крутимая кость и все её предки**. То есть крутишь корпус — рука догоняет СВОИМИ
суставами; крутишь плечо — догоняет один локоть (и честно не дотягивает — шарнир одноосевой).

Вторая половина того же бага: `captureRig` звался КАЖДЫЙ КАДР вне драга и тянул `syncEff` для
ВСЕХ эффекторов — то есть стоило отпустить мышь, как цель пина переезжала туда, куда точку как раз
увезло. Пин отменял сам себя. Теперь разделены `syncHandles()` (каждый кадр, НЕ трогает цели
пинов) и `captureRig()` (поза ЗАМЕНЕНА — клип/кадр/T-поза/undo). И FK-поворот кости конечности
больше не гасит её IK, если она ЗАКОЛОТА: фиксатор важнее авто-FK.

#### 2. Таз уезжал за предел досягаемости

Замер: тянешь ручку таза вверх на 120u при запиненных стопах — **стопа едет за ним 1:1** при длине
ноги 41.2u. Солвер тут НЕ виноват (это тоже замерено): он честно вытягивает ногу в струну (бедро 3.6°,
колено 1.1°, таз→стопа 38.4 из 41.2) — больше ему делать нечего. Ограничивать надо САМО
ДВИЖЕНИЕ ТАЗА — точно так же делает foot-IK в играх («pelvis adjustment prevents the character
from splitting»).

`clampHipsToPins()`: корень цепи жёстко связан с тазом, значит обязан остаться в ШАРЕ радиуса
«сумма длин звеньев» вокруг цели пина; несколько пинов — пересечение шаров, берётся 4 итерациями.

**ГРАБЛЯ, пойманная замером:** одного клампа МАЛО. С ним таз всё равно ехал на 1.8u из 20
и вставал: `writeHipsPosition` тянул таз ОБРАТНО к стопам, кламп поднимал снова, система
уравновешивалась. Лечится тем же механизмом: когда таз тянешь ТЫ, он помечен ЖЁСТКИМ.

После (стопы запинены, длина ноги 41.2u):

| тяну таз | таз проехал | стопа дрейф |
|---|---|---|
| вверх 120 | 4.5 | 2.67 |
| вбок 80 | 39.8 | **0.08** |
| вниз 6 / 12 | 6 / 12 | 0 / **0.01** |
| вниз 20 / 25 | 20 / 25 | 2.29 / 6.29 |

Глубокий присед (≥20u) даёт дрейф — туда не пускает ПРЕДЕЛ КОЛЕНА, а не число итераций
(проверено: 48 итераций не меняют ничего). Запиненная ПРЯМАЯ рука зажимает таз почти насмерть
— это геометрически верно (плечо→кисть уже равно длине руки), но знать об этом надо.

#### 2б. Таз всё равно ломал позу — шара недостаточно

После шар-клампа юзер всё равно развалил фигуру, повозив таз. Стресс-серия драгов показала
накопление: отрыв стопы от фиксатора 0.27 → 3.71 → 9.33 → **29.14u**, таз на y = −3.7 (под полом).

Три независимые причины, все пойманы замером.

**Шар ловит только «слишком далеко».** А на приседе цель недостижима по «СЛИШКОМ БЛИЗКО» и
по УГЛУ в суставах — шар этого не видит, и таз спокойно уходит под пол, утаскивая стопы.

**ФЛИП КОЛЕНА.** Сторона сгиба бралась из знака предела через ось шарнира В МИРЕ, а она зависит
от ориентации бедра — самоподдерживающийся флип. Замер: сгиб колена 70.4° → внезапно 2.3°, таз
проваливался на 20u, нога уходила вбок — тот самый «шпагат». Лечится полюсом: **у НОГ он
работает ВСЕГДА** (колено вперёд — это анатомия, а не ручная докрутка), у рук — по-прежнему
только после ручного драга (там полюс ронял недолёт с 0 до 15–17u, Ф21.5).

**КЛАМП ПОРТИЛ ЖЕЛАНИЕ ПОЛЬЗОВАТЕЛЯ.** Первая версия писала в `rig.hipsPos`, а `moveHips` считает
дельту ОТ него же — кламп и драг боролись, ручка отрывалась от таза (жёлтый куб на полу
на скрине юзера). Теперь **`rig.hipsPos` = ЖЕЛАНИЕ, позиция кости = РЕЗУЛЬТАТ** — точно как
у ручки кисти, которая может быть вне досягаемости; `syncHandles` вне драга схлопывает желание к факту.

**ГЛАВНОЕ — СЕМАНТИКА ФИКСАТОРА.** Она НЕ «найди лучшее положение таза», а «ДАЛЬШЕ НЕ ПУЩУ».
Поиск минимума недолёта пробовался и оказался НЕГОДНЫМ: цель стопы достижима ДВУМЯ позами —
ПРИСЕДОМ и СТОЙКОЙ — и минимизатор уводил в стойку: тянешь таз вниз, а персонаж ВЫПРЯМЛЯЕТСЯ
(колено 126° → 0.4°). Демпфер шага проблему не решил, а размазал.

Решение: во время драга хранится **ПОСЛЕДНИЙ ХОРОШИЙ КАДР** (позиция таза **И** поза всех костей
цепей пинов), и как только фиксатор срывается — откат к нему целиком. Две тонкости, каждая
стоила отдельного замера:

* Откатывать надо **ЦЕЛЫЙ КАДР, а не одну позицию таза**: при ТОМ ЖЕ тазе y = 22.7 отрыв
  бывал то 1.32, то 10.3 — разница только в позе ног (колено 113° против 119°). Снимок берётся
  и на `pointerdown`, иначе первый же срыв откатывал таз в пустоту (отрыв 27.9u).
* Критерий — **«не УХУДШАТЬ», а не «быть идеальным»**, с допуском на транзиент солвера (1.5u).
  Абсолютный порог 0.25u заклинивал таз НАВСЕГДА: солвер не идеален, остаточный отрыв 1.3u
  переживал драг, порог не достигался никогда и откат шёл каждый кадр (замер: y = 36.7 на ЛЮБОЙ тяге).

Стресс-серия после (10 драгов подряд, включая тяги на 200u, стопы заколоты):

|---|---|---|
| макс. отрыв стопы от фиксатора | **29.14u** (и рос) | **2.52u** (не копится) |
| стопа по y | до −34.6 (под полом) | −0.2 … 2.8 |
| растяжение костей | — | **0** |
| отрыв ручки таза от таза | большой | **0** |

#### 3. Корпус не распрямлялся обратно

Жалоба: «завёл руку назад — корпус довернул; двигаю руку вперёд — не распрямляется».
Причина точечная: в Ф21 скрутка хранилась числом `pullTwist` («сколько я накрутил в ЭТОМ драге»),
и его обнулял `captureRig` — а он звался каждый кадр вне драга. Отпустил мышь → скрутка
запеклась в позу, и снимать её было уже нечем.

Решение взято из **HumanIK Stiffness**: часть тела «resists transformation and tries to maintain its
INITIAL FK ANGLES». Значит хранить надо не накопитель, а **ОПОРНУЮ ПОЗУ** — снимок кватернионов
[Spine..Head] ДО первого доворота (`pullBase`). Каждый солв начинается с `pullRelax()` — точного
отката к опоре, без накопления ошибки. Опора ЖИВЁТ МЕЖДУ ДРАГАМИ и забывается только когда
корпус правят РУКАМИ (FK по любой из `TWIST_BONES`) или меняют позу целиком.

**Авторский изгиб руки/ноги не трогается вовсе** — восстанавливаются ТОЛЬКО кости цепочки скрутки.

Замер цикла (Pull = 1, правая кисть):

| шаг | Spine y | Chest y | UpperChest y |
|---|---|---|---|
| завёл руку поперёк тела | 8° | 16° | 16° |
| вернул на место | **0°** | **0°** | **0°** |
| снова поперёк | 8° | 16° | 16° |
| увёл назад | **0°** | **0°** | **0°** |

### Свивель локтя/колена и залипание Shift (Ф23)

#### 1. Оранжевые ручки ни на что не влияли

Жалоба: «локти/колени нельзя тянуть как стопы, перемещение их точек ни на что не влияет».

Причина оказалась не в солвере, а в том, что его НЕ ЗВАЛИ: при драге полюса `activeKey` и
`fkProxyBone` ОБА `null`, поэтому ни одна ветка `solvePlan` не срабатывала, `plan.targets.size === 0`,
и `solve` не вызывался вообще. `e.pole` честно менялся — и его никто не читал до следующего драга кисти.

**Свивель считается АНАЛИТИЧЕСКИ, а не через FABRIK** (`applySwivel`). Это вращение цепи
ВОКРУГ ЛИНИИ корень→конец; оба конца лежат НА оси, поэтому кисть/стопа остаётся на месте
ПО ПОСТРОЕНИЮ — достаточно повернуть ОДНУ кость-корень. Попытка отдать свивель солверу
была замерена и отвергнута: сгиб локтя 106° → 138°, кисть уезжала на 15–26u.

Две тонкости:

* **Шагами с клэмпом и откатом.** Сам свивель конец не двигает, но КЛЭМП ПЛЕЧА двигает:
  одним большим шагом сгиб сохранялся точно (110°→110°), а кисть уезжала на 22–29u. Поэтому
  та же семантика, что у фиксаторов таза: шагнули → зажали по пределу → конец сошёл с места →
  шаг откатили и СТОП. Свивель доворачивается до анатомического предела и там упирается.
* **Цель эффектора ЗАМОРАЖИВАЕТСЯ на время драга полюса.** Без этого она переписывалась
  каждый кадр на текущее место кисти (в `solveRig` и `syncHandles` гейт был только по `activeKey`) —
  удерживать было НЕЧЕГО.

**В СОЛВЕР полюс идёт ТОЛЬКО ДЛЯ НОГ.** Замер: после ручного свивеля руки, если полюс подать
в FABRIK, недолёт кисти растёт с 0 до **10.53u** (зафиксированный свивель загоняет твист плеча за предел
±80°, клэмп режет — та же причина, что в Ф21.5). У НОГ полюс в солвере НУЖЕН — он чинит
флип колена (Ф22.4), а стопа от него не страдает.

| | было | стало |
|---|---|---|
| сустав едет за оранжевой ручкой | **0** | 7–13.5u |
| конец остаётся на месте | — | **0–0.37u** |
| угол сгиба | — | сохраняется точно (106°→106°) |
| тяга кисти ПОСЛЕ свивеля | недолёт 10.53u | 3.32u |

#### 2. «Пропал Shift и вращение»

`keyup` может НЕ ПРИЙТИ вообще — Alt+Tab, клик мимо окна, переключение вкладки с зажатой
клавишей. Тогда `shiftRings` оставался непустым НАВСЕГДА, `ringsOn` выходил по первой же
строке — кольца больше не появлялись. А кольца и есть вращение — отсюда «пропало и то и другое».
Снап залипал точно так же.

Лечится сбросом по `blur` и `visibilitychange`, плюс проверкой `ev.shiftKey` на `pointerdown`
(состояние протухло — чиним до пикинга). Проверено циклом: ручка → Shift даёт кольца →
`blur` без `keyup` возвращает стрелки → Shift снова работает.

### Запястье и взгляд (Ф24)

#### 1. Reach R — кисть едет за рукой, а не висит параллельно полу

Жалоба: «если из T-позы опускать кисть за хелпер, она остаётся параллельно полу и выкручивает руку».

Причина: `setEndOrient` держал МИРОВУЮ ориентацию конца ВСЕГДА. В HumanIK это ДВА НЕЗАВИСИМЫХ
канала — «adjust the percentage of translation and rotation reach… using the **Reach T** and **Reach R**
sliders»; у нас Reach R был жёстко прибит к 1.

Теперь у эффектора есть `keepRot`: **стопы держат** (подошва обязана стоять плоско),
**кисти — нет** (локальный угол запястья не трогается, кисть едет за предплечьем). Для оружия —
чекбокс на конечность в панели «ДЕРЖАТЬ ПОВОРОТ КОНЦА (Reach R)».

Замер (кисть опущена из T-позы на 25u):

| `keepRot` | угол запястья (локальный) | мировой угол кисти |
|---|---|---|
| вкл (было всегда) | **49.5° вывернуто** | 0° (висит в мире) |
| выкл (дефолт для кистей) | **0°** — нейтраль | 49.5° (повернулась с рукой) |

#### 2. Хелпер взгляда — голова держит направление при скрутке корпуса

Кнопка `👁 взгляд` — белый шар-цель перед лицом; голова смотрит в него, как бы ни скручивался корпус.

По индустрии (Unity Animation Rigging, Multi-Aim) важны две вещи, и обе сделаны:

* **Распределение по цепочке с разными весами** («chain multiple aim constraints — head, neck,
  upper spine — each with decreasing weights»): у нас `Neck 0.35` + `Head 0.65`, два прохода.
* **Пределы против «owl neck»** («set generous limits 45–60° per bone»): берём не из воздуха, а из той же
  таблицы суставов, что и весь редактор (`limitViewForBone` + `clampLocalToLimit`).

Хранится ОПОРНАЯ ПОЗА шеи/головы (тот же приём, что `pullBase` в Ф22.3): каждый кадр взгляд
СНИМАЕТСЯ и считается заново от авторской позы — иначе довороты копятся и голова «уплывает».
Правишь шею/голову руками — опора забывается, твой угол становится новой базой.

Замер (корпус скручивается, смотрим отклонение взгляда от цели):

| | взгляд выкл | взгляд вкл |
|---|---|---|
| корпус скручен 70° | 70° | **0.6°** (шея 40° + голова 30°) |
| корпус скручен 110° | 110° | 29.8° — честно упёрлись в предел, а не вывернули шею |
| корпус вернули прямо | 0° | 0.6°, шея/голова расслабились до ~2–3° |

### Точка позиции персонажа

`⌖ позиция` рисует то, чем персонаж является для СЕРВЕРА: центр круга коллизии на полу
(`PlayerView {x, y, r}`), радиус — из `@dm/shared` (`PLAYER_RADIUS`/`MONSTER_RADIUS`), а не переписанное
число. **Это не таз:** таз намеренно уезжает с точки (авторский `__hipsD`, выпад удара), и в игре так же.
В редакторе `human.root` закреплён в начале координат и никогда не двигается — бег это тредмилл, едет пол,
поэтому маркер статичен.

### Горячие клавиши

`1/3/7` виды спереди/сбоку/сверху · `F` фокус на выбранной кости · `.` фокус на тазе ·
`W/E` перемещение/вращение · `S` снап (оба сбрасываются при потере фокуса окна) · **`Shift` (удержание) — кольца вращения кости** · `Ctrl+Z / Ctrl+Shift+Z` откат.
Раскладка ловит и кириллицу — иначе на русской раскладке клавиши молча не работают.

### Конечность аналитически, локоть и колено — эффекторы (Ф25)

Жалоба: «локти и колени иногда не сгибаются, хелпер кулака выкручивает; крутишь хелпер локтя —
рука улетает вверх от хелпера кулака; хелпер локтя должен и ключицу подтягивать».

#### Почему не FABRIK

Конечность = сфера (плечо/бедро) + **шарнир** (локоть/колено) + конец. Позиционный солвер с шарниром
теряет непрерывность — это известная слабость («each rotation limit decreases the stability and continuity
of the FABRIK solver», FinalIK). Замер на нашем риге (`knight_05`) это подтвердил: цель «кисть к бедру» —
сгиб локтя **7° вместо 24°** по закону косинусов, недолёт 6u.

Теперь конечность решается **аналитически** (`limbIk.ts` — чистая математика, node-тесты; `solveLimb`
в `pose-editor.ts` — применение к скелету с пределами). FABRIK жив за Про-кнопкой «солвер: аналитика /
FABRIK (старый)» на один релиз для сравнения.

#### Порядок операций (ozz-animation / Unity TwoBoneIK) — главное решение фазы

1. **Шарнир ставится УГЛОМ** по закону косинусов вокруг СВОЕЙ оси (`setHingeBend`), а не «целься в точку,
   потом клэмп». Прицеливание даёт внеосевую компоненту, а 1-DOF клэмп её ВЫБРАСЫВАЕТ — вместе со сгибом
   (замер «колено вверх»: 88° вместо 116°, недолёт 13.3u; без клэмпа — 116°/0.00u).
2. **Корень целит КОНЕЦ ЦЕПИ в цель** (а не себя в локоть): длина |корень→конец| уже задана сгибом, поэтому
   ОДИН поворот ставит кисть РОВНО на ручку. Предел плеча теперь забирает СТОРОНУ ЛОКТЯ, а не дотягивание.
3. **Свивель к полюсу** вокруг линии корень→цель — конец по построению не двигается (Ф23.1).

**ГРАБЛЯ ФФ25, стоившая всей работы полюса:** `aimBoneAt` (`setFromUnitVectors`) строит кватернион **ЦЕЛИКОМ**
минимальной дугой, то есть **стирает твист** — а именно твистом задана плоскость сгиба. Свивель честно
уводил колено на 13.1u при стоящей стопе (0.00u), а следующий аим возвращал колено РОВНО НА МЕСТО — оттого
оранжевые ручки и «ни на что не влияли». Корень должен доворачиваться **ДЕЛЬТОЙ** — тогда сохраняются
и свивель, и поза прошлого кадра (так же стартуют HumanIK/Unity — из текущей FK-позы).

Вторая грабля там же: при выборе лучшего кадра среди итераций критерий «СТРОГО лучше» отбрасывает
свивель всегда, когда цель достижима (свивель не меняет недолёт — значит «не лучше»). Надо «НЕ ХУЖЕ →
берём поздний».

#### Локоть/колено как эффектор (HumanIK aux effector)

Раньше оранжевая ручка была только полюсом (сторона сгиба). Теперь — цель по позиции при ПРИБИТОЙ кисти
(«translating the Elbow and Knee effectors will replicate a Pole-vector constraint»). Цепочка (`elbowGoal`):
желаемый локоть → он обязан лежать на сфере L2 вокруг кисти → плечо обязано лежать на сфере L1 вокруг
локтя → **ключица** (`shoulderGirdle`, пределы Ф21.4: ±20°/±15°/±10°) → **корпус** (та же Pull-скрутка Ф21.4).

Каждая ступень помощи тела держится, **только если СТАЛО ЛУЧШЕ** (правило Ф22.4). Недолёт бывает двух родов —
«далеко» (ключица реально помогает) и «предел сустава» (там пояс может СДЕЛАТЬ ХУЖЕ): без гварда замер на
дуге кисти за спину давал прыжок локтя 4.25u и недолёт 8.8u против 1.6u/6.4u у голой конечности. У локтя-эффектора
кисть весит втрое — кулак не срывается ради локтя.

#### Soft IK — есть, но ПО УМОЛЧАНИЮ ВЫКЛ (осознанное отклонение от плана)

План требовал «цепь никогда не выпрямляется в струну» (Maya soft IK). Замер с `soft = 0.1`: **стоящая прямая нога
получала колено 30° и отрыв стопы 1.23u**, а кисть на 98% вытяжения не доходила до ручки 0.8u. Сгиб у полного
разгиба растёт как √недолёта — ЛЮБОЙ soft > 0 виден на стойке (0.02 → ещё 14°). Для ПОЗИНГА точность важнее:
`LIMB_SOFT = 0`. Цена — один прыжок локтя 2.8u ровно на полном разгибе (кисть при этом держится за ручку, 0.02u).
Функция `softDistance` осталась и покрыта тестами — она нужна для запекания клипов, где важнее непрерывность.

#### Что упирается в ТАБЛИЦУ ПРЕДЕЛОВ, а не в солвер

Оставшиеся недолёты — честный упор в пределы физ-таблицы (`humanoidRagdoll.ts`, тюнятся в панели суставов):

* плечо — подъём/опускание ±69° от T-позы (оттого «к бедру» решается только с ключицей, сгиб 38° вместо 19°);
* бедро — сгиб ±52° («колено высоко вверх» недобирает 10.2u — солвер выдаёт ровно 116° в колене, как и положено).

Хочешь глубже — расширять надо именно пределы (они общие с рэгдоллом игры), а не солвер.

### Тело едет за рукой, хелперы плеч/головы, прозрачность (Ф26.1–26.3, 26.6)

#### 1. «Персонаж взлетел после вкладки Бег» — две причины, главная — ПОРЯДОК

`tabSwitch` восстанавливал кадр (`goFrame`) **ДО** `tab = k`, а `goFrame` внутри зовёт `refreshAll()` — то есть
перерисовывал **ещё старую** вкладку, а `renderTurn` снова ставил `locoOn = true`. Превью походки
НИКОГДА не выключалось: гейт каждый кадр ставил таз в `30 + bobY` (`gaitToHumanoid`), а авторская высота — ~40
(замер: таз 40.28 → 30.0, стопа 1.84 → −8.63 под полом).

Вторая половина — заземление призрака: `gs.off` копился без затухания, а когда перерастал гейт опоры
`PLANT_MAX = 6`, ОБЕ стопы становились «маховыми» → блок коррекции пропускался целиком, и накопитель
**замирал навсегда**, продолжая поднимать фигуру (самозапирающийся режим). Теперь без опорной стопы сдвиг
затухает (так же, как в ветке смерти), выход из превью обнуляет `ghostGround.off`, а `goFrame` снимает и `root.position.y`.

Проверка: три круга «Анимация → Повороты → Анимация» подряд дают одно и то же (таз 40.00, стопа 2.18) —
накопления нет; инъекция `off = 12` рассасывается сама (12 → 3.2 → 1.07 → 0).

#### 2. Прозрачность

Два ползунка (скелет 0.55, хелперы 0.7), персист в `pe_ui`. Приём — от онион-скина (`transparent` +
`opacity` + `depthWrite = false`). Все ручки регистрируются в списке прямо в `mkHandle` — иначе каждый новый
хелпер пришлось бы вручную дописывать в проход. Заодно `pe_ui` стал ОДНИМ словарём: было два
независимых чтения того же ключа и запись целиком — любое новое поле затирало соседей.

#### 3. Хелперы плеч и головы

**Плечи** (фиолетовые): тянут ключицу через тот же `shoulderGirdle`, которым локтевой хелпер Ф25 опускает её
автоматом. **`girdleForget()` после правки обязателен** — иначе следующий же `solveRig` сделает `girdleRelax()`
и вернёт ключицу в опорную позу (ручка не держала бы). Замер: ключица −5.4° → +10° вверх и → −20.8° вниз
(упор в предел), запиненная кисть на месте (0.28u).

**Голова**: белая точка взгляда видна вместе с остальными ручками (тумблер IK), клик по ней включает
наведение; от головы к точке идёт луч (иначе шар перед лицом читается как «что-то висит»). Замер:
голова поворачивается на 29.4° при корпусе 0.0°.

#### 4. ТЕЛО ЕДЕТ ЗА РУКОЙ (главное в фазе)

Жалоба: «оттянул руку наверх и назад — тело почти не двигается». Две причины:

| | было | стало |
|---|---|---|
| **Когда** | только по НЕДОЛЁТУ — а замах руке доступен, значит никогда | максимум трёх драйверов: ВЫНОС руки от нейтрали (главный), натяжение с 70% вытяжения, недолёт |
| **Что** | одна ось — осевая скрутка (`rotateY`) | `bendTorso`: скрутка + прогиб/сгиб + боковой наклон, свои веса на ось |

Почему главный драйвер — ВЫНОС, а не дистанция: настоящий замах делают **СОГНУТОЙ** рукой, и по одной
дистанции он неотличим от руки у груди (замер с одним натяжением: сила 0.37, прогиб 2.2°). Натяжение
вдобавок **гасится у нейтрали**: рука, висящая вдоль тела, тоже почти вытянута — без гейта просто стоящий
персонаж клонило вперёд на 10.5°.

**ПОРЯДОК РЕШАЕТ:** тяга применяется **ДО** решения руки. Когда она шла после солва и сравнивалась
сама с собой по «стало ли лучше», у полного вытяжения возникал цикл «согнулся → плечо уехало → откат»
через кадр (замер на дуге: скачки до 29.7°; стало 9° и монотонно). Добавка по недолёту идёт сверху
и вот её откатывать можно — она существует именно ради дотягивания.

Пределы: скрутка 45°, прогиб назад 35°, наклон вперёд 40°, вбок 35° (разгиб меньше сгиба — анатомия,
поэтому два разных числа); таз берёт 15% скрутки. Профиль гибкости — пер-персонаж в `pe_phys[char].flex`
(та же секция, что match/footLift — её читает игра): доспешный воин скованнее, акробат гибче.

Замеры (замах вверх-назад, стопы запинены):

| сила / поза | скрутка | прогиб | таз | кисть | стопы |
|---|---|---|---|---|---|
| 0.45 (дефолт) | −21.4° | −11.4° | −3.2° | 0.00u | 0.00u |
| 1.0 | −45.0° | −25.3° | −6.8° | 0.00u | 0.01u |
| гибкость 0.4 (скованный), сила 1.0 | −18.0° | −14.0° | | | |

Рука вдоль тела и в Т-позе корпус НЕ трогают (0°); возврат руки в стойку возвращает корпус в 0.
Часть замеров Ф25 улучшилась: «кисть за спину» недолёт 3.62 → **0.12**, дуга 3.69 → **0.49**, дальняя цель 24 → **2.5**.

**ИЗОЛЯЦИЯ ПЕРЕФОРМУЛИРОВАНА** (Ф21 говорила «тяга правой кисти не двигает левую»): теперь
**запиненное держится** (стопы 0.05u), а незапиненная левая кисть едет за телом (2.25u) — это и есть «естественно».

### Локоть, пины и панель на свитках (Ф26.4, Ф26.7)

#### Плоскость локтя: полюс хранится УГЛОМ, а не мировым вектором

Жалоба: «тянешь руку вверх — локоть уходит за спину, вниз его не сделать». Три причины:

1. **Мировой вектор полюса.** Дефолт «вниз-назад» верен для опущенной руки и НЕВЕРЕН для поднятой.
   Теперь полюс = **анатомическое предпочтение + угол свивеля**: рука ниже плеча — локоть вниз-наружу,
   рука выше плеча — вперёд-наружу. Ручная правка хранится УГЛОМ от натурали и переживает движение руки.
2. **`poleFromPose` записывал ДОСТИГНУТУЮ плоскость как «ручную правку»** — а она часто зажата пределом
   плеча. После первого же солва свивель становился ≈180° и предпочтение было перебито НАВСЕГДА.
   Свивель теперь пишет только оранжевая ручка.
3. **Сама таблица пределов.** Подъём плеча был **±69° от T-позы**, а до «руки над головой» ровно 90°
   и до «руки вдоль тела» тоже 90° — ОБА бытовых положения были ЗА ПРЕДЕЛОМ. Стало ±109° подъём
   и ±92° твист. Замер: рука над головой — локоть +1.0 вперёд / +14.6 вверх (был за спиной),
   рука вдоль тела — +0.1 / −13.9.

Остаётся крайний случай «кисть за головой»: локоть вперёд там требует **−227° твиста плеча** (замер), что
вне любой анатомии — там локоть ведётся ручкой, и эта правка держится.

#### Пины держат при ЛЮБОЙ манипуляции + сила привязки

`holdPins()` — последний проход солва: запиненные конечности дорешаются ПОСЛЕ корпуса, ключицы и таза;
если пин всё равно не удержался — снимается тяга тела. Ползунок «сила привязки»: 1 — насмерть,
меньше — точка частично едет за телом. Замер: 12 положений точки взгляда — кисть 0.00u, стопа 0.00u.

#### Корпус больше не распрямляется сам — ДВЕ причины

* **Утечка таза**: `syncHandles` копировал ЖИВОЙ кватернион таза в авторский `rig.hipsQuat`, и доворот таза
  от тяги впитывался в позу каждый кадр (замер: 3.2° → 6.2° → 9.1° → 14.2° за пять кадров) — плечо уезжало,
  а тяга, меряемая от плеча, таяла. Авторский таз меняют только ручка таза, FK-правка и смена позы.
* **Вклад тяги запечатывается** в позу на отпускании мыши и дальше идёт ДЕЛЬТОЙ (`bodyApplied`):
  поза держится при любом следующем действии и НЕ удваивается при повторном драге той же руки.
  Замер: замах −21.4°/−11.4° → 15 кадров покоя и 12 положений головы — без изменений.

#### Панель на свитках (Ф26.4)

`rollout(key, title, draw)` — заголовок ▾/▸, состояние в `pe_ui.open`. Внутри `draw()` цель аппенда (`body`)
временно подменяется на контейнер свитка — весь старый код секций работает без правок. ВОКРУГ
ПЕРЕРИСОВКИ СОХРАНЯЕТСЯ `panel.scrollTop`: `renderAnim` зовётся на каждый клик по кости/ручке.

Список клипов — вертикальный, со своим скроллом, поиском, чипсами вида и сортировкой; вид клипа берётся
теми же префиксами, что читает игра (`clipToAnimation`). Запечённая ходьба — отдельной группой,
свёрнутой по умолчанию. Панель 288 → 340px и тянется мышью (240…620, персист).

### Физ-тела по костям и баланс (Ф26.5, Ф26.6б)

#### Формы и размеры

Форма тела — `box | sphere | cylinder | capsule`. Цилиндр и капсула в Jolt и three всегда по оси Y,
а кости смотрят по ±X (руки), −Y (ноги) и +Z (стопы) — форма разворачивается кватернионом в том же
`RotatedTranslatedShapeSettings`, куда уже передавалось смещение (там стояла единичная ротация). Разворот —
по ФАКТИЧЕСКОМУ направлению тела, а не по доминантной оси: после подгонки кости стоят наискосок.

Размеры — секция `sizes` в `pe_ragdoll` (форма, полудлина, множители ширины/толщины, анкер, смещение).
Отсутствующее поле берётся из каталога, поэтому «сброс» = удалить ключ. Свиток «РАЗМЕРЫ ФИЗ-ТЕЛ»: выбор
тела, форма, три ползунка, кнопки «снять с костей / сброс тела / сброс всех».

**Снять с костей.** Начало тела — первая кость его цепи ретаргета, конец — среднее по детям последней
(у кисти это середина оснований пальцев = конец ладони). Замер идёт В Т-ПОЗЕ: анкеры физ-рига заданы
именно в рест-фрейме (там же оси суставов и рест-трансляции констрейнтов), а длины в Т-позе уже с морфом.
Анкер пишется ВСЕГДА, даже где длины нет (таз): рест-трансляция считается как разница анкеров, и
пропущенный родитель сдвинул бы всю цепь на свою ошибку.

**ГРАБЛЯ:** активный набор тел собирается ТОЛЬКО в `applyPhysProfile` — без его вызова из `rebuildRagdoll`
правка размера сохранялась в конфиг, а кукла пересобиралась со старыми телами.

Замер: расхождение анкеров с костями **13.41u → 0.00u**, длин **6.80u → 0.00u** (17 тел). Стабильность:
10 секунд симуляции и четыре толчка «дёрг» — 0 разлетевшихся тел. Размеры абсолютны и глобальны
(`pe_ragdoll` один на всех), поэтому тела переснимаются с костей при смене морфа, смене персонажа и на
старте физики; ручные множители и формы при этом сохраняются.

#### Ф26.8 — три бага того же узла

**Боксы гасли на каждую правку.** `rebuildRagdoll` создаёт НОВУЮ `ragdoll.group` и клал её в сцену
всегда скрытой, а кнопка «боксы: видны» в свитке размеров вообще не трогала видимость — тела
исчезали ровно в тот момент, когда на них и смотрят. Видимость теперь один шов `applyBoxVis()`
во всех точках, где группа появляется в сцене.

**Подгонка кормилась своим выходом.** У ЛИСТЬЕВ цепи (голова, кисти, носки) детей нет, то есть
скелет ДЛИНЫ НЕ СОДЕРЖИТ, и её брали как `|off| × 2` у ТЕКУЩЕГО тела — а оно само же и подогнано.
Голова росла на 2.45u за каждую переподгонку (а она идёт на старте физики, смене морфа и смене
персонажа): 4 → 57.11u, шар улетел над персонажем. Теперь длина листа = КАТАЛОЖНАЯ (`physCatalogOff`,
константа), масштабированная МЕДИАНОЙ отношений «замер / каталог» по измеримым телам —
то есть ростом текущего телосложения. Замер: три прогона подряд дают байт-в-байт одно и то же
(голова 4.80, кисть 2.40, носок 1.80).

**Таз становился блином.** У СТУПИЦЫ среднее по детям вырождено: ноги идут вниз, спина вверх,
они гасят друг друга и дают полудлину 0.35u — порог «≥ 0.3u» её пропускал, и бокс таза схлопывался.
Критерий теперь по КАТАЛОГУ: тело без выноса в каталоге длины со скелета НЕ ПОЛУЧАЕТ — пишется
только анкер, а прежняя длина удаляется (старый испорченный конфиг лечится сам при загрузке).

Плюс мелочи: ось в `sized()` берётся из ФАКТИЧЕСКОГО `off` (как в `shapeRot`, иначе длина ложится
на поперечную полуось); у шара ползунок длины скрыт — радиус задаётся шириной.

#### Баланс: центр масс над опорой

Центр масс считается по ФИЗ-ТЕЛАМ (объём формы × плотность) плюс масса оружия в кистях — именно поэтому
баланс идёт ПОСЛЕ Ф26.5: тела сняты с костей и едут за морфом, значит центр масс верен для любого
телосложения без отдельной таблицы весов.

Опора — прямоугольник по стопам **НА ПОЛУ**. Критерий — высота, а не пин: заколотая в воздухе стопа
ничего не держит (сначала считал по пину — опора стойки на одной ноге оставалась двуногой).

Сдвиг таза живёт в ОТДЕЛЬНОМ `balanceOff` и вычитается в `syncHandles` — иначе он впитался бы в авторскую
позицию и персонаж уползал бы кадр за кадром (та же утечка, что чинилась в Ф26.7 для поворота таза).

Замер (стойка на одной ноге):

| сила «перенос веса» | выход центра масс за опору | сдвиг таза |
|---|---|---|
| баланс выкл | **4.91u** (упал бы) | 0 |
| 0.3 | 1.48u | 3.7u |
| 0.6 (дефолт) | 0.39u | 5.0u |
| 1.0 | **0.00u** | 7.5u |

Двуногая стойка, вытянутая рука и наклон корпуса баланс НЕ трогают — центр масс и так над опорой,
и это физически верно: рука лёгкая, её вынос сдвигает центр масс на 0.1u.

### Один рецепт скелета на все риги (Ф27)

**Жалоба:** «меш и серое тело расходятся, он же повторяет кости».

В редакторе живут ЧЕТЫРЕ рига ОДНОЙ анатомии: авторский манекен, физ-призрак (он же `solid`
игры — именно он ведёт меш), онионы соседних кадров и риг-источник модели. Входы одни, а
ПОВОД пересборки был у каждого свой — и любой повод, поднявший только один, разводил их по РАЗНЫМ скелетам.

Три причины, каждая замерена:

1. **Смена вида манекена** (`setManView` → `rebuildManikin`) поднимала ТОЛЬКО манекен: плечо
   10.80u против 15.60u у призрака, кисть уезжала на 4.71u, стопа на 4.91u.
2. **Сторож сравнивал офсеты атласа ПО ССЫЛКЕ**, а их лечение ДОПИСЫВАЕТ тот же объект —
   смена не замечалась. Офсеты готовы на 366-й мс, а оба рига оставались процедурными девять секунд и
   дольше — до нажатия посторонней кнопки.
3. **Гейт `if (pw)`** молча пропускал пересборку призрака, пометив смену применённой.

**Решение.** Рецепт — ЗНАЧЕНИЕ (`rigRecipe`) с ключом **по СОДЕРЖИМОМУ** (`recipeKey`), ключ штампуется
НА САМОМ риге (`stampRig` → `root.userData.rigKey`), а `syncRigs()` раз в кадр поднимает те, чей ключ
устарел. Поводов больше нет — есть один ключ. В покое `syncRigs` не делает ничего (замер: 300 кадров —
0 пересборок), иначе выбор кости слетал бы каждый кадр.

**Риг-источник модели в эту синхронизацию НЕ ВХОДИТ осознанно:** он строится ПРЯМО из атласа,
то есть всегда актуален (замер: расхождение 5.15u было ЦЕЛИКОМ из-за манекена). Пересобирать его
по ключу ВРЕДНО: `rebuildAsm()` дизпоузит скин и тянет GLB заново — меш пропадал на несколько секунд.

#### Расхождение числом

`rigDelta()` и строка в панели рядом с прозрачностью. Два РАЗНЫХ числа:

* **призрак ↔ кости модели** — обязано быть **0.00u ВСЕГДА**: серое тело и есть тот риг, которым
  ведётся меш, врать про него оно права не имеет;
* **манекен ↔ призрак** — честная разница, разложенная на **заземление** (вертикаль таза: призрак
  стоит на полу, авторская поза — нет) и **позу** (физ-бленд по `PHYS.match`).

СЧЁТЧИК СРАВНЁННЫХ КОСТЕЙ ОБЯЗАТЕЛЕН. Первая версия без него показывала бодрый 0.00u там, где
модель просто не загружена и сравнивать НЕ С ЧЕМ — поймано контрольным замером.

#### Замеры (19 костей, атлас загружен)

| состояние | призрак ↔ меш | манекен ↔ призрак (заземл. · поза) |
|---|---|---|
| ДО Ф27 | **5.15u** | — |
| `match` 1.0 | **0.00u** | 1.06u (1.06 · 0.36) |
| `match` 0.5 (дефолт) | **0.00u** | 1.09u (1.06 · 1.16) |
| `match` 0.0 | **0.00u** | 3.23u (0.34 · 3.13) |
| смена вида манекена | **0.00u** | не меняется |

Остаток «манекен ↔ призрак» — НЕ баг: при `match` = 1 это почти целиком заземление призрака,
а ниже — физический бленд, то есть ровно то, что покажет игра.

#### ГРАБЛЯ ЗАМЕРА

При СКРЫТОМ пейне браузера `requestAnimationFrame` не тикает (0 кадров за 600 мс): цикл стоит,
физика не шагает, риги заморожены — и любое расхождение выглядит «не зависящим от физики».
Мерять только с открытым пейном либо явными `__pe.physStep(dt, n)` и `__pe.syncRigs()`.

#### Ф27.5 — манекен рисуется заземлённым

Остаток «манекен ↔ призрак» оказался НЕ рассинхроном ригов, а **подъёмом стопы** (`pe_phys.footLift`).
Замер: при `footLift = 1.4` призрак стоит на 1.11u выше, при `footLift = 0` — на −0.29u. Призрак
поднимает лодыжку, чтобы подошва МЕША лежала на полу; манекен этот подъём не применял вообще — его
`footLift` читает только `groundFeet`, а на манекене он никогда не звался.

**Заземлить манекен насовсем нельзя по двум причинам,** и обе уже куплены багами:

1. `groundFeet` **пишет углы опорных ног** — авторский сгиб колена стирался бы каждый кадр
   (ровно то, против чего написан шов `groundManikin` в Ф20.5).
2. **Сдвинуть манекен на `gs.off` призрака тоже нельзя:** физика берёт цель таза С МАНЕКЕНА,
   поэтому сдвиг вернётся в следующий `gs.off` с обратным знаком — автоколебатель с усилением −1.
   Та же семья ошибок, что утечка таза в Ф26.7 и самокормящаяся подгонка в Ф26.8.

Поэтому заземление делается **только на отрисовку**: заземлили → нарисовали → вернули, всё в ОДНОМ
синхронном блоке. Между заземлением и возвратом нет ни `await`, ни событий, поэтому солвер, физика,
пины и запись кадра видят только авторскую позу. Ручки целей (кисти/стопы/таз) едут на тот же сдвиг,
иначе они оторвались бы от костей; полюсные и плечевые НЕ трогаются — при включённой физике они
уже стоят на призраке, то есть уже в заземлённом пространстве.

Работает только при ВКЛЮЧЁННОЙ физике (без призрака сравнивать не с чем) и снимается тумблером
«манекен на полу» рядом с «заземл. стоп».

| состояние | манекен ↔ призрак | призрак ↔ меш |
|---|---|---|
| без заземления манекена | 1.10u (заземл. 1.10 · поза 0.08) | 0.00u |
| В ОКНЕ отрисовки, `match` 1.0 | **0.00u** | **0.00u** |
| В ОКНЕ, `match` 0.5 | 1.14u (заземл. 0.00 · поза 1.14) | 0.00u |
| после возврата | 1.10u | 0.00u |

Вертикаль снята полностью на любом `match`; остаток при `match < 1` — честный физ-бленд, то есть
ровно то, что покажет игра. 300 циклов «заземлил-вернул» — поза и корень байт-в-байт те же, дрейфа нет.
