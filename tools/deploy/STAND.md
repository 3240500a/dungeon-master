# Вторая машина под стенд — короткий порядок действий

Ноутбук грузит, 9950X держит сервер. Это **не боевой деплой** (тот — [docs/DEPLOY.md](../../docs/DEPLOY.md):
Linux, Caddy, HTTPS, домен). Здесь всё в локальной сети и живёт ровно столько, сколько идёт замер.

## Зачем вообще

На одной машине прибор и сервер делят процессор, а задержки идут через петлю, где сети нет.
Из-за этого три вещи не проверяются в принципе:

1. **Ёмкость.** Сервер упирается в своё одно ядро при 100–109 % CPU, а стенд рядом отъедает
   ещё треть ядра. На 9950X сервер получает машину целиком — и кластер наконец меряется не
   в тесноте.
2. **Хвосты задержки.** Все наши RTT сняты через loopback: это задержка обработки, а не сети.
   Wi-Fi добавит свои десятки миллисекунд и покажет, как выглядит p99 у живого игрока.
3. **Переполнение исходящей очереди.** Проверено: на петле ядро поглощает всё, `bufferedAmount`
   не растёт даже при потолке в 64 КБ и клиенте, молчавшем полторы минуты. Механизм
   `maxBackpressure` можно проверить ТОЛЬКО по настоящей сети.

## Шаг 1. Доставить код

Два пути, оба рабочие.

**Через GitHub** (нужен доступ к репозиторию с обеих машин):
```bash
git push origin feat/3d-online-client
```
на 9950X:
```bash
git clone -b feat/3d-online-client https://github.com/3240500a/dungeon-master.git
```

**Одним файлом, без сети и логинов** — на ноутбуке уже собран `C:\work\dm-transfer\dm.bundle`
(вся история, ~25 МБ). Скопировать флешкой или по сети, дальше на 9950X:
```bash
git clone -b feat/3d-online-client C:\путь\куда\скопировал\dm.bundle dungeon_master
```
Пересобрать бандл, если код успел уйти вперёд:
```bash
git bundle create C:/work/dm-transfer/dm.bundle --all
```

## Шаг 2. Подготовить машину

**PowerShell от имени администратора** (иначе не откроются порты в фаерволе), из корня проекта:

```powershell
powershell -ExecutionPolicy Bypass -File tools\deploy\setup-stand.ps1
```

Скрипт проверяет Node 24, PostgreSQL и git, создаёт роль `dm` и базы `dungeon` / `dungeon_test`,
ставит зависимости и открывает TCP 3999 и 3001–3015 для частной сети. **Ничего не ставит молча:**
чего нет — назовёт и даст команду (`winget install OpenJS.NodeJS.LTS`,
`winget install PostgreSQL.PostgreSQL.17`, `winget install Git.Git`). В конце печатает адреса машины.

Отдельная база под стенд обязательна: боты плодят аккаунты сотнями.

## Шаг 3. Поднять сервер

```powershell
# один процесс на :3999 — с ним сравнимы все прежние замеры
powershell -ExecutionPolicy Bypass -File tools\deploy\run-stand.ps1 -Mode single

# кластер: гейтвей :3001 + ноды :3002… (по умолчанию ядра минус два)
powershell -ExecutionPolicy Bypass -File tools\deploy\run-stand.ps1 -Mode cluster -Nodes 12
```

Скрипт сам подставляет `DM_NODE_HOST` — адрес машины в локальной сети. **Без этого кластер
по сети не работает:** гейтвей не проксирует игру, он выдаёт клиенту адрес ноды, и по умолчанию
это `127.0.0.1` — ноутбук пошёл бы к самому себе.

## Шаг 4. Проверить связь с ноутбука

```bash
cd tools/dmload
./target/release/dmload --base=http://192.168.1.146:3999 --mode=net
```

Печатает задержку канала вхолостую. **Записать это число** — дальше все RTT читаются
относительно него, иначе задержку Wi-Fi припишем серверу.

Потом обычный поиск потолка:
```bash
./target/release/dmload --base=http://192.168.1.146:3999 --from=100 --step=100 --max=1000 --see=50 --out=single.json
./target/release/dmload --base=http://192.168.1.146:3001 --from=200 --step=200 --max=3000 --group=4 --out=cluster.json
```

## Что мерить в первую очередь

| Что | Как | Чего ждём |
|---|---|---|
| Канал вхолостую | `--mode=net`, до всякой нагрузки | база для всех RTT; на Wi-Fi единицы мс и заметный разброс |
| Потолок одного процесса | `--from=100 --step=100 --max=1000` | больше 200: сервер получил машину целиком |
| Потолок кластера | `--mode=cluster`, `--group=4` | ночью на ноутбуке было 1000 на 4 нодах; здесь ядер больше |
| Переполнение очереди | `--slow=10 --slowMs=60000`, на сервере `DM_MAX_BACKPRESSURE=200000` | `dm_slow_clients_dropped_total` наконец должен вырасти |
| Хвосты по сети | любой прогон, смотреть p95/p99 | впервые видно вклад настоящей сети |

## Грабли, на которые уже наступали

* **Порты нод.** Фаервол должен пропускать ВЕСЬ диапазон, а не только гейтвей: боты входят
  прямо на ноды. Иначе все окажутся на одной.
* **Комнаты живут час после выхода.** Между прогонами сервер поднимать заново, иначе ступени
  несравнимы. На ноутбуке для этого есть `tools/dmload/restart-server.sh`.
* **Сравнивать только прогоны подряд.** Разброс повтора большой: у одного и того же стенда
  на 200 ботах CPU сервера гулял 83 → 95 %. Меньшую разницу объявлять нельзя. Для сравнения
  есть `--out` и `--compare`.
* **Только один стенд за раз.** Одиночный сервер и кластер пишутся в ОДИН реестр узлов
  в базе и оба называют себя `node-0`. Запущенные разом, они перетирают запись друг друга,
  и гейтвей раздаёт ботам адрес чужого процесса. Наступал на это при проверке скриптов.
* **Адрес машины скрипт выбирает не наугад.** Туннели (VPN, WireGuard, Tailscale…) он из
  кандидатов выбрасывает по имени адаптера: проверено, что по метрике интерфейса Windows
  предпочитает как раз ВПН. Если после этого адрес всё ещё неоднозначен — скрипт не гадает,
  а просит `-Host_ <адрес>`.
* **Wi-Fi у обеих машин.** Задержка и её разброс — это про канал, а не про сервер. Поэтому
  сначала `--mode=net`, и только потом всё остальное.
