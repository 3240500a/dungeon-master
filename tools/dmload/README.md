# dmload — нагрузочный стенд на Rust

Задаёт серверу один вопрос: **сколько игроков он держит**, — и старается не мешать ему в момент
ответа. Существующий стенд на Node (`packages/server/src/loadtest/`) остаётся регрессионным
гейтом и «зрячим» клиентом протокола; этот нужен там, где прежний упирался в себя.

```bash
cargo build --release

# один замер
./target/release/dmload --base=http://127.0.0.1:3999 --n=200 --secs=20

# поиск потолка ступенями
./target/release/dmload --base=http://127.0.0.1:3999 --from=50 --step=50 --max=400

# пати по 4, как играют люди
./target/release/dmload --base=http://192.168.1.146:3001 --from=100 --step=100 --max=800 --group=4

# только канал, без нагрузки
./target/release/dmload --base=http://192.168.1.146:3001 --mode=net
```

Перед каждым прогоном сервер поднимается **с чистого листа** (`restart-server.sh`) — см.
«Комнаты живут после выхода» ниже.

## Зачем ещё один стенд

Прибор не должен быть дороже измеряемого. Замер подряд на одной машине, один и тот же сервер,
соло-боты (каждый в своей комнате):

| Ботов | Node: кадры / CPU стенда | Rust: кадры / CPU стенда |
|---|---|---|
| 50 | 20,0 / 0,28 ядра | 20,0 / 0,10 ядра |
| 100 | 20,0 / 0,33 | 20,0 / 0,14 |
| 150 | 20,0 / 0,35 | 20,0 / 0,21 |
| 200 | **18,9 ✗** / 0,38 | **19,9 ✓** / 0,28 |
| 250 | — | 15,5 ✗ / 0,26 |
| **Потолок** | **150** | **200** |

Разница в потолке — не в сервере, сервер тот же. Прежний стенд забирал у машины столько, что
его собственные боты переставали успевать читать сокет, и недобор кадров записывался серверу.
Освободили треть ядра — потолок вырос на 33 %. CPU сервера на 150 ботах: 77 % под Node-стендом
против 68 % под dmload.

В пати по 4 dmload держит 400 (на 400 сервер съел 111 % ядра: Node не строго однопоточен —
ввод-вывод и сборка мусора живут в стороне). Node-стенд в этот день на пати не гоняли, так
что A/B здесь нет — только соло.

⚠ **Абсолютные числа этого дня НЕ сравнивать с записанными в `loadtest/README.md` 250/400.**
`bench:tick` на том же ядре дал сегодня 21,24 / 24,82 / 46,06 мкс против записанных
18,97 / 22,54 / 41,5 — машина медленнее на 11 % равномерно, а потолок это ступенчатая функция.
Правило прежнее: сравнивать только прогоны ПОДРЯД. Таблица выше — прогоны подряд, поэтому
сравнение стендов в ней честное; сравнение с прошлой ночью — нет.

Цена сообщения на стороне стенда, на тех же 150 ботах: **27 мкс** против **46 мкс** у Node.
Оговорка, без которой число врёт: боты здесь **слепые** — они не разбирают двоичные кадры мира
и не сверяют контрольные суммы, а боты Node это делают. Часть разрыва — разная работа, а не
разный язык. Зрячие боты появятся в фазе С2, тогда сравнение станет полным.

## Три вещи, которые сделаны иначе

**Перцентили по каждому замеру.** Node-стенд усреднял RTT внутри бота и считал перцентили по
тысяче средних — хвосты в таком усреднении тонут. Здесь каждый замер падает в гистограмму
(4096 корзин по 250 мкс, до 1024 мс), и p50/p95/p99 считаются по всем замерам. Что не влезло
в шкалу — печатается отдельной строкой, а не тихо приписывается к последней корзине.

**Пауз сборки мусора нет.** У Node-стенда они попадали в наши же перцентили и выглядели как
задержка сервера.

**Потоков ровно столько, сколько нужно.** Умолчание tokio — поток на ядро; для нашей задачи это
худший вариант. Работы на сообщение микроскопически мало, зато каждый таймер бота будит поток
и тянет задачу через work-stealing между ядрами, а пробуждение потока на Windows дороже самой
работы. Замер на 100 ботах:

| Потоков | 16 | 4 | 2 | 1 |
|---|---|---|---|---|
| мкс на сообщение | 54,2 | 32,0 | 26,6 | 21,5 |

Умолчание — `--threads=4`, для замеров ставим 2. Один поток дешевле всего, но на нём стенд сам
становится узким местом раньше сервера.

## Что стенд нашёл в сервере

**`dm_tick_hz` занижался паузами грейса.** Комната живёт ещё час после выхода последнего игрока
(грейс на реконнект) и при этом **не тикает** — её снимают с планировщика. Но частота мира
считалась как «шаги ÷ время ÷ ВСЕ комнаты процесса». После пяти прогонов подряд накопилось
520 комнат в грейсе, и метрика показала 5,8 Гц при живых 30 — ворота качества падали на здоровом
сервере. Починено: делитель теперь `dm_rooms_ticking`, обе величины видны в `/metrics`
(и то же исправление — в сердцебиении ноды кластера, `cluster/node.ts`).

**Комнаты живут после выхода.** Это по замыслу, но для стенда означает: между прогонами память
растёт (134 → 650 МБ за пять прогонов), и ступени становятся несравнимы. Правило замера —
сравнивать только подряд и только на свежем процессе; `restart-server.sh` для этого и есть.

**Трафик на игрока зависит от возраста забега** — и это чуть не было записано в регрессию.
Первая ступень даёт 10,0 КБ/с соло, последняя 7,3: боты за это время выбивают монстров, этаж
пустеет, кадр худеет. Значит числа «на потолке» из старых таблиц сравнимы только с ПОСЛЕДНЕЙ
ступенью такого же по длине прогона. Оба стенда на каждой ступени согласны между собой.

## Ворота качества ступени

Ступень засчитана, только если держатся все:

* кадров мира не ниже 95 % нормы (20 Гц → 19,0) — иначе клиент видит рывки;
* `dm_tick_hz` не ниже 28 — ниже мир идёт в слоу-мо;
* медиана RTT в пределах `--rttLimit` (120 мс);
* никто не отвалился, ошибок сервера нет.

Последняя удержавшаяся ступень — ёмкость. Стенд печатает и **свой** расход процессора: если он
занял машину вместе с сервером, число не значит ничего, и это должно быть видно.

## Устройство

| Файл | Что внутри |
|---|---|
| `src/main.rs` | аргументы, рантайм, ступени, ворота, отчёт |
| `src/bot.rs` | один бот: регистрация → персонаж → маршрут → сокет → ввод и пинг |
| `src/http.rs` | HTTP/1.1 на семьдесят строк (нужны три запроса — hyper с rustls за них не берём) |
| `src/stats.rs` | атомики без блокировок, гистограмма RTT, своё процессорное время |

Маршрут спрашивается у `/api/route`, поэтому стенд одинаково работает и против одиночного
процесса, и против кластера: очередь на вход — штатный ответ на потолке, бот её ждёт, а не
считает ошибкой. Код комнаты несёт букву узла, поэтому не-хост ждёт код **до** маршрутизации.

## Аргументы

| | |
|---|---|
| `--base` | адрес сервера, умолчание `http://127.0.0.1:3999` |
| `--n` | сколько ботов (фиксированный замер) |
| `--from --step --max` | ступени поиска потолка |
| `--secs --warmup` | длина замера и прогрева, с |
| `--hz` | частота ввода бота, умолчание 30 |
| `--group` | размер пати; 1 — каждый в своей комнате |
| `--threads` | рабочих потоков стенда, умолчание 4 |
| `--rttLimit --tickFloor --snapHz` | пороги ворот |
| `--mode=net` | только задержка канала вхолостую |

## Сборка на Windows

Нужен линкер MinGW (`x86_64-w64-mingw32`) в `PATH`. Если сборка падает на
`dlltool.exe: program not found` — путь к MinGW записан в виде `C:/…`, а двоеточие ломает
разбор `PATH` в bash. Писать как `/c/…`.
