# dmload — нагрузочный стенд на Rust

Задаёт серверу один вопрос: **сколько игроков он держит**, — и старается не мешать ему в момент
ответа. Существующий стенд на Node (`packages/server/src/loadtest/`) остаётся регрессионным
гейтом и «зрячим» клиентом протокола; этот нужен там, где прежний упирался в себя.

```bash
cargo build --release

# один замер
./target/release/dmload --base=http://127.0.0.1:3999 --n=200 --secs=20

# поиск потолка ступенями
./target/release/dmload --base=http://127.0.0.1:3999 --from=50 --step=50 --max=400

# пати по 4, как играют люди
./target/release/dmload --base=http://192.168.1.146:3001 --from=100 --step=100 --max=800 --group=4

# только канал, без нагрузки
./target/release/dmload --base=http://192.168.1.146:3001 --mode=net
```

Перед каждым прогоном сервер поднимается **с чистого листа** (`restart-server.sh`) — см.
«Комнаты живут после выхода» ниже.

## Зачем ещё один стенд

Прибор не должен быть дороже измеряемого. Замер подряд на одной машине, один и тот же сервер,
соло-боты (каждый в своей комнате):

| Ботов | Node: кадры / CPU стенда | Rust: кадры / CPU стенда |
|---|---|---|
| 50 | 20,0 / 0,28 ядра | 20,0 / 0,10 ядра |
| 100 | 20,0 / 0,33 | 20,0 / 0,14 |
| 150 | 20,0 / 0,35 | 20,0 / 0,21 |
| 200 | **18,9 ✗** / 0,38 | **19,9 ✓** / 0,28 |
| 250 | — | 15,5 ✗ / 0,26 |
| **Потолок** | **150** | **200** |

Разница в потолке — не в сервере, сервер тот же. Прежний стенд забирал у машины столько, что
его собственные боты переставали успевать читать сокет, и недобор кадров записывался серверу.
Освободили треть ядра — потолок вырос на 33 %. CPU сервера на 150 ботах: 77 % под Node-стендом
против 68 % под dmload.

В пати по 4 dmload держит 400 (на 400 сервер съел 111 % ядра: Node не строго однопоточен —
ввод-вывод и сборка мусора живут в стороне). Node-стенд в этот день на пати не гоняли, так
что A/B здесь нет — только соло.

⚠ **Абсолютные числа этого дня НЕ сравнивать с записанными в `loadtest/README.md` 250/400.**
`bench:tick` на том же ядре дал сегодня 21,24 / 24,82 / 46,06 мкс против записанных
18,97 / 22,54 / 41,5 — машина медленнее на 11 % равномерно, а потолок это ступенчатая функция.
Правило прежнее: сравнивать только прогоны ПОДРЯД. Таблица выше — прогоны подряд, поэтому
сравнение стендов в ней честное; сравнение с прошлой ночью — нет.

Цена сообщения на стороне стенда, на тех же 150 ботах: **27 мкс** против **46 мкс** у Node.

## Зрячие боты: `--see=N`

Слепой бот считает байты и кадры, но не заметит, что кадры испорчены — сервер может слать
мусор, а стенд покажет зелёные цифры. Зрячий разбирает двоичный кадр, накладывает дельту на
свою копию мира и сверяет контрольную сумму ТОГО ЖЕ тика (сумма приезжает в кадре).

Умолчание — 20 зрячих: расхождение протокола видно и на горстке, а платить за всех незачем.
Хотя платить, как выяснилось, почти не за что — замер подряд на 200 ботах:

| | слепые | зрячие |
|---|---|---|
| мкс на сообщение | 24,3 | **27,0** |
| сверок за 25 с | — | 87 060, расхождений 0 |

**Цена зрения — 2,7 мкс на кадр**, то есть +11 % к стенду и ничего к серверу. На 60 ботах
разница вообще тонет в шуме. Значит масштаб больше не аргумент против сверки: если понадобится
гонять зрячими всех, это по карману.

⚠ **Порт декодера обязан быть доказан ДО того, как ему поверят.** Его собственная ошибка
выглядит как баг сервера — именно так теряют дни. Поэтому `npm run golden:wire` записывает
точную последовательность настоящих кадров с ожидаемыми суммами (400 кадров, из них 7 полных,
65 со снарядами, 297 с дропами), а `cargo test` прогоняет её через порт. Генератор **падает**,
если в сценарии не оказалось снарядов или дропов: иначе он выдал бы зелёный порт, который
рассыплется на живом сервере. Проверено и обратное — точечная порча множителя в сумме роняет
эталон на первом же кадре.

Три места, где порт легко разошёлся бы с оригиналом молча:

* `Math.round` округляет половину **вверх** (к +∞), а `f64::round` — от нуля: `-2.5` даёт −2
  против −3;
* `| 0` — это `ToInt32`: усечение к нулю и обрезка по модулю 2³², а не насыщение;
* хеш строки идёт по кодовым единицам **UTF-16**, а не по байтам UTF-8.

## Три вещи, которые сделаны иначе

**Перцентили по каждому замеру.** Node-стенд усреднял RTT внутри бота и считал перцентили по
тысяче средних — хвосты в таком усреднении тонут. Здесь каждый замер падает в гистограмму
(4096 корзин по 250 мкс, до 1024 мс), и p50/p95/p99 считаются по всем замерам. Что не влезло
в шкалу — печатается отдельной строкой, а не тихо приписывается к последней корзине.

**Пауз сборки мусора нет.** У Node-стенда они попадали в наши же перцентили и выглядели как
задержка сервера.

**Потоков ровно столько, сколько нужно.** Умолчание tokio — поток на ядро; для нашей задачи это
худший вариант. Работы на сообщение микроскопически мало, зато каждый таймер бота будит поток
и тянет задачу через work-stealing между ядрами, а пробуждение потока на Windows дороже самой
работы. Замер на 100 ботах:

| Потоков | 16 | 4 | 2 | 1 |
|---|---|---|---|---|
| мкс на сообщение | 54,2 | 32,0 | 26,6 | 21,5 |

Умолчание — `--threads=4`, для замеров ставим 2. Один поток дешевле всего, но на нём стенд сам
становится узким местом раньше сервера.

## Что стенд нашёл в сервере

**`dm_tick_hz` занижался паузами грейса.** Комната живёт ещё час после выхода последнего игрока
(грейс на реконнект) и при этом **не тикает** — её снимают с планировщика. Но частота мира
считалась как «шаги ÷ время ÷ ВСЕ комнаты процесса». После пяти прогонов подряд накопилось
520 комнат в грейсе, и метрика показала 5,8 Гц при живых 30 — ворота качества падали на здоровом
сервере. Починено: делитель теперь `dm_rooms_ticking`, обе величины видны в `/metrics`
(и то же исправление — в сердцебиении ноды кластера, `cluster/node.ts`).

**`dm_tick_hz` завышался, когда число комнат менялось ВНУТРИ окна.** Частота считалась как
«шаги ÷ время ÷ комнаты на момент замера». В сценарии медленных клиентов сервер отключил
половину ботов посреди окна — и метрика показала **52,4 Гц при живых 30**. Тот же перекос
работает и в другую сторону: пока комнаты добавляются, частота занижается и роняет ворота.
Починено: знаменатель теперь комнато-секунды, которые копит сам планировщик, — величина,
на которую изменение числа комнат не влияет по построению. Проверено вживую: на том же
переходе 12 → 6 комнат теперь 29,99 Гц.

**Не успевающий читать клиент отключается по молчанию, а не по переполнению.** uWS сам шлёт
ping, и клиент, который не читает, не отвечает — `idleTimeout: 32` рубит его примерно за
полминуты (замерено: 12 соединений → 6). Потолок неотправленного (`maxBackpressure`, 16 МБ)
за это время даже не подходит близко. ⚠ Проверить его на петле НЕЛЬЗЯ: ядро на loopback
поглощает всё, и `bufferedAmount` не растёт — даже при потолке в 64 КБ и клиенте, не читавшем
полторы минуты, счётчик остался нулём. Этот механизм проверяется только по настоящей сети.
Попутно потолок стал общим для обоих транспортов: у `ws` его не было вовсе (в комментарии
честно значилось «его никто не рубит»), теперь есть, вместе с метрикой
`dm_slow_clients_dropped_total` и ручкой `DM_MAX_BACKPRESSURE`.

**Комнаты живут после выхода.** Это по замыслу, но для стенда означает: между прогонами память
растёт (134 → 650 МБ за пять прогонов), и ступени становятся несравнимы. Правило замера —
сравнивать только подряд и только на свежем процессе; `restart-server.sh` для этого и есть.

**Трафик на игрока зависит от возраста забега** — и это чуть не было записано в регрессию.
Первая ступень даёт 10,0 КБ/с соло, последняя 7,3: боты за это время выбивают монстров, этаж
пустеет, кадр худеет. Значит числа «на потолке» из старых таблиц сравнимы только с ПОСЛЕДНЕЙ
ступенью такого же по длине прогона. Оба стенда на каждой ступени согласны между собой.

## Сценарии отказов (С3)

Поиск потолка отвечает «сколько держит». Эти четыре — «что ломается»; сочетаются друг с другом
и с любым режимом.

```bash
dmload --n=40 --mode=soak --secs=1200 --every=120        # выдержка: ищем ДРЕЙФ, а не потолок
dmload --n=40 --churn=40 --churnSec=20                   # реконнект: рвём связь и возвращаемся
dmload --n=40 --slow=10 --slowMs=2000                    # медленные клиенты
dmload --n=100 --burst                                   # всплеск: все подключаются залпом
```

**Выдержка** (`--mode=soak`) держит одну нагрузку и печатает окно за окном, а в конце — дрейф
первого окна против последнего. Проваленное окно её НЕ останавливает: интересно ровно то, как
деградация пойдёт дальше. Смысл в том, что сервер, который час держит те же числа, и сервер,
у которого память растёт по мегабайту в минуту, на коротком замере неразличимы.

**Реконнект.** Здесь легко проверить не то. Входов в игру ТРИ, и они делают разное:

| join | что делает сервер |
|---|---|
| `resume: true` | возвращает в свой забег: грейс-комната или пересборка из сейва |
| `roomCode` | осознанный вход в чужую комнату — свой незавершённый забег считается **брошенным**, персонаж получает штраф смерти |
| `fresh` | новая комната с нуля |

Первая версия сценария рвала связь и возвращалась `roomCode` — сервер честно отвечал «комната
не найдена» (соло-комната ушла в грейс, а по коду её не отдают) и заодно засчитывал забег
брошенным. Правильный реконнект — `resume`. Замер на 40 соло-ботах, рвущих связь каждые 20 с:
**220 возвращений за 2 минуты, ноль ошибок, ноль расхождений дельт**, кадры и тик не дрогнули.

**Медленные клиенты** (`--slow=N --slowMs=M`) читают сокет с паузой — так ведёт себя подвисший
главный поток браузера. Гейт на кадры при них ОТКЛЮЧАЕТСЯ: среднее по построению тянут вниз
наши же боты, и здоровье сервера в этом сценарии показывают тик, RTT остальных и рост памяти.

**Всплеск** (`--burst`) снимает разбивку при подключении. 100 ботов залпом: все вошли, ошибок
нет, RTT 6,4 мс.

## Сравнение прогонов (С4)

```bash
dmload --n=200 --secs=25 --out=before.json
#   ... правка сервера ...
dmload --n=200 --secs=25 --out=after.json
dmload --compare=before.json,after.json
```

Правило в этом проекте одно и выстрадано: **сравнивать только прогоны подряд**. Но глазами
сравнивают плохо — на этом уже один раз поехал разбор: числа дня сопоставили с числами ночи
и получили вывод об «оптимизации», которой не было (машина в тот день оказалась на 11 %
медленнее). Поэтому сравнивает инструмент, и первым делом он ГРОМКО говорит, когда сравнивать
нельзя: разные параметры прогона, разная машина, разрыв во времени больше часа. Только потом —
таблица «было → стало» и ёмкость.

## Ворота качества ступени

Ступень засчитана, только если держатся все:

* кадров мира не ниже 95 % нормы (20 Гц → 19,0) — иначе клиент видит рывки;
* `dm_tick_hz` не ниже 28 — ниже мир идёт в слоу-мо;
* медиана RTT в пределах `--rttLimit` (120 мс);
* никто не отвалился, ошибок сервера нет;
* расхождений реконструкции нет — любое означает порчу протокола.

Последняя удержавшаяся ступень — ёмкость. Стенд печатает и **свой** расход процессора: если он
занял машину вместе с сервером, число не значит ничего, и это должно быть видно.

## Устройство

| Файл | Что внутри |
|---|---|
| `src/main.rs` | аргументы, рантайм, ступени, ворота, отчёт |
| `src/bot.rs` | один бот: регистрация → персонаж → маршрут → сокет → ввод и пинг |
| `src/http.rs` | HTTP/1.1 на семьдесят строк (нужны три запроса — hyper с rustls за них не берём) |
| `src/stats.rs` | атомики без блокировок, гистограмма RTT, своё процессорное время |
| `src/wire.rs` | порт клиентской половины протокола: разбор кадра, дельта, контрольная сумма |
| `src/report.rs` | отчёт прогона в JSON и сравнение двух отчётов с оговорками |
| `tests/golden.json` | эталонные кадры от настоящего движка (`npm run golden:wire`) |

Маршрут спрашивается у `/api/route`, поэтому стенд одинаково работает и против одиночного
процесса, и против кластера: очередь на вход — штатный ответ на потолке, бот её ждёт, а не
считает ошибкой. Код комнаты несёт букву узла, поэтому не-хост ждёт код **до** маршрутизации.

## Аргументы

| | |
|---|---|
| `--base` | адрес сервера, умолчание `http://127.0.0.1:3999` |
| `--n` | сколько ботов (фиксированный замер) |
| `--from --step --max` | ступени поиска потолка |
| `--secs --warmup` | длина замера и прогрева, с |
| `--hz` | частота ввода бота, умолчание 30 |
| `--group` | размер пати; 1 — каждый в своей комнате |
| `--threads` | рабочих потоков стенда, умолчание 4 |
| `--see` | сколько первых ботов зрячие (разбор + сверка суммы), умолчание 20 |
| `--mode` | `ramp` (умолчание), `soak` (выдержка), `net` (только канал) |
| `--every` | шаг отчёта в выдержке, с (умолчание 60); `--secs` тогда = вся длительность |
| `--churn --churnSec` | сколько ботов рвут связь и через сколько секунд |
| `--slow --slowMs` | сколько ботов читают медленно и с какой паузой |
| `--burst` | подключаться залпом, без разбивки |
| `--rttLimit --tickFloor --snapHz` | пороги ворот |
| `--mode=net` | только задержка канала вхолостую |
| `--out` | записать отчёт прогона в JSON |
| `--compare` | `первый.json,второй.json` — сравнить два отчёта и не соврать при этом |

## Сборка на Windows

Нужен линкер MinGW (`x86_64-w64-mingw32`) в `PATH`. Если сборка падает на
`dlltool.exe: program not found` — путь к MinGW записан в виде `C:/…`, а двоеточие ломает
разбор `PATH` в bash. Писать как `/c/…`.
